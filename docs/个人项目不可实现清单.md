# 个人项目不可实现清单（JD 砍词字典）

> step00 选题阶段必查。JD 里出现下列词时，**主动砍掉、不硬塞进个人项目**。
> 面试时诚实说「了解原理但未在生产环境实践」，比造假被追问穿帮强。
> 每完成一个项目（step10 选题准确率复盘），回头补充新踩过的坑。

---

## 一、本机硬件跑不动（RTX 2050 4GB + 16GB 内存）

| 词 | 为什么做不了 | 面试怎么说 |
|---|---|---|
| 大模型微调 / 7B+ 本地推理 | 4GB 显存放不下 7B 量化模型，16GB 内存跑训练直接 OOM | 了解 LoRA/QLoRA 原理，实践用远程 API + RAG |
| K8s 集群 / 多节点分布式部署 | 本机起不了多节点，Docker Desktop 单节点都紧张 | 了解 K8s 编排原理，本地用 Docker Compose 模拟多服务 |
| 存算分离 / 存算一体 | 需要分布式存储集群（Ceph/MinIO 集群），个人项目没有多机 | 了解存算分离架构思想，本地用单机 MinIO |
| 全球化部署 / 多区域容灾 | 需要多机房、CDN、全球 DNS，个人项目无资源 | 了解多活/异地容灾概念，本地只做单区域 |
| GPU 训练类 CV/多模态项目 | 4GB 显存训练不动任何有规模的模型 | 用现成模型 API，不做训练 |
| 超过 5 个服务的微服务拆分 | Docker Compose 起 5+ 个 JVM/Node 进程 16GB 内存吃满 | 单体 + 模块化分包，或最多 3-4 个服务 |

## 二、业务量级撑不起来（个人项目没真实流量）

| 词 | 为什么做不了 | 面试怎么说 |
|---|---|---|
| 高并发秒杀 / 百万 QPS | 个人项目没有真实流量，压测数据撑不起"生产级高并发"叙事 | 在压测脚本里把瓶颈分析讲清楚（连接池/线程池/DB 索引），承认是工程验证非生产流量 |
| 大数据离线数仓 / PB 级数据 | 没有真实业务数据，造的假数据没有统计意义 | 了解数仓分层（ODS/DWD/DWS/ADS），本地用小数据集演示链路 |
| 实时数仓 / Flink 实时计算 | 本机起不动 Flink 集群 + Kafka 大流量 | 了解 Flink 窗口/水位线/Exactly-Once 原理，本地用单节点演示 |
| 千万级用户 / 千万级日活 | 个人项目没有真实用户基数 | 承认是练手项目，把重点放在架构可扩展性设计上 |

## 三、需要企业资质/真实数据/合规审批

| 词 | 为什么做不了 | 面试怎么说 |
|---|---|---|
| 支付系统（微信/支付宝真实商户号） | 需要企业资质、商户号、真实资金流 | 用模拟支付沙箱，讲清楚支付状态机和对账逻辑 |
| 真实短信/邮件群发通道 | 需要企业签名和模板审核，个人申请不到 | 用测试通道或 mock，讲清楚幂等和重试 |
| 等保三级 / 金融级合规 | 个人项目过不了等保测评 | 了解等保要求，把能做的安全实践（鉴权/审计/加密）做到位 |
| 实名认证 / 人脸识别 | 需要企业资质对接公安/运营商接口 | 用 mock 替换，讲清楚 Oauth2/SSO 流程 |

## 四、需要多端/多角色协同场景撑不起来

| 词 | 为什么做不了 | 面试怎么说 |
|---|---|---|
| 全渠道（App + 小程序 + H5 + 公众号） | 一个人写不动四端 | 聚焦 Web 端，讲清楚多端共用后端 API 的设计 |
| 复杂工作流引擎（BPMN 全功能） | 个人项目流程没那么复杂 | 用状态机自己实现核心流转，讲清楚状态机设计模式即可 |

## 五、框架版本与过度选型避坑（本机实测，2026-10-28 回填）

> 来源：saas-workflow-agent 第 10 步复盘。以下不是"绝对做不了"，而是"个人项目里性价比极低/容易翻车"。

| 词/组合 | 为什么个人项目要谨慎 | 面试怎么说 |
|---|---|---|
| CrewAI 1.x 全家桶（含 Crew/记忆/工具） | 1.15.30 牵出 langgraph/pydantic/httpx/pyyaml/uvicorn 五连版本冲突；Windows 受限环境下 import 期写探测会长时间阻塞；`BaseLLM.call` 签名随版本漂移。本项目为此付出 9 条失败记录、跨 4 小时排障 | 讲清多 Agent 编排原理与三角色协作，说明适配层如何隔离三方库版本风险；不吹"开箱即用" |
| Spring Cloud Alibaba / Nacos / Sentinel | 需要额外注册中心与控制台，个人项目往往只引 BOM 不落地，成为"纸面技能点" | 了解服务注册/配置中心/熔断原理，诚实说明本项目未落地，只用 Spring Boot 模块化 |
| Qdrant / 向量库（无真实检索需求时） | 容器能起但检索/召回/评测要额外工作量，容易"容器在、功能无"，形成沉没成本 | 讲清 RAG 原理与向量检索流程；若未实现就明说，或改用 MySQL 全文检索降级并讲清取舍 |
| 真实 LLM 语义生成验收（无 key 时） | 无 key 只能做协议替身，语义质量无法评审；不能因此把整条链路挂起不验 | 区分"协议链路已验证"与"语义质量未验证"，主动标注缺口，不把 Mock 当真实能力 |
| patch 三方 SDK 类属性（如 `OpenAI.chat`） | 2026-10-30 llm-eval-observability 实测：openai 1.57.4 的 `chat` 是**实例属性**不是类属性，`patch.object(OpenAI, "chat")` 直接 AttributeError（P1 事故 Q-002）；且三方类结构随版本漂移 | hook 目标选实测存在的类方法（如 `Completions.create`），全链路 try/except 兜底降级手动模式；面试讲"适配层隔离三方版本风险"，不吹"无缝自动注入" |
| Windows 本机测试用 `localhost` / PowerShell `curl` | 2026-10-30 实测双坑：①`localhost` 触发 IPv6(::1) 回退，每连接固定 ~2s 延迟（Q-001 虚惊一场 P1）；②PowerShell `curl` 是 Invoke-WebRequest 别名，JSON 中文按 Latin-1 提交全丢（Q-004） | 本机测试一律 127.0.0.1；提交中文用 curl.exe 或 python requests；别把工具伪影当应用 bug 修 |
| 多厂商真实 LLM 调用（无 key 时） | 2026-11-01 saas-workflow-agent 实测：只有 DashScope 有 key，DeepSeek/OpenAI/Claude 只能做协议替身；若按「3 家真调」设计会把验收拖死，且容易把 Mock 包装成真实能力 | 讲清「统一适配层 + 一家真调 + 其余协议替身」的分层口径，主动标注 Mock；不要把协议替身说成厂商对接经验 |
| 全容器化 5 服务端到端（本机 16GB） | 2026-11-01 saas-workflow-agent 实测：3 个应用进程 + 3 个中间件容器同机，Docker Desktop 内存紧张，应用容器化路径未做端到端复验；compose 文件写好不等于部署跑通 | 讲清 Compose 编排与中间件容器化实践，明确应用进程本地直跑、全容器化未做端到端验证，不吹「一键部署」 |
| WSL2 内 `perf record/report` 火焰图（cpp-game-server-kit 实测） | WSL 内核与系统 perf 版本不匹配，perf 不可用，出不了热点函数栈与火焰图；只能 ps/top -H 线程级采样替代 | 讲清 perf 原理与热点定位思路，说明本机受 WSL 限制未出火焰图，以线程级采样 + 压测拐点归因，不贴不存在的火焰图 |
| JMeter 压测私有 TCP+Protobuf 二进制协议 | JMeter 原生 TCP Sampler 无法静态构造 pb body，动态序列化要在 JSR223 另写一套客户端，成本高收益低；jmx 骨架不产出可运行压测 | 用 Python 多线程 / 自研 C++ 客户端压测；讲清私有协议压测工具选型取舍，不吹「JMeter 压测达标」 |
| 自研最小 KCP 兼容实现 ≠ 原版 libkcp 深度可靠传输 | 自研最小兼容实现只打通收发封装；超时重传、滑动窗口、丢包注入未端到端验证，裸 UDP 客户端解不出应用层帧时间戳 | 讲清 KCP 封装与收发链路，明确 ARQ/窗口为既定边界，不吹「KCP 可靠传输深度调优/抗丢包实测」 |
| 单机回环承诺 ≥30% QPS 调优收益 | 回环 RTT、epoll 唤醒粒度、同步读写模型与单线程压测客户端构成瓶颈，用户态字符串/容器微调收益仅个位数百分比；个人项目无真实流量也打不满服务端 | 讲清瓶颈分层归因（线程数/同步阻塞/调度/客户端），承认是工程验证非生产流量；设计阶段不承诺固定 ≥30% 提升目标 |

## 维护规则

- step00 拆 JD 时，遇到上面表里的词，直接在 `00_JD技能点清单.md` 的 `red_flags` 字段标出来
- step00 选题设计书 §8「主动砍掉的东西」必须引用本表条目
- step10 选题准确率复盘时，如果发现表里某个词**其实能做**（比如降级后能做），从表里移到「可做但需降级」区；如果发现新踩了一个做不了的坑，加进对应分区
- 这个文件进 Git，长期沉淀，不删历史条目
