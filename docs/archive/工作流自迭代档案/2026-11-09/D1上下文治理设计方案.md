# D1 上下文治理 · 设计方案

> **历史档案 · 章节编号说明（2026-11-09）**：本文件正文沿用 2026-11-08 之前的旧版主控章节编号（§0–§9）。主控现为 <100 行指针文件，现行权威见 `WORKFLOW_步骤定义.md` / `WORKFLOW_规则库.md` / `WORKFLOW_卡点协议.md` / `WORKFLOW_执行约定.md`；文中「主控 §X」均指旧版，勿按现行章节查找。

> 对应本质问题 E1（流水线为"人"设计，不是为 AI）+ 架构问题 D1（上下文管理失败）。
> 目标：把"每次新对话必读 557 行主控"降到"每次新对话读 <100 行主控 + 1 张输入卡"。
> 原则：不推翻 step 编排，只做"瘦主控 + 按需加载 + 脚本即规则 + 输入卡交接"。

---

## 一、现状问题

| 问题 | 数据证据 |
|---|---|
| 主控 557 行，每个新对话必读 | §4.2 新对话恢复清单要求读 §0–§7 + §8 本步规则 |
| 25 条规则是文字描述，Agent 要背 | R1–R25 正文全在主控 §8，每次新对话都要重新读 |
| 步骤间交接靠文档，信息密度低 | R21 交接卡 6 行 + 看板恢复摘要 5 字段，Agent 还要重新读大量产物 |
| 产物全量进对话，按需读没执行 | #62 已加"上下文卫生"约定，但实际执行中 Agent 经常全量读上游产物 |

## 二、四个改造点

### 改造点 1：主控拆成按需加载（瘦主控）

**现在**：一个 557 行单体文件，包含流程图、步骤表、双模块协议、单步协议、卡点表、闸门表、循环规则、看板规则、25 条规则、登记表、休眠区、唤起口令、step00 反粗制滥造规则。

**改造后**：

| 文件 | 内容 | 什么时候读 |
|---|---|---|
| `WORKFLOW_主控.md` | **<100 行**：流程图 + 底线规则 4 条 + 指针（指向其他文件） | **每次新对话必读** |
| `WORKFLOW_步骤定义.md` | §2 步骤编排表 + §3 双模块协议 | 执行某步时读对应行 |
| `WORKFLOW_规则库.md` | §8 全量：R1–R25 + 登记表 + 休眠区 | **日常不读**；只在 step11 体检时读全量 |
| `WORKFLOW_卡点协议.md` | §5 人工卡点表 + §5.1 机器闸门表 | 到卡点/闸门时读 |
| `WORKFLOW_执行约定.md` | §4 单步协议 + §6 循环回流 + §7 看板规则 | 新对话恢复时读一次（约 30 行） |

**瘦主控长什么样（草案）**：

```markdown
# 从 0 到 1 项目自动工作流 · 主控

> 本文件是入口，<100 行。详细规则见各专项文件。

## 流程图
（保留现有 §0 总执行顺序图，约 20 行）

## 底线规则（4 条，不可违背）
1. 卡点不跳过：到卡点必须停，等用户确认
2. 机器校验优先：能跑脚本就跑脚本，脚本结果才是判据
3. 不虚构运行结果：有终端就必须亲自跑
4. 产物落盘 + 逐步回写：不靠对话记忆充当产物

## 指针
- 步骤编排表 → WORKFLOW_步骤定义.md
- 卡点/闸门 → WORKFLOW_卡点协议.md
- 执行约定（单步协议/循环/看板）→ WORKFLOW_执行约定.md
- 规则库 R1–R25 → WORKFLOW_规则库.md（日常不读，step11 体检时读）
- 翻新线协议 → WORKFLOW_翻新线设计.md
- 唤起口令 → WORKFLOW_唤起口令.md
```

**关键变化**：规则库从"每次必读"变成"日常不读"。因为规则已经由脚本执行了，Agent 不需要背规则正文。

---

### 改造点 2：规则从"文字"变"脚本即规则"

**现在**：25 条规则，每条都有详细正文（为什么加、怎么执行、证据是什么）。Agent 每次新对话都要重新读一遍才能知道怎么做。

**改造后**：

**主控里只留一句话摘要 + 对应执行方式**：

```
| R1 | 卡点不跳过 | 到卡点必须停，见卡点协议.md |
| R9 | 机器校验优先 | 能跑脚本就跑脚本，结果才是判据 |
| R10 | 失败必记录 | 返工/打回/拦截时跑 log_failure.py |
| R17 | 完成门禁唯一判据 | 改队列状态前必须跑 workflow_completion_check.py |
```

**规则的详细解释（为什么加、来源证据、执行细节）全部移到规则库.md**。

**Agent 执行步骤时不需要读规则库**——它跑脚本，看脚本输出，按脚本输出行动。就像你不需要读"红灯停绿灯行"的规则原文，你只需要看红绿灯。脚本就是红绿灯。

**什么时候才需要读规则库？**
- step11 工作流自迭代时（要做规则治理：体检、休眠、复用）
- 新规则 triage 时（要判断是复用旧规则还是新建）
- 日常执行步骤时，**不读**

---

### 改造点 3：步骤间用"输入卡"交接

**现在**：步骤间靠产物文件串联。Agent 执行 step N 时，要读很多 step N-1 的产物（基线/架构/任务拆解/映射表），信息密度低、上下文负载大。

**改造后**：每个步骤定义里写死"输入卡"——本步需要的所有上游信息，压缩到 1-2 页结构化卡。

**输入卡格式**（YAML，结构化不是散文）：

```yaml
# step5A 后端开发 · 输入卡
project: saas-workflow-agent
tech_stack:
  backend: Java 17 + Spring Boot 3
  db: MySQL 8 + Redis 7
  mq: RabbitMQ
tasks:
  - task_id: T01
    desc: 实现 Workflow CRUD 接口
    endpoint: POST /api/v1/workflows
    contract_ref: 06.5_契约/openapi.json#/paths/~1api~1v1~1workflows/post
  - task_id: T02
    desc: 执行引擎核心逻辑
    ...
ports:
  backend: 8083
  mysql: 3310
  redis: 6379
hardware_limit: RTX 2050 4GB + 16GB 内存
mock_policy: 外部依赖必须 Mock，带 # MOCK: 注释
```

**关键设计**：
- 输入卡由上一步产出时自动生成（比如 step4 产出任务拆解时，同时生成 step5A 和 step5B 的输入卡）
- Agent 只读输入卡，不读上游产物全文
- 输入卡 ≤ 1 页，超过说明信息冗余
- 输入卡是"指针式"的——需要详细信息时才去读对应产物，不预加载

**哪些步骤需要输入卡？**
- step1 基线 → 输入卡：项目原始描述 + JD 对账表
- step2 架构 → 输入卡：基线说明书 + 硬件约束 + 端口分配
- step4 拆解 → 输入卡：架构定稿 + D-清单
- step5A/5B → 输入卡：任务拆解 + 契约冻结点 + 端口
- step6 冒烟 → 输入卡：代码目录 + 启动命令 + 探活 URL + P0 任务清单
- step8 测试 → 输入卡：基线指标 + 干净系统 + p0_cases
- step9 验收 → 输入卡：基线 + 问题台账 open/deferred + 安全扫描通过证明

---

### 改造点 4：产物按需读，不预加载

**现在**：§4.2 "新对话恢复清单"已经规定了"按 step 追加读"，但实际执行中 Agent 经常把上游产物全量读进来。

**改造后**：在每个步骤定义里明确写"本步必读文件"和"本步选读文件"：

```
## step6 冒烟
- 必读（≤3 个）：
  1. _项目状态.md（看板）
  2. 输入卡（step5A/5B 产出）
  3. 06_冒烟/冒烟记录.md（若已存在）
- 选读（按需）：
  - 架构定稿（只查某个接口设计时）
  - 映射表（只查某条 D-清单状态时）
  - 报错档案（修某个 bug 时）
```

**硬规则**：
- 必读文件 ≤ 3 个
- 选读文件按需读，不预加载
- 大文件分段读（已经是约定，强化执行）

## 四、风险和注意事项

| 风险 | 应对 |
|---|---|
| 拆分后多份文件事实源漂移（#94 刚审计过这个问题） | 步骤定义.md 是唯一事实源，steps.yaml 是机器可读版本；主控只留指针不复制内容 |
| 规则库不日常读，Agent 会不会不知道规则？ | 不会。规则由脚本执行，Agent 跑脚本就知道了。就像红绿灯不需要读规则原文 |
| 输入卡谁来生成？ | 上一步产出时自动生成。比如 step4 产出任务拆解时，同时生成 step5A/5B 输入卡 |
| 输入卡会不会信息不全？ | 输入卡是指针式的——需要详细信息时才去读对应产物。宁可少给、按需读，不要多给、预加载 |
| 瘦主控会不会太瘦，丢失关键信息？ | 底线规则 4 条不可删；流程图不可删；指针不可删。其他全部移到专项文件 |

## 五、实施步骤（建议顺序）

1. **先拆主控文件**：把 557 行拆成 5 个文件（主控/步骤定义/规则库/卡点协议/执行约定），内容不增不减，只是物理拆分
2. **再瘦主控**：把规则正文从主控移到规则库，主控只留一句话摘要 + 指针
3. **然后做输入卡 schema**：定义 YAML 格式，先从 step5A/5B/step6 三个高频步骤试点
4. **最后改步骤定义**：每个步骤加"必读/选读文件"清单

**每一步做完验证一次**：新对话恢复时，读的文件是不是变少了？上下文负载是不是降了？不要一口气全改完再验证。
