> **阶段**：「优化」四阶段之第 2 阶段——出方案交用户审核。**本草案审核通过前，不改任何活文档 / 脚本 / 模板 / 队列状态。**

> **参照范式**：`WORKFLOW_翻新线设计.md`——前几步专属建档/设计，中段验证与尾部交付复用生产线序列。
> **权威文件边界**：现行流程以 `WORKFLOW_步骤定义.md` / `WORKFLOW_规则库.md` / `WORKFLOW_卡点协议.md` / `WORKFLOW_执行约定.md` 为准；本档案是一次性方案，落地后归档只读。

## 一、背景与定位

现有两条线路都不覆盖「已交付闭环的项目继续加增量能力」：

| 线路 | 适用对象 | 本质 | 前置专属步骤 | 中段/尾部复用 |
|---|---|---|---|---|
| 生产线（step00→11） | 从 0 到 1 新项目 | 新建 MVP，走全序列门禁 | step00 选题 → 0.5 设计书 | step1→11 全序列 |
| 翻新线（F0→F4） | 野生老项目 / 已交付但未达标的项目 | 体检返修、补门禁、修烂尾 | F0 迁入建档 / F1 逆向建档 / F2 九维度体检 | F3 返修复用 5.5→6→6.5→7→7.5→8→8.5→9；F4 复用 step10→10.0→10.5→10.6→11 |
| **迭代线（I0→I3，本规格）** | **已交付闭环的项目，继续加增量能力** | 增量开发：新 JD 缺口补强 / 硬骨头升级 / 性能或 UI 改进 / 自用工具持续迭代；**不推翻已验收架构** | **I0 增量建档、I1 增量设计评审** | I2 复用 5.5→6→6.5→7→7.5→8→8.5→9；I3 复用 step10→10.0→10.5→10.6→11 |

**完成定义（硬目标）**：每轮迭代结束必须通过不退化校验 + 生产线对应门禁全绿；不设降级档。

**适用入口对象**：`projects/` 下已闭环（门禁全绿 / 已交付）的生产线或翻新线项目。野生未闭环项目不走迭代线。

| B 首批试点项目 | **待定** | 候选：`dev-metrics-dashboard`（自用效能工具，长期迭代典型）；落地首个迭代项目前由用户点名 |

## 三、入口与路由

### 3.1 入口

| 入口 | 唤起口令 | 适用对象 | 差异 |
|---|---|---|---|
| 迭代入口 | 「迭代：<项目名>，<增量目标>」 | `projects/<项目名>/` 下已闭环项目 | 走 I0→I1→I2→I3 |

启动前置校验：项目看板状态为已完成 / 已闭环，且 10.0 门禁曾全绿（历史豁免项目走人工确认）。未闭环项目拒绝进入迭代线。

### 3.2 三线路由原则

```
已交付项目要加东西
  ├─ 发现是 v1 原有硬伤 / 烂尾 / 缺门禁 → 转翻新线 F2 体检（不在迭代线返修）
  ├─ 命中 §六拆项硬信号（推翻架构 / 重写闭环模块 / 换栈 / 独立子系统 / 破坏性契约）
  │     → 拆成新生产线项目，不走迭代线
  └─ 增量在现有架构边界内 → 留迭代线
```

「继续」「这是报错：」「回到第 X 步」「人工检查通过，继续」等既有口令对迭代线同样生效。

### 4.1 I2 增量验证条款（复用步骤，挂增量条款）

- 复用 v1 代码骨架；本轮改动文件以 I0 增量基线书登记清单为准，不碰 out_of_scope。
- 5.5 独立 Review：新上下文、同铁律，三层含「回归」维度。
- 冒烟：增量链路走通 **+ v1 主链路不退化探活**。
- 增量回归：v1 已验收 P0 链路仍通；v1 基线 C 指标不下降（不退化校验，§五）。
- 8.5 安全扫描覆盖增量代码。

### 4.2 I3 交付条款

- 版本号 v2.0（大增量）/ v1.1（小修）+ changelog（新增 / 修改 / 修复 / 仍 deferred）。

- 反查对应 S1 JD，四同步回写 → S2。
- 门禁复用 `workflow_completion_check.py`，加「不退化」核对项。

## 五、指标挂接规则（沿用 / 演进 / 新增）

一张统一指标表，每条标类型；编号全局唯一续排，旧号不回收、不重排。

| 指标ID | 归属版本 | 类型 | 指标描述 | v1 基线值 | 本轮目标值 | 实测值 | 口径/来源 |
|---|---|---|---|---|---|---|---|
| C03 | v1 | 演进 | 列表接口 P95 响应 | 200ms | 150ms | 待实测 | 本轮 step8 验证表 |
| C07 | v1 | 沿用 | 登录成功率 | ≥99.9% | ≥99.9% | 待实测 | v1 基线 |
| C12 | v2 | 新增 | 增量导出任务成功率 | — | ≥99% | 待实测 | 本轮 step8 验证表 |

- **沿用（keep）**：v1 指标，本轮不动，继续守着不许退化。
- **演进（evolve）**：同一指标本轮提目标 / 调口径，**ID 不变**，保留 v1 基线值再填本轮目标值，前后对比看脉络。
- **新增（new）**：新功能带来的全新指标，接 v1 最大编号往下续，归属版本标本轮。

**不退化判据**：沿用 + 演进类，本轮实测不得跌破 v1 基线值（演进类目标可更高，底线不降）；新增类无基线，只看本轮达标。

> 待定细化（不阻塞草案）：指标表落在增量基线书内还是独立 v2 指标表；脚本解析表头口径；与现有 `_设计实施映射表.md`「验收指标」列的挂接方式（倾向：原表加「归属版本」列，v1 行保留 + 追加 v2 行）。

## 六、拆项红线与边界复核

### 6.1 留在迭代线（同时满足）

- 不动已验收的架构分层；
- 不重写已闭环模块；
- 不换技术栈 / 核心框架 / 数据库 / 消息队列；
- 新功能挂得进现有模块与对外契约；
- 改动文件在 I0 增量基线书登记范围内。

### 6.2 必须拆成新生产线项目（命中任一硬信号）

1. 推翻或重构 v1 已定架构（分层、模块划分、数据流）；
2. 整体重写某个已闭环交付的模块；
3. 换技术栈、核心框架、数据库、消息队列等基础依赖；
4. 新功能是自成体系的独立子系统（独立业务域 / 数据模型 / 对外契约），硬塞会糊掉边界；
5. 破坏性 Schema 迁移，或改对外契约且 v1 调用方无法兼容；
6. ~~轮次到顶~~（**已取消硬轮次上限**，见 §二 C）。

### 6.3 转翻新线

迭代中发现的是 v1 原有硬伤、烂尾、缺门禁 → 走翻新线 F2 体检，不在迭代线内返修。

### 6.4 v5 软复核

做到 v5 时，I0 建档环节逐条对照 §6.1 / §6.2 做边界复核，结论写入增量基线书；未踩信号继续，踩到信号按 §3.2 路由。拿不准归类的信号先记入迭代问题清单待观察，不阻塞本轮。

## 七、目录与产物约定（E · 第二类摆法）

**原则**：不新建 `I0_` / `I1_` 专属编号目录；增量产物归到对应生产线步骤目录下，按轮次（`v2/`、`v3/`……）分子目录；**v1 全部产物原样保留，不得覆盖**。代码是活代码，不按轮次分文件夹，历史版本靠 git commit 留痕。

以某项目出 v2 为例：

```
projects/<项目名>/
├── 01_增量基线书_v2.md            # I0 产物（01 现状为根目录单文件，增量版平级放置，不动 v1 原文件）
├── 02_架构设计/
│   ├── （v1 旧架构文档原样保留）
│   └── v2/增量设计与影响面.md      # I1 产物
├── 05_代码/                        # 活代码，不分轮次；改动范围由 I0 基线书登记、脚本核对
├── 05.5_代码Review/v2/代码Review报告.md
├── 06_冒烟/v2/冒烟记录.md（+ UI/taste 报告）
├── 06.5_契约/v2/openapi.json + 校验记录.md
├── 07_联调/v2/联调检查清单.md + 数据重置记录.md
├── 08_测试/v2/p0_cases.json + 基线指标验证表.md
├── 08.5_安全扫描/v2/docs/安全扫描报告.md
├── 09_验收/v2/最终验收清单与报告.md
├── 10_交付/v2/changelog.md + 简历项目描述（增量段）+ 面试问答库（增量段）
├── _问题台账.md / _失败日志.md      # 追加本轮条目，不清空 v1 记录
├── _设计实施映射表.md               # 加「归属版本」列：v1 行保留 + 追加 v2 行
└── _项目状态.md                     # 路线=迭代；迭代轮次=v2
```

> 待审核确认点：I0 增量基线书落在根目录平级文件（上表口径），还是建 `01_基线说明书/v2/` 目录；02 及以下步骤目录已有目录结构，直接挂 `v2/` 子目录无歧义。

## 八、看板 / 队列 / 状态机改动

- **状态机不变**：沿用 待开工 → 进行中 → 已完成；不新增状态枚举（与翻新线 §5 同范式）。
- **看板新增字段**：
  - `路线` 取值扩为 生产 / 翻新 / **迭代**；
  - 新增 `迭代轮次`（v1 / v2 / v3……）；
  - 新增 `上一轮 git commit`（不退化对照基线，可选）。
- **队列「路线」列**：加「迭代」取值；事实列（状态 / 完成日期 / 卡点）仍由 `wf queue --sync` 推导，禁止手改。
- 迭代轮次不进主状态枚举，避免 v3/v4 每轮改状态机与门禁脚本。

## 九、简历适配规则（10.6）

- **一个项目条目**：单一标题、一句最新定位概述；内部按版本分段——一期 v1 的 bullet；迭代 v2/v3 增量 bullet（标注「v2 新增/优化」）。**不得写成两个项目、两段独立定位。**
- 投递取舍：篇幅有限时优先保留最新、功能最全版本的 bullet；旧轮次只留体现复杂度与演进的关键条，细节可砍。
- 数字仍只来自本轮实测产物；未验证写「未验证」，不拿设计目标值冒充实测。

## 十一、开放问题（专题细化时拍板，不阻塞草案审核）

1. 看板「迭代轮次」字段格式；CLI 队列推导是否在业务一句话/卡点列展示轮次。
2. 指标表载体（增量基线书内 vs 独立 v2 指标表）与脚本解析表头口径。
