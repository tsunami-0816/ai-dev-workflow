## 一、P1 每日求职流程（日巡检编排）

### 1.1 现状与缺口

求职入口 `D:\lg\_求职流水线入口.md` 已有 4 个分散触发词：甩 JD+「存入」（入库）、「开始生成」（出简历）、「最近投了哪些」/「XX 约面试/拒了」（台账）、「启动队列下一个」（补项目）。缺口是**没有一个按固定顺序串起来的日流程**，每天要靠人记着先做哪步；补项目跟进也没有和当日入库/生成/投递串成一条线。

### 1.2 方案：新增日巡检口令「今日求职」

**触发词**：「今日求职」/「每日流程」/「跑一下今天的求职流水线」。

**固定顺序（每步产物落盘、状态机只认产物）：**

```
① 恢复现场（只读，不改动）
   ├─ 读求职入口 → PROJECT_INDEX.md → JD 仓库 _索引.md → 投递跟踪.md
   ├─ 读本仓 WORKFLOW_项目队列.md + 进行中项目 _项目状态.md
   └─ 三文件交叉核对：索引分区 vs 台账 vs 当前投递/ 实物，不一致以产物为准先修滞后

② 入库（需用户提供新 JD 截图）
   └─ 走阶段一入库流程：保存截图 → 分段 OCR 逐字全文 → 字段完整性清单
      → skills.json 落盘 → 对账（机器校验 + 人工复核）→ 三结局
      → 落 S0 / S1(等项目) / S2(待生成) / S5(留档)，更新索引与队列

③ 待生成（S2）
   ├─ 列出 S2 清单（公司/岗位/星级/命中项目），用户选范围（全部/前 N/指定公司）
   ├─ 分批出 PDF + 话术，过出件门禁（0 meta 泄漏、数字有出处、PDF 回读）
   └─ 过门禁 → S3 待投递；四同步回写（JD md / 索引 / 台账 / 优先级队列）

④ 待投递（S3）
   ├─ 列 S3 清单：公司/岗位/简历 PDF 路径/打招呼话术，交用户去 Boss 手动投
   ├─ 用户回填「投了」→ S4；岗位关闭/过期 → S5
   └─ 不自动代投（投递是真人动作）

⑤ 补项目跟进（S1 ⏳等项目 ↔ 工作流队列）
   ├─ 扫所有 S1 的 JD md，取「待补项目」清单
   ├─ 对照本仓队列：
   │    ├─ 进行中项目 → 读看板卡点，按「继续」推进；卡在人工卡点就列给用户，不跳过
   │    ├─ 待开工项目 → 按优先级列出，等「启动队列下一个」，不擅自开工
   │    └─ 刚完成项目 → 反查 S1 清单：待补项目清单空了 → 提示可出简历；还有 → 说明还在等什么
   └─ 项目 step10 门禁全绿后，按四同步反向回写对应 JD → S2

⑥ 当日小结（落盘）
   └─ 一份日巡检记录：入库 X / 生成 Y / 待投 Z / 在做项目 W 及卡点 / 阻塞项
      落点建议：`D:\lg\resume\当前投递\日巡检_YYYY-MM-DD.md`（求职侧目录，不入本工作流仓）
```

### 1.3 边界与约束

- 入库必须用户给截图；投递必须真人操作；补项目走生产线卡点，日流程不跳过任何 👤 卡点。
- 分批原则沿用入口文档：不一次性把所有待生成 JD 处理完，防上下文膨胀（与 P3 过载信号联动）。
- **本轮先作为编排口令落地**，跑 2–3 天看卡点和摩擦点，再决定是否固化成规则/脚本；不新增 R 规则。

### 1.4 落点（确认执行后）

| 改动 | 位置 |
|---|---|
| 日巡检口令 + 六步顺序 + 小结格式 | `D:\lg\_求职流水线入口.md` 触发词总表 + 新增「每日流程」小节 |
| 本仓侧无需改流程；仅在主控唤起口令表补一条「今日求职 → 求职侧日巡检」指针 | `WORKFLOW_工作流主控.md` 唤起口令段（指针级，不复制正文） |

- **设计模式（R24）**：`普通` / `精修` —— 决定是否走精修专属动作。

两套机制触发条件正交：

- **G9 门面页方向稿**：触发看**项目类型**（仅 landing/portfolio 或看板标注含门面页）；step2 定稿后、5B 动工前出方向稿 + 1~2 张方向稿，👤 用户确认后 5B 才动工。

### 2.2 问题定性：缺一条串行主干，两套分支交叉插入

用户判断准确：现状不是「一步接一步的一条龙」，而是 G9（按项目类型）和 R24（按设计模式）两套分支在 step02、step05B、step06、step09 里反复插入、各自描述，形成多条并行小流程。调整目标是：**前端质量流程收敛成一条串行主干，分叉只在固定决策点出现一次；开关在 step01 问一次落看板，下游只读看板取值，不再中途重新判断。** 真正保留的并行只有 5A∥5B 开发并行，前端质量链路本身全部串行。

### 2.3 调整后：一条龙串行主干（建议作为唯一事实源）

```
step01 定开关（只问一次，写入看板：项目类型 / 设计模式 / demo 视频）
   │  未回复按默认：普通 / AI 归类 / 不录，标「用户未确认」
   ▼
step02 架构定稿
   ├─ 决策点① 读看板「项目类型」：landing/portfolio → 出 G9 门面页方向稿
   │            +1~2 张方向稿 → 👤 用户确认（未确认 5B 不动工）
   └─ 决策点② 读看板「设计模式」：精修 → 出「§ 前端设计方向」小节
              （候选方向/HEX/字体字重/圆角/间距/不做什么，禁废词）
   ▼
step05B 前端开发（动工前先复核看板开关：有无「用户未确认」标注、中途变更是否需回补）
   ├─ 有 G9 方向稿 → 按已确认方向稿实现
   ├─ 普通模式：功能跑通即止，不出三版发散、不出精修记录，warning 记 deferred
   └─ 精修模式（初版功能闭环后才进，顺序不能乱）：
        ① 三版首页发散 → ② 👤 用户挑 1 版 → ③ 主循环改 2 轮
        → ④ 空上下文视觉评审 ≥9（2 轮封顶，未达记 deferred）→ ⑤ 落《设计精修记录.md》
   ▼

   ├─ design_quality_check → 前端UI质量报告
   └─ design_taste_gate   → taste 审美检测报告（软观察）
   ▼
step09 最终验收（只读看板模式分叉一次）
   ├─ 普通：报告写「视觉验收不适用」，不硬做
   └─ 精修：三项核对 ① 对照设计方向 ② warning 清零 ③ 评审 ≥9 或已 deferred
```

### 3.4 兜底：不可换场景里上下文撑不住怎么办

## 四、P4 项目 2.0 跟进流程（构思 · 本轮不落地）

### 4.1 定位：第三条线路，与现有两条线区分

| 线路 | 适用对象 | 本质 | 前置专属步骤 | 中段/尾部复用 |
|---|---|---|---|---|
| 生产线（step00→11） | 从 0 到 1 新项目 | 新建 MVP，走全序列门禁 | step00 选题→0.5 设计书 | step1→11 全序列 |
| 翻新线（F0→F4） | 野生老项目 / 已交付但未达标的项目 | 体检返修、补门禁、修烂尾 | F0 迁入建档 / F1 逆向建档 / F2 九维度体检 | F3 返修强制复用生产线 5.5→6→6.5→7→7.5→8→8.5→9；F4 = step10→10.0→10.5→10.6→11 原样 |
| **迭代线（构思，I0→I3）** | **已交付闭环的项目，继续加增量能力** | 增量开发：新 JD 缺口补强 / 硬骨头升级 / 性能或 UI 改进 / 新想法；不推翻已验收架构 | **只需设计 I0 增量建档、I1 增量设计评审两个前置步骤** | I2 复用 5.5→6→6.5→7→7.5→8→8.5→9；I3 复用 step10→10.0→10.5→10.6→11 |

**确认用户判断**：翻新线正是「前几步不一样、后续步骤都是原步骤」——F0/F1/F2 专属建档体检，中段 F3 返修复用生产线全序列，尾部 F4 交付原样复用。迭代线照同一套路：**只设计前置差异段（I0/I1），中段验证与尾部交付直接复用生产线步骤**，仅在增量差异处加条款（不退化校验、changelog、简历增量补 bullet）。

**路由原则**：迭代中发现 v1 实现硬伤 → 转翻新线 F2 体检；增量过大（超出 MVP 边界、要推翻架构/重写已闭环模块）→ 拆成新生产线项目，不走迭代线。
