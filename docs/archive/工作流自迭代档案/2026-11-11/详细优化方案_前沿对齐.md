## 3. 详细设计

### G1 · 输入卡 Schema 校验 —— P0

**目标**：步骤交接卡开工前过机器校验，缺字段、引用失效、路径越界直接报红，不允许"解释执行"。

**现状**：执行约定 §四 有 YAML 格式约定，但无校验；卡由上一步自觉生成。

**改动落点**：

1. **新增 `workflow/input_card_schema.yaml`**：按步骤定义必填字段、枚举值、引用规则。
2. **新增 `scripts/input_card_check.py <step> <card.yaml>`**：
   - 参数：`<step>` 步骤编号；`<card.yaml>` 卡路径；`--project <目录>` 用于校验引用产物存在性。
   - 校验规则：必填字段非空；`sources` 列出的上游产物路径真实存在；所有路径落在项目目录内（越出目录即报红）；风险级别/项目类型等枚举值合法；端口为数字。
   - 退出码：`0` 全绿；`1` 报红（缺失/越界/失效引用/枚举非法，逐条列出）；`2` 脚本自身错误（按 R12 先怀疑脚本）。
3. **`workflow/steps.yaml`**：每步补 `input_card: <相对路径>` 字段，与现有 `artifacts` 同级。
4. **执行约定 §四** 补硬规则：本步开工先跑卡校验，报红回上一步补卡，卡不绿不动手；历史项目豁免（复用 10.0 门禁历史项目口径）。

**通用卡字段**（所有步骤）：

```yaml
step: "5A"
project: <项目名>
updated_at: "2026-11-11 14:30"
sources:            # 上游产物引用，必须存在于项目目录内
  - 02_架构设计/第二轮技术架构设计文档.md
  - 04_任务拆解与开发规范.md
```

**分步骤扩展字段**：

| 步骤 | 扩展字段 |
|---|---|
| 1 | `baseline_ref`, `scope_ref` |
| 2 | `baseline_ref`, `hardware_limit`, `ports` |
| 4 | `arch_ref`, `tasks[]`（task_id/desc/risk/criterion_ref）, `scope`, `limits` |
| 5A | `arch_ref`, `tasks[]`, `mock_policy`, `ports`, `scope`, `limits` |
| 5B | `arch_ref`, `tasks[]`, `mock_ref`, `ports`, `scope`, `limits` |
| 6 | `code_dirs[]`, `start_commands[]`, `probe_urls[]`, `p0_ref` |
| 7 | `ledger_ref`, `contract_ref` |
| 8 | `baseline_ref`, `ledger_ref`, `cases_ref` |
| 9 | `baseline_ref`, `ledger_ref`, `security_ref` |

**验收标准**：缺必填字段 → 退出码 1；引用不存在的产物 → 退出码 1；路径写到项目目录外 → 退出码 1；合法卡 → 退出码 0；`wf steps --check` 能校验 steps.yaml 的 `input_card` 字段与执行约定清单一致。

**风险回退**：schema 过严卡老项目 → 历史项目豁免；校验脚本误报按 R12 抽验复核。

### G3 · 失败响应四分类 + 振荡检测 —— P0

**目标**：失败不再笼统"回去修"，按类型分四种响应；限额重试必须问题数递减；反复撤销自己修复的振荡直接转人工。

**现状**：收敛判据只管 open P0/P1 单调不增 + 同根因 3 次无效回流；无响应分类、无振荡识别。

**改动落点**：

1. **执行约定 §二 失败循环加四分类表**：

| 响应类型 | 触发条件 | 动作 | 回流去向 |
|---|---|---|---|
| `stop` 停止 | diff 碰 CI/闸门配置；出现真实密钥；prompt 注入嫌疑 | 暂停、保留证据、告警用户，**不自动重试** | 交用户处置 |
| `retry` 限额重试 | 测试失败；闸门报新 bug/漏洞 | 结构化 findings 回执行方；封顶轮次；每轮 findings 必须递减；重跑全部闸门 | 执行方（5A/5B/对应步骤） |
| `human` 转人工 | 计划低置信；用例 flaky；同一发现 3 轮未消；diff 异常超大；第 2 次振荡 | 带闸门结果 + diff + 尝试历史交用户 | 卡点人工确认 |
| `transient` 瞬时退避 | 限流、超时、runner/环境临时失败 | 退避后从最近断点恢复（接 G10），不整段重跑 | 原步骤续跑 |

2. **`_问题台账.md` 轮次日志扩展字段**：`response_type`（stop/retry/human/transient）、`findings_count`（本轮问题数）；递减规则并入现有收敛判据。
3. **`scripts/log_failure.py` 扩展**：加 `--response-type` 枚举（默认 `retry`）；失败日志表加对应列；步骤白名单不变。
4. **振荡检测规则**：
   - 同一文件连续两轮改动互逆（改回上一轮内容），或同根因修复后 reopen 第二次 → 记振荡；
   - 第 1 次振荡记台账观察，第 2 次直接 `human`，不进限额重试。
5. **边界**：P2/P3 不套这套重流程；本项只规范 5.5/6/6.5/7/8/8.5/9 的修复循环。

**验收标准**：四类响应在台账/日志可区分；retry 轮次 findings 不递减 → 判违规转 human；振荡第 2 次 → 必须 human；stop 类不得出现自动重试记录。

**对应诊断**：D4、M1。

### G2 · 计划范围与限额字段 —— P1（依赖 G1）

**目标**：计划交接物写清改动边界与限额，越界改动在计划层就有尺可量。

**现状**：step4 任务表有风险级别列，无 files_in_scope/out_of_scope、无文件数/轮次/超时上限。

**改动落点**：

1. step4 输出与 5A/5B 输入卡补两个字段（并入 G1 schema 校验）：

```yaml
scope:
  files_in_scope: ["05_代码/backend/workflow/**", "05_代码/backend/controller/**"]
  out_of_scope: ["05_代码/frontend/**", "**/docker-compose.yml", "**/auth/**"]
limits:
  max_files: 12
  max_attempts: 3
  timeout_min: 20
```

2. `prompts/step04_任务拆解与开发规范.md` 输出要求加：每条 P0 链路标注归属文件范围；限额默认值由 step4 按项目规模给，step5 不得自行扩大范围。
3. 校验并入 `input_card_check.py`：`out_of_scope` 中的路径不得出现在 `files_in_scope`；`limits` 字段为正整数。

**验收标准**：卡内 scope 为空或自相矛盾 → 报红；实现 diff 命中 out_of_scope → 5.5 Review 记越界项。

**对应诊断**：D3、M2。

### G5 · 风险分级细化 + 审批绑定版本 —— P1

**目标**：在现有高/中/低三级上补"关键"档；人工审批绑定具体 commit，代码一改旧审批作废。

**现状**：#72 三级风险，高风险 5.5 后升级人工；审批未绑定 commit。

**改动落点**：

1. **step4 风险列枚举扩为 低 / 中 / 高 / 关键**。现有高风险清单保留，补"关键"判定：
   - 鉴权与权限、数据迁移/Schema 变更、并发·事务·幂等、外部 API 与密钥、部署与启动脚本、公共组件签名变更；
   - **工作流闸门 / 脚本 / 规则本身的修改**（agent 不得自行改门禁定义）。
2. **审批绑 commit**：关键项 5.5 后必须具名人工确认；Review 报告与看板填 `approved_commit: <SHA>`；后续新 commit 提交后该审批作废，需重审。

**目标**：中断后靠标记文件恢复，不靠猜看板；恢复不整段重跑；长脚本可重入。

**现状**：#64 方案存档；无断点标记；中断后靠看板旧状态反推（saas 项目积分耗尽事故）。

**改动落点**：

1. **断点标记目录**：项目根 `.checkpoint/`（不进 10.0 门禁产物清单，属运行时状态；`.gitignore` 排除）。
2. **新增 `scripts/checkpoint.py`**，三个子命令：

```
python scripts/checkpoint.py mark <项目目录> --step 6 --command "npm run dev" --pid 12345 --output-path "06_冒烟/冒烟记录.md"
python scripts/checkpoint.py done <项目目录> --step 6 --exit-code 0
python scripts/checkpoint.py status <项目目录>   # 读最新断点，输出恢复分支建议
```

   **`.checkpoint/<step>.json` schema**：

```json
{
  "step": "6",
  "command": "npm run dev",
  "pid": 12345,
  "started_at": "2026-11-11 14:30:00",
  "ended_at": null,
  "exit_code": null,
  "output_path": "06_冒烟/冒烟记录.md",
  "artifacts": ["06_冒烟/冒烟记录.md"]
}
```

3. **恢复决策树**（写入执行约定 §一新对话恢复清单，优先级在看板之前）：

| 断点状态 | 动作 |
|---|---|
| 产物已落盘 + `exit_code=0` | 该步已完成，跳过 |
| `pid` 仍存活 | 先探活，活着就等，不重启 |
| 进程死 + `exit_code≠0` | 只重跑这一步 |
| 无标记文件 | 从该步开始 |

   硬规则：禁止整段从头重跑；恢复第一步永远先 `env_preflight.py --smoke <已知 URL>` 探活，服务活着不重启。
4. **幂等规范**（写入 step4/5 开发规范）：长耗时脚本先查后写、唯一业务键、不依赖上次残留状态；重复执行不造出重复数据。
5. **与 R21 衔接**：换对话/中断恢复时，先读 `.checkpoint/` 再读看板恢复摘要。
6. **验证方式**：不等真实事故——下一个项目做一次模拟中断（手动 kill 后台进程或中断会话），按决策树走一遍恢复，结论记入 step11。

**边界（本期不做）**：自动崩溃重启、跨机器恢复、断点状态同步到云端。

**验收标准**：中断后 `checkpoint.py status` 能给出明确分支；恢复动作与决策树一致；模拟中断演练记录落盘；重跑脚本无重复数据。

**对应诊断**：D1、#64。

## 4. 候选独立项目：研发效能度量看板（消费层）

### 4.1 能不能当作品集项目：结论

**能做，但定位要清醒**：它是"内部研发效能工具"，不是大数据平台。立身点是**指标体系设计 + 产物解析工程**，面试时不能吹"海量数据分析"。是否立项必须走 step00 选题流程（JD 对账、缺口分析、硬件约束、硬骨头判定），不直接开工。

### 4.2 定位

把 G7 沉淀的各项目度量台账、台账、失败日志、门禁输出，跨项目聚合后可视化：哪步最容易卡、返工率、缺陷逃逸路径、质量趋势。

### 4.3 技术骨架（贴合本机 RTX 2050 4GB / 16GB 内存）

| 层 | 选型建议 | 说明 |
|---|---|---|
| 采集 | Python 脚本解析 markdown / json 产物 → 结构化记录 | 容错解析状态机；数据落 SQLite 或 JSON 文件仓，不上重数据库 |
| 后端 | FastAPI（Python 方向）或 Spring Boot（Java 方向） | 出聚合查询接口 |
| 前端 | ECharts 可视化 dashboard | 步骤耗时分布、返工轮次、闸门报红 TOP、根因分布、跨项目对比 |

### 4.4 指标体系（可讲的设计点）

- 前置时间：step1 → step10 时长；
- 返工率：失败日志条数 / 项目步骤数；
- 缺陷逃逸：问题在哪步埋下、在哪步才发现（按根因路由表统计）；
- 门禁一次通过率；P0/P1 修复轮次；
- 跨项目趋势对比。

### 4.5 硬骨头模块（满足 step00 反粗制滥造规则）

1. markdown 产物容错解析 + 结构化抽取（状态词识别、表格列对齐、坏行跳过）；
2. 跨项目指标口径统一与趋势对比；
3. 数据一致性对账：看板 vs 台账 vs 失败日志三方互相校验。

### 4.6 诚实边界（简历与面试口径）

- 数据量为十几个内部项目，演示需补一套模拟历史数据集讲趋势；
- 业务复杂度有限，技术亮点在解析工程与指标设计，不在高并发/大数据；
- 与现有工作流仓的关系：消费其产物，不反过来耦合工作流规则。

### 4.7 立项条件

进 `projects/_队列/` 前过 step00：目标岗位 JD 是否含"效能平台 / 数据看板 / 质量度量 / 可观测"类关键词；与已有项目技术栈 + 业务领域不双撞车（反粗制滥造规则 2/6）；工作量 ≤ 15 人天，砍到 MVP。
