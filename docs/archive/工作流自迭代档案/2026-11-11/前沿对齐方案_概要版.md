## 一、背景与判断

2026 年高质量 AI 交付的共识结构：**外层确定性工作流（闸门、契约、独立验证、风险分级审批），内层受限的 agent 判断**——agent 决定尝试什么，流水线决定什么能放行。单点模型能力差距不大，拉开质量的是流程：spec 先行、计划先于编码、验证独立于实现、失败循环有硬边界、知识跨会话沉淀。

对照本仓现状：上下文治理（D1）、独立 Review（#71）、风险分级雏形（#72）、台账收敛判据、输入卡协议已经落地；本方案只补**前沿有、现状未覆盖或半覆盖**的缺口，不重复建设。

## 三、改进项（按优先级）

### G1 · 输入卡 Typed Schema 校验 —— P0

**现状差距**：执行约定 §四 规定了输入卡 YAML 格式，但没有机器校验。卡缺字段、引用的上游产物不存在、路径越出项目目录、枚举值写错，目前靠 Agent 自觉填、自觉读；跨步骤漂移（M2 的根因之一）在开工前拦不住。

**前沿做法**：typed handoff——交接物带 schema，接收方开工前先 validate，非法直接拒绝，不做"解释执行"；阶段状态存在模型上下文之外，传文件引用而不是贴正文（Sonar: typed handoffs）。

**改动落点**：
1. 新增 `workflow/input_card_schema.yaml`：按步骤定义必填字段（step / project / 任务引用 / 端口 / 限额 / 验收标准引用），路径必须落在项目目录内，枚举值合法。
2. 新增 `scripts/input_card_check.py <step> <card.yaml>`：必填字段、引用产物存在性、路径不越界、枚举合法；报红按 `fallback` 回上一步补卡，**卡校验不绿不得动手开发**。
3. 执行约定 §四 补一条硬规则：开工先跑卡校验；`workflow/steps.yaml` 各 step 补 `input_card` 字段指向卡路径。
4. 历史项目豁免（复用 10.0 门禁的历史项目口径，不追溯）。

**对应诊断**：D1（结构化状态）、M2（契约一致性）。
**风险与回退**：schema 过严会卡住老项目 → 历史项目走豁免；校验脚本自身按 R12 对待（先怀疑脚本，抽 1–2 条复核）。

### G3 · 失败响应四分类 + 振荡检测 —— P0

**现状差距**：现有收敛判据只管"问题数单调不增 + 同根因 3 次无效回流"，但失败响应没有分类。触红线的问题（出现密钥、动 CI/闸门配置、注入嫌疑）应该**停止留证、不重试**；flaky / 低置信 / 超大 diff 应该**转人工**；瞬时错误（超时/限流/runner 失败）应该**退避后从检查点恢复**；普通缺陷才进限额重试。另外缺少振荡检测——agent 反复撤销自己的修复、同一问题修了又 reopen。

**前沿做法**：流水线预先定义四类失败响应——stop / retry-with-limits / route-to-human / transient-backoff；限额重试必须 findings 逐轮递减；循环有最大轮次、时间与 token 预算；检测振荡（Sonar: bounded repair loops, failure routing）。

**改动落点**：
1. 执行约定 §二 失败循环加**四分类表**：触发条件 → 动作 → 台账记录字段。
   | 响应类型 | 触发条件 | 动作 |
   |---|---|---|
   | stop（停止） | diff 碰 CI/闸门配置、出现密钥、prompt 注入嫌疑 | 暂停、保留证据、告警用户，**不自动重试** |
   | retry（限额重试） | 测试失败、闸门报新 bug/漏洞 | 结构化 findings 回执行方，封顶轮次，每轮 findings 必须递减，重跑全部闸门 |
   | human（转人工） | 计划低置信、用例 flaky、同一发现 3 轮未消、diff 异常超大 | 带闸门结果 + diff + 尝试历史交用户 |
   | transient（瞬时退避） | 限流、超时、runner 失败 | 退避后从最近检查点恢复，不整段重跑 |
2. `_问题台账.md` 轮次日志加 `response_type` 与 `findings_count` 字段；递减规则并入现有收敛判据。
3. **振荡检测**：同一文件连续两轮改回上一轮内容，或同根因修复后 reopen，记振荡；第 2 次振荡直接转人工，不进限额重试。
4. `log_failure.py` 加 `response_type` 枚举（复用现有脚本，不新建）。

**对应诊断**：D4（问题后置 / 循环失控）、M1（环境坑反复试错）。
**边界**：P2/P3 不套这套重流程；本项只规范 5.5/6/7/8/8.5/9 的修复循环。

### G2 · 计划交接物补范围与限额字段 —— P1（依赖 G1）

**现状差距**：step4 任务表有风险级别列，但没有 `files_in_scope / out_of_scope` 清单，也没有改动文件数上限、尝试轮次、时间预算；执行 Agent 越界改文件时，计划层面没有可核对的尺。

**前沿做法**：计划交接物是带 schema 的计划对象：改动范围、明确排除项、验收标准、限额（最大文件数、最大尝试次数、超时）；越界计划在计划闸就被拒（Sonar: plan check）。

**改动落点**：
1. step4 输出与 5A/5B 输入卡补 `scope: {files_in_scope, out_of_scope}`、`limits: {max_files, max_attempts, timeout_min}`。
2. 字段校验并入 G1 的 `input_card_check.py`，不另起脚本。

**对应诊断**：D3（流水线模型为 AI 设计）、M2。

### G4 · 安全轻量前置（叠加，不替代 8.5） —— P1

**现状差距**：安全检查集中在 step8.5 后置；5A/5B 宣布完成前没有任何安全快扫。硬编码密钥、明显 SQL 拼接、`exec/shell=True` 这类问题要走到 8.5 才暴露，修复成本高。

**前沿做法**：纵深左移——生成/提交时实时反馈一层，CI/深度闸后置一层；AI 代码与人代码同一标准（AWS/Sonar 安全分层；Semgrep/Snyk/DryRun 类 MCP 实时反馈）。

**改动落点**：
1. 5A/5B 完成定义加前置快扫：复用 `security_scan_secrets.py --sast`（#26 已有规则与能力），宣布完成前跑一次；命中硬编码密钥 / SQL 拼接 / 命令执行直接回修，不带进 5.5。
2. step8.5 保持深度闸不变：依赖 CVE、配置完整性、接口级渗透、豁免清单人工复审。
3. 新引入第三方包必须过 `dependency_checker.py --solve`（已有能力，不新增脚本），在 step2/4 拦下"包查得到但装不上"。

**对应诊断**：D4、M1、E2（信任等级对等）。
**风险与回退**：前置快扫误报 → 复用 R12 先怀疑脚本 + 豁免清单（#54 口径）；前置只拦硬伤，不做深度判定。

### G5 · 风险分级细化 + 审批绑定版本 —— P1

**现状差距**：#72 现有 高/中/低 三级，高风险在 5.5 后升级人工；但审批没有绑定具体 commit/产物版本——确认后又改了代码，旧审批仍然有效。也缺一档"关键动作"：agent 永不自行执行、必须具名人工的动作类型。

**前沿做法**：四级风险（低/中/高/关键）；审批绑定特定 commit，新提交作废重审；生产部署、密钥、改闸门/流水线配置属关键动作，agent 永不执行（Sonar: risk-tiered approval）。

**改动落点**：
1. step4 风险列枚举扩为 **低 / 中 / 高 / 关键**；在现有高风险清单上补"关键"判定：鉴权权限、数据迁移、并发事务、外部 API 与密钥、部署脚本、公共组件签名，以及**工作流闸门 / 脚本 / 规则本身的修改**。
2. 关键项：5.5 后必须具名人工确认；确认记录绑定 commit SHA（Review 报告/看板填 `approved_commit`），后续新 commit 审批作废、重审。
3. 映射本流水线的关键动作：step10.5 push public 仓（已有 prepush 硬闸）、step11 改工作流文件（已有 👤 step11）；**agent 不得自行修改门禁脚本与闸门定义**。

**对应诊断**：D2、R6/R20。

### G6 · 测试有效性审查 —— P1

**现状差距**：5.5 三层评审（需求正确性 / 系统一致性 / 回归）审代码逻辑，但不审"测试有没有测对东西"——mock 错抽象、断言只断状态码的假绿仍可能漏过（#74 已补字段值断言，但审查口径未写进 reviewer 职责）。

**前沿做法**：验证 ≠ 评审；要核对断言打的是真实业务字段/状态，而不是 mock 返回值或 200 状态码（Blink: verify the tests are testing the right thing）。

**改动落点**：
1. 5.5 reviewer 检查项加一条：抽 P0 用例，核对断言针对真实业务字段/状态，而非仅 mock 返回值或状态码；step8 自测同口径。
2. 假绿用例记台账，按"测试遗漏"路由回 step8。

**对应诊断**：D2、M3（脚本/测试可信度）。

### G7 · 跨步骤轻量度量台账 —— P2

**现状差距**：失败日志、轮次日志、规则使用统计（`rule_usage_stats.py`）分散；没有每步耗时、轮次、闸门报红次数、评审评分的聚合视图；#61 成本议题当时暂缓，理由是不造大系统。

**前沿做法**：流水线埋点采集失败率、成本、延迟、产出质量，用数据决定放权节奏（Sonar: instrument the pipeline）。

**改动落点**：
1. 新增 `projects/<名>/_运行度量.md`（轻量台账，不建平台）：每步开始/结束时间、轮次、闸门报红次数、失败日志条数、Review/视觉评审评分；数据从看板/台账/`log_failure.py` 提取，不增加采集负担。
2. step10 复盘 + step11 体检跨项目聚合：哪步耗时最长、哪类闸门反复报红、哪类问题回流最多，反哺 backlog。
3. token/费用如平台可导出则记，不可得不编（底线规则 3：不虚构运行结果）。

**对应诊断**：D5（规则治理）、#61。

### G8 · Spec 验收条目与映射表对齐 —— P2（半覆盖补全）

**现状差距**：step1 基线指标已有数字 + 验证归属 + 排除范围，但验收条目没有逐条挂到映射表任务；step9 对照清单可能漏掉基线项。

**前沿做法**：spec 的 success criteria 是后续每个阶段的核对尺，逐条可追溯（Blink: success criteria；RTADev 需求-文件映射）。

**改动落点**：
1. step1 基线每条量化指标给 `criterion_id`；step4 建映射表时逐条挂接。
2. 10.0 门禁核对基线 criterion 100% 有映射行（扩展 `design_impl_check.py`，不新建门禁）。

**对应诊断**：D4、R8（设计↔实施映射）。

### G9 · 门面页视觉方向稿前置 —— P2（✅ 2026-11-11 用户拍板启用）

**现状差距**：R24 三版发散在功能跑通之后；step2 只落到设计方向小节（#85 废词黑名单）。门面页方向若动工前没定，写完一版再推翻成本高。

**前沿做法**：两条成熟路径——code-first（需求/草图 → 可运行原型迭代）；design-to-code（高保真稿/Figma → 代码还原，Code Connect 双向绑定）。门面页先定方向，业务页直接代码（v0/Figma 实践）。

**改动落点（已启用分支）**：step2 定稿后、5B 动工前，对首页/门面页先出 1 版高保真方向稿（静态图或可玩原型），👤 确认方向后 5B 按稿实现；现有"功能后三版发散"保留为兜底。**范围只限门面页（首页/落地页），后台业务页不走前置稿。**

**风险与控制**：多一轮评审；静态稿到代码有失真，实现时留弹性。首个带前端的项目试点后再评估是否扩大范围。

**对应诊断**：M6（UI/视觉域）。

### G11 · 全局 API Key 仓库约定（backlog #79，✅ 2026-11-11 用户拍板采纳） —— P2

**现状**：`D:\lg\project\resources\api-keys.env` 已存在（在所有项目目录之外，不被任何 git 追踪），已含阿里云百炼 key 与使用说明；缺的是流程约定——新项目需要外部 LLM/API 时主动从目录取用，不再问用户要。

**改动落点**：
1. step00/step2 设计阶段识别到需要外部 API（LLM / embedding / 短信等）时，直接从全局 key 仓库复制对应配置到项目 `.env`；项目目录内不另存 key 原件。
2. 全局仓库文件留在项目目录之外，不进任何 git；项目 `.env` 走 `.secretignore` / `.gitignore`；`prepush_check.py` 已有 git 历史密钥扫描兜底。
3. 新增 key 时在仓库文件登记用途与来源；发现泄露（如误 push）立即去对应控制台吊销。
4. 本仓当前无外部 key 实证，约定随第一个带外部 API 的项目试点验证。

**对应诊断**：M4（基础设施债）、G4 安全前置配套。

### G10 · 断点标记 + 恢复决策树 —— P1（✅ 2026-11-11 用户拍板：未雨绸缪，现在落地轻量骨架）

**现状差距**：#64 断点标记 + 恢复决策树方案已存档；开发过程中没有 checkpoint 回滚点约定，中断后只能靠看板旧状态反推。

**前沿做法**：每步留断点标记，中断后按决策树恢复、禁止整段重跑；长耗时脚本幂等可重入（Blink: checkpoint commits；Sonar: idempotency）。

**改动落点**：现在落地轻量骨架——`.checkpoint/<step>.json` 标记 + 回写脚本、恢复决策树入执行约定、幂等规范入开发规范；用一次模拟中断验证恢复树，不等真实事故。不做自动崩溃重启与跨机恢复。详细设计见 `详细优化方案_前沿对齐.md` G10。

**对应诊断**：D1、#64。

## 五、实施路线
