# step00 · JD 驱动的项目选题模块设计

> 本模块插在现有 10 步流程**之前**，输入是若干份招聘 JD，输出是若干个"符合 JD 技能点、不与作品集重复、有技术深度、工作量可控"的项目设计书。
> 设计书落盘后，无缝接入现有 step01（项目基线定义），不重复做需求分析。

---

## 0. 模块定位

**解决的问题**：直接说"启动新项目"时，项目方向是拍脑袋的，容易出现三种死法：
1. 跟作品集里已有项目撞车（已经做了 3 个 RAG，又做第 4 个）
2. JD 要的技能点没真正覆盖（JD 要 Kafka，项目里只是加了个 `@Async`）
3. 项目粗制滥造（CRUD 换皮、技术栈堆砌、工作量估错烂尾、面试讲不出深度）

**模块产物**：
- `00_JD技能点清单.md`：结构化拆解后的 JD 技能点
- `00_作品集画像库.json`（+ `.md` 人类可读版）：已有项目覆盖了哪些技能点
- `00_选题矩阵.md`：候选项目 × 技能点覆盖对账
- 每个选中项目一份 `00_项目设计书.md`（直接作为 step01 的输入）

## 1. 流程定义（严格按序）

```
JD 原文（图片/PDF/文本均可）
 → 0.1 JD 结构化拆解
 → 0.2 扫描作品集，建能力画像库
 → 0.3 技能点 × 现有覆盖度对账，找缺口
 → 0.4 生成 N 个候选项目选题矩阵（N ≤ 5）
 → 👤 卡点 1：选题拍板（选哪几个、砍哪几个、业务场景是否认可）
 → 0.5 每个选中项目出一页纸设计书
 → 🤖 WORKFLOW_卡点协议.md「机器闸门」（step00 设计书闸门）：依赖真实性 + 本机环境预检 + 技能点覆盖率 100% + 工作量拆解 + MVP 最小可用场景，全绿自动过、报红才叫人
 → 落盘 00_项目设计书.md + 00_JD对账表.md
 → 设计书入 projects/_队列/<项目名>/，等「开工：<项目名>」时再复制模板骨架进 step01
```

### 1.1 step 0.1 · JD 结构化拆解

把每份 JD 拆成四类标签，不允许笼统描述：

| 标签类型 | 示例 | 粒度要求 |
|---|---|---|
| 硬技术栈 | Java、Spring Cloud、Kafka、Redis、MySQL、MyBatis、Pytest | 具体到组件名，不能写"熟悉微服务" |
| 架构/中间件能力 | 高并发、高可用、分布式事务、缓存一致性、消息队列 | 必须是可考核的机制 |
| 业务领域 | SaaS、电商、企业内部系统、AI Agent、推荐 | 具体场景 |
| 工程规范 | Git Flow、Code Review、接口规范、技术文档、CI | 行为项 |

**输出**：`00_JD技能点清单.md`，每份 JD 一个小节，标签去重后合并成总表。

### 1.2 step 0.2 · 作品集画像扫描

脚本扫描 `D:\lg\project\` 下每个项目目录，提取：
- 项目名、业务领域（读 README 第一句）
- 用到的技术栈（扫 `pom.xml`/`build.gradle`/`requirements.txt`/`package.json`）
- 中间件使用情况（扫 docker-compose.yml、application.yml）
- 已覆盖的技能点（人工 + AI 兜底打标）

**输出**：`00_作品集画像库.json`，每个项目一条记录。长期沉淀，每次 step00 跑完把新项目回写进去。

### 1.3 step 0.3 · 缺口分析

把 JD 技能点清单 ∩ 作品集画像库做差集，找出：
- **JD 高频要求但作品集完全没覆盖的** → 必须由新项目承担
- **JD 要求但作品集已有浅层覆盖的** → 新项目要做深（不能再浅尝辄止）
- **JD 提到但个人项目不可能实现的**（如"全球化部署""存算分离""K8s 集群""大模型微调"）→ **主动标注砍掉**，不硬塞。面试时诚实说"了解原理但未在生产实践"，比造假强。

### 1.4 step 0.4 · 候选选题矩阵

N 个候选项目（建议 2-3 个，最多 5 个），每个项目必须打标签：
- 覆盖哪些缺口技能点
- 业务场景（一句话，小而真，反"XX 电商平台"）
- 技术栈组合
- 1-2 个硬骨头模块（面试能讲 10 分钟的技术难点）
- 工作量预估（**预估步骤轮次 + 卡点次数 + AI 协作系数**，不再写人天——AI 全程协作下人天口径已失真，见 2026-10-30 实测回填）
- 与已有项目的差异化说明（为什么不算撞车）

### 1.5 step 0.5 · 一页纸项目设计书

每个选中项目一份，结构固定：
1. 一句话定位
2. 业务场景（真实小痛点，3-5 行）
3. 技术架构（含服务拆分图，文字描述即可）
4. 硬骨头模块 1、2（每个讲清楚问题是什么、方案是什么、trade-off）
5. JD 技能点对账表（脚本校验覆盖率；表头必须含 **`step10 落地验证`** 列，值为「真实落地 / 降级 / 纸面」，step10 复盘时回填）
6. 工作量拆解（**预估步骤轮次 × 模块 + 卡点次数 + AI 协作系数**；禁止再写人天）
7. 面试三问（为什么用 A 不用 B / 最难的问题 / 再做一次怎么改）
8. 主动砍掉的东西（JD 哪些词不实现、为什么）
9. 风险点（硬件约束、技术栈不熟点）

## 2. 反粗制滥造的 6 道闸

每道闸都有机器校验或明确判据，不靠 AI 自检。

| 闸 | 名称 | 判据 | 不通过的处理 |
|---|---|---|---|
| 1 | JD 技能点覆盖率 | 脚本扫设计书，JD 高频技能点覆盖率 < 100% | 补设计，或明确标注"本项目不覆盖，由项目 N 覆盖" |
| 2 | 现有项目硬去重 | "技术栈组合 + 业务领域"两个维度同时撞车 | 改业务领域或技术栈，否则毙掉 |
| 3 | 反 CRUD 换皮 | 每个项目至少 1-2 个硬骨头模块，写不出"自己实现了 XX 机制"或"解决了 XX 一致性/性能问题" | 打回重设计 |
| 4 | 面试三问 | AI 必须能答出三个问题，答不上来就是设计失败 | 打回 |
| 5 | 工作量预算 | 预估步骤轮次/卡点次数明显超出单项目承受范围 → 强制砍到 MVP（不再用「人天」当判据） | 砍范围，高级特性列为"可选加分项" |
| 6 | 项目间差异化 | N 个项目两两对比，技术栈/业务领域/硬骨头三个维度不能有两个雷同 | 合并或砍一个 |

> **实测回填（2026-10-28，saas-workflow-agent step10 复盘）**
> - 15 人天预算里必须显式预留**依赖/环境集成 3~5 人天**：本项目第 6 步吞掉 22/32 条失败、35/45 个修复轮次，其中 CrewAI 相关 9 条；集成成本远超设计书默认预期。
> - 设计书模板必须包含 **§6 工作量拆解（人天×模块）、§7 硬骨头、§8 主动砍掉项**：本项目设计书缺这 3 节，导致 step10 复盘的工作量/硬骨头两项只能降级为定性分析。
> - 选型时默认排除「只引 BOM 不落地」的框架（如 Spring Cloud Alibaba）与「容器在、功能无」的组件（如 Qdrant RAG），要么写实现，要么明确删除。
>
> **实测回填（2026-10-30，llm-eval-observability step10 复盘）**
> - 设计书缺 §6/§7/§8 的问题**再次出现**（本项目设计书仍只有 6 节、无工作量拆解/硬骨头/砍词）——纯文档回填无约束力，必须改为机器闸门（skills_coverage_checker 或 step00 闸门加必备节校验，见改进建议 #55）。
> - 「人天」口径在 AI 全程协作下彻底失真：基线预算 ≤12 人天，实际同日完成全流程（用户卡点 4 次约半小时）。后续设计书 §6 建议改记「预估步骤轮次 + 卡点次数 + AI 协作系数」，否则工作量偏差项永远无法定量复盘。
> - JD 对账表标「✅ 覆盖」≠ 实际落地：本项目 Qdrant/RabbitMQ 在 step1 被降级砍掉但对账表仍标 ✅，面试按原表讲会穿帮。对账表须加「step10 落地验证」列（改进建议 #57）。

## 3. 硬件约束（写死在规则里）

用户本机：RTX 2050 4GB 显存、16GB 内存。

**允许**：
- Docker Compose 起 3-5 个服务（MySQL、Redis、Kafka、Nacos、后端服务 × 3）
- 调远程大模型 API（DeepSeek/通义/OpenAI 兼容接口）
- 本地跑 Embedding 小模型（bge-small 级别，CPU 可跑）

**禁止**（写进 step00 评审规则）：
- 本地跑 7B 以上模型微调/推理
- K8s 集群、多节点分布式部署
- 需要 GPU 训练的计算机视觉/多模态项目
- 超过 5 个服务的微服务拆分（Docker Compose 起不动）

## 5. 脚本需求清单

### 5.1 `scripts/portfolio_scanner.py` · 作品集画像扫描器

**输入**：`D:\lg\project\` 根目录
**输出**：`00_作品集画像库.json`

**逻辑**：
1. 遍历一级子目录（跳过 `.` 开头、`archive`、`工作流测试`）
2. 每个项目目录里：
   - 读 `README.md` 前 30 行 → 业务领域
   - 找 `pom.xml` → 提取 Java 依赖
   - 找 `build.gradle` → Gradle 依赖
   - 找 `requirements.txt` / `pyproject.toml` → Python 依赖
   - 找 `package.json` → 前端依赖
   - 找 `docker-compose.yml` → 中间件列表
   - 找 `application*.yml` / `application*.properties` → 中间件连接配置
3. 依赖关键词 → 技能点映射表（写死一个 dict）：
   ```python
   SKILL_MAP = {
     "spring-cloud-starter-gateway": "Spring Cloud Gateway",
     "spring-cloud-starter-alibaba-nacos": "Nacos",
     "kafka-clients" / "spring-kafka": "Kafka",
     "spring-boot-starter-data-redis" / "lettuce": "Redis",
     "mybatis-plus-boot-starter": "MyBatis-Plus",
     "qdrant-client": "Qdrant 向量库",
     "langchain": "LangChain",
     ...
   }
   ```
4. 输出 JSON 落盘，已存在则合并更新（不删除人工补充的打标）

**自检计数**：扫描了多少个项目目录、识别出多少个技能点，打印出来。

### 5.2 `scripts/skills_coverage_checker.py` · JD 技能点对账器

**输入**：
- `00_JD技能点清单.md`（或 JSON）
- `00_项目设计书.md`
- `00_作品集画像库.json`

**输出**：对账表 + 覆盖率百分比

**逻辑**：
1. 解析 JD 技能点清单里的 `hard_stack` 和 `architecture_skills`
2. 在设计书里关键词匹配（技术栈名、中间件名）
3. 对每个技能点标注：✅ 已覆盖 / ⚠️ 浅覆盖 / ❌ 未覆盖
4. 输出覆盖率：高频技能点（must_have 里的）覆盖率必须 100%，nice_to_have 允许 < 100% 但要说明由哪个项目覆盖
5. 输出撞车检测：新项目的"技术栈 + 业务领域"组合是否与画像库里已有项目双撞

**自检计数**：JD 共 X 个技能点，匹配上 Y 个，覆盖率 Z%；撞车检测 N 对。

## 6. 与 step01 的接缝

step00 结束后，`00_项目设计书.md` 直接写入新项目目录的 `00_原始项目描述.md`（**不要让 step01 重新做需求分析**）。

同时把 `00_JD对账表.md` 放在项目根目录，**step03 架构评审时必须回头核对**：
- 基线每个量化指标在架构上有对应机制（现有规则）
- **JD 对账表里每个高频技能点在架构上有真实落地模块**（新增）

架构评审时如果发现"JD 要 Kafka 但架构里只是个摆设"，打回 step02 重设计。

## 7. 卡点与机器闸门

| 类型 | 时机 | 执行方式 |
|---|---|---|
| 👤 卡点 1 | 选题矩阵（0.4）出来后 | 用户花 2 分钟看候选项目方向，确认业务场景是否感兴趣、优先级怎么排；Agent 不得替用户拍板 |
| 🤖 WORKFLOW_卡点协议.md「机器闸门」（原人工确认，2026-10-30 起降级） | 一页纸设计书（0.5）出来后 | Agent 跑 `dependency_checker.py`（依赖真实性）+ `env_preflight.py`（本机工具/端口/内存）+ 技能点覆盖率脚本（must_have 100% + 设计书必备节），并核对工作量拆解与「MVP 最小可用场景」；全绿直接进 step01，不回用户；报红才列出报红项 + 建议改法等用户确认 |

> 说明：本模块只剩 1 处人工卡点（卡点 1）。0.5 的「详细设计确认」不再是卡点——R20 要求机器能判的就不打扰用户，报红才叫人。
