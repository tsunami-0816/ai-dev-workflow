# 原始项目描述 · ecom-scrape-rpa-dashboard

# 项目设计书 · ecom-scrape-rpa-dashboard（电商多平台采集 + 反爬 + RPA + Excel 报表 + 看板）

> 目的：补 G1 缺口——证明「电商平台（天猫/京东/拼多多/抖音）多源采集、平台取数与反爬应对、数据清洗校验、RPA 流程化执行、Excel 报表导出、SQL 取数、BI 看板」这一整条数据生产线能力。
> 覆盖 JD：乐福思健康产业（杰士邦母公司）· 电商爬虫工程师 J10888（主，S1-a 停投中）；杭州索骥数据 · 初级Java开发工程师（加分项「数据抓取相关开发经验」）。
> 与已有项目的关系：#20 dev-metrics-dashboard 是「研发效能看板」，数据源是本地项目产物，**不含外网采集、不含反爬、不含 RPA、不含 Excel 导出**；#20 的 FastAPI+ECharts 只复用骨架与图表思路。本项目增量 = **多站点采集适配器 + 反爬策略 + RPA 流程引擎 + Excel 公式/透视导出**。

## 1. 一句话定位

一个「电商竞品数据生产线」：定时从京东/天猫/拼多多/抖音采集指定品类商品的价格与销量 → 过反爬与清洗校验 → 落 MySQL → 用一份可选流程 DSL 驱动的浏览器 RPA 补采需要登录态的页面 → 每日自动导出多 sheet 的 Excel 日报（含公式、透视、条件格式、图表）→ 并在 Web 看板上看价格走势与采集健康度。

## 2. 业务场景（MVP 最小可用场景，必须能做完）

以「某品牌（避孕套/润滑剂品类）在 3 个平台的价格与销量监控」为业务壳：

1. 配置一份 `targets.yaml`：品类关键词、目标商品链接或 SKU 列表、平台、采集频率。
2. 每天 02:00 定时触发：京东列表页 + 详情页采集；天猫用导入的 Cookie 走详情页；拼多多走移动端页面；抖音走公开内容页（不碰私域）。
3. 采集落 `raw_page`（原始 HTML/JSON 快照，便于复盘字段变更）；解析后落 `product` + `price_snapshot`。
4. 清洗校验：价格/销量字符串转数值、缺失值策略、价格突变 >30% 标异常、同 SKU 多来源合并去重；生成 `clean_report`。
5. 需要登录态或复杂翻页的页面，用 `flows/jd_price_scan.yaml` 的 RPA 流程跑（登录 → 搜索 → 翻页 → 抽取 → 截图留证）。
6. 08:00 生成 Excel 日报：明细 / 清洗后明细 / 透视汇总 / 异常清单 / 趋势图，共 5 个 sheet。
7. Web 看板看 4 个视图：价格走势、平台对比、TOP 变动、采集健康度（成功率/封禁率/耗时）。

**做完这件事，项目就算成了。** 不做支付数据、不做私信/评论抓取、不做验证码破解、不做 App 端逆向、不做分布式集群调度。

合规边界（写进 README 与验收材料）：只采集**公开可见**的商品信息（标题、价格、销量标签、评价数），遵守目标站点 `robots.txt` 与用户协议，不绕过登录墙与付费墙，不破解加密接口，不存储任何个人隐私信息；Cookie/账号仅用本地测试账号，用完即清。

## 3. 技术架构

| 层 | 选型 | 说明 |
|---|---|---|
| 采集调度 | **Python 3.11 + APScheduler** | 每日 02:00 采集、08:00 出报表；任务串并行配置化 |
| HTTP 采集 | **httpx（异步）+ requests** | 异步并发 + 连接池；同步路径用于简单页面 |
| 浏览器采集 | **Playwright（Chromium）** | 需要登录态/懒加载/翻页的页面；同时作为 RPA 执行内核 |
| 反爬层 | 自研 `antibot/`（限速令牌桶 + UA 池 + Cookie 池 + 代理池 + 指数退避 + 断点续采） | 不引入重型框架，策略可配置、可观测 |
| 解析 | **parsel / lxml + 正则 + JSON 路径** | 每站点一个 adapter，字段映射集中管理 |
| 清洗校验 | **pandas** | 标准化、缺失策略、异常检测、多源比对、去重 |
| 存储 | **MySQL 8** | 原始快照 + 结构化表 + 任务表；按日期分区 |
| 报表 | **openpyxl** | 多 sheet、写入公式、条件格式、冻结窗格、嵌入图表 |
| 接口 | **FastAPI** | 5 个只读接口给看板（走势/对比/变动/健康度/任务） |
| 看板 | **Vue3 + ECharts** | 4 个视图；对应 FineBI 的指标口径与图表配置写进文档 |
| 部署 | **Docker Compose**（MySQL + app + nginx） | 本地一键起；不依赖云 |
| 测试 | **pytest**（解析/清洗/去重/报表断言） | 解析层用固定 HTML 快照做回归 |

**明确不做**：Scrapy 全家桶（本项目的价值是策略与流程，不是框架）、分布式爬虫集群、验证码识别服务、App/小程序逆向、真实支付与订单数据、云函数。

## 4. 硬骨头模块（P0，只做这些）

### 模块 1：多平台数据采集引擎 + 反爬策略（1.3 人天）

- **站点适配器**：`adapters/jd.py`、`adapters/tmall.py`、`adapters/pdd.py`、`adapters/douyin.py`，统一 `fetch_list()` / `fetch_detail()` 接口，输出统一字段（platform / sku_id / title / price / sales_tag / shop / url / crawled_at）。
  - 京东：搜索列表页 + 详情页，价格在页面 JSON 片段里；
  - 天猫：详情页需登录态，走 Cookie 池；
  - 拼多多：移动端页面（窄屏 UA），列表走页面内嵌 JSON；
  - 抖音：公开内容页/榜单页，只取公开字段。
- **限速令牌桶**：按域名独立配额（如 1 req / 1.5s），并发上限按站点配置（京东 4、天猫 2、拼多多 2、抖音 1）。
- **UA 池 + 请求头模板**：每站点维护 10 条真实 UA，随机轮换；header 顺序与常见浏览器一致。
- **Cookie 池**：本地导入（手动登录后导出 JSON），按账号轮换；失效探测（返回登录页/302 → 标记失效并切换）。
- **代理池**：本地代理列表（可为空，走直连），失败 2 次切下一个，记录代理健康度。
- **指数退避重试**：`base=1s, factor=2, max=3`；429/503 单独更长冷却。
- **断点续采**：`task_run.cursor` 记录页偏移，重启从断点继续，不重复不跳过。
- **去重**：URL 指纹（sha1）+ `(platform, sku_id, date)` 唯一键，DB 层 unique index 兜底。
- **反爬观测**：`antibot_metrics` 表记每次请求的域名、状态码、耗时、是否触发风控页、是否走代理；看板出「封禁率 / 成功率 / P95 耗时」。

### 模块 2：RPA 流程引擎（1.0 人天）

- **流程 DSL（YAML）**：步骤类型 `goto / click / type / wait / extract / loop / screenshot / assert`，支持变量 `${keyword}`、选择器优先级（role/text/css）。
- **执行内核**：Playwright 同步 API 顺序执行；每步独立超时（默认 15s）与重试（默认 2 次）；失败自动截图落 `rpa_run/screenshots/`。
- **流程版本**：`rpa_flow` 表存流程名、版本、YAML、启用状态；改动留版本号，便于回滚。
- **示例流程**：`jd_price_scan.yaml`——打开搜索页 → 输入关键词 → 点击搜索 → 循环 3 页 → 每页抽取商品卡片 → 滚动加载 → 截图 → 落库。
- **与商业 RPA 的对照**（写进文档）：选择器稳定性、等待策略（显式等待优于 sleep）、异常处理、变量与循环、定时调度、审计日志；说明为什么用代码化 RPA（可版本化、可测试、可 CI）。

### 模块 3：清洗校验 + SQL + MySQL（0.7 人天）

- **pandas 清洗**：`¥1,299.00` / `1.3万+人付款` → 数值；空值策略（价格缺失 → 沿用上次 + 标 `imputed`）；标题归一（去营销词、统一全半角）。
- **异常检测**：同 SKU 价格环比变动 >30% 标 `price_anomaly`；销量标签单位不一致（万/件）统一；同一商品多平台标题相似度（`difflib`）>0.8 视为同款，做跨平台比价表。
- **校验规则引擎**：必填、范围、枚举、唯一四类规则，输出 `clean_report`（总行数/通过/拦截/各类原因计数）。
- **MySQL 建模 + SQL**：按日分区的 `price_snapshot`；报表查询用 GROUP BY 聚合 + 窗口函数（`ROW_NUMBER() OVER (PARTITION BY sku_id ORDER BY date DESC)` 取最新价；`LAG()` 算环比）。
- 只读账号给看板，写账号只给采集进程（最小权限）。

### 模块 4：Excel 报表导出（0.7 人天）

- **openpyxl 多 sheet**：`原始明细` / `清洗后明细` / `透视汇总` / `异常清单` / `趋势`。
- **公式写入**：汇总 sheet 写 `SUMIFS`（按平台求和）、`COUNTIFS`（异常计数）、`VLOOKUP`（SKU 补全）、`AVERAGEIF`；不是只写死值，Excel 打开后可重算。
- **透视口径**：pandas `pivot_table` 生成「平台 × 品类」的价格均值/最低价/商品数，写进 `透视汇总`。
- **格式**：条件格式（涨幅 >20% 红底）、冻结首行、列宽自适应、数字格式（¥ 两位小数）、超链接（商品链接）。
- **图表**：`LineChart`（TOP5 商品 7 日价格）+ `BarChart`（平台均价对比）嵌入 sheet。
- **日报模板化**：文件名 `ecom_report_YYYYMMDD.xlsx`，sheet 名与列顺序固定，可被下游直接消费。

### 模块 5：报表/BI 看板 + 定时调度（0.7 人天）

- **报表/BI 出数链路**：采集 → 清洗 → MySQL → Excel 日报 + Web 看板，两条消费路径共用同一套指标口径，避免「报表一个数、看板另一个数」。
- **FastAPI 5 接口**：`/api/trend`（商品 7/30 日走势）、`/api/platform-compare`、`/api/top-changes`、`/api/health`（采集成功率/封禁率/P95）、`/api/tasks`。
- **Vue3 + ECharts 4 视图**：折线（走势）、分组柱（平台对比）、表格+涨幅色（TOP 变动）、仪表盘+折线（健康度）。
- **指标口径文档**（对应 FineBI）：每个图表的维度、度量、过滤条件、刷新频率写成一张表，可直接照搬到 FineBI 数据集与仪表板。
- **APScheduler**：02:00 采集、08:00 生成 Excel 并写 `report_file` 记录；失败重试 1 次 + 告警日志。

### 模块 6：文档 / 证据 / 部署（0.5 人天）

- README（架构图、目录结构、运行步骤、合规边界）、反爬策略说明、RPA 流程说明、报表字段字典。
- 证据集：采集日志、封禁率曲线、清洗报告、Excel 截图（含公式栏）、看板 4 视图截图、pytest 输出。
- Docker Compose 一键起；`.env.example` 只放占位。

## 7. 面试三问（本项目要能答出来的三个问题）

1. **电商反爬你会怎么设计？被封了怎么办？** 分层说：请求层（限速令牌桶、UA/Header 模板、连接复用）、身份层（Cookie 池轮换与失效探测）、网络层（代理池与健康度）、失败层（指数退避、429 长冷却、断点续采）、观测层（封禁率/成功率/P95 上板）。被封锁时的降级顺序：降并发 → 换 UA/Cookie → 换代理 → 退到 RPA 低频补采 → 人工兜底。同时讲清合规边界：只采公开数据、不绕登录墙、不破解加密。
2. **RPA 和爬虫的区别？你的流程 DSL 凭什么稳定？** 爬虫面向「接口/页面结构」，RPA 面向「人的操作序列」，能处理登录态、懒加载、多步交互。稳定性靠四件事：选择器优先用语义（role/text）而非脆弱 CSS 路径、显式等待替代固定 sleep、每步超时+重试+失败截图、流程版本化可回滚。
3. **Excel 报表怎么做到"能重算、能对账"？** 不写死值：汇总用 SUMIFS/COUNTIFS/VLOOKUP 公式，透视口径由 pandas 统一生成并写清维度度量；报表与 DB 做三方对账（总行数、平台分布、异常数），差异为 0 才算通过；模板固定 sheet 名与列序，下游可直接消费。

## 8. 主动砍掉项

| 砍掉 | 原因 |
|---|---|
| 真实验证码识别/破解 | 违反平台规则，且属灰色能力；本项目做「检测到验证码 → 转人工队列」，不做破解 |
| App / 小程序逆向抓包 | 超出 JD 范围，且合规风险高 |
| 分布式爬虫集群 / 消息队列编排 | MVP 用单机 APScheduler 足够证明能力，集群属另一个量级项目 |
| Scrapy 全家桶 | 框架会用不等于会做采集策略；本项目重点在策略与流程 |
| 真实账号池交易 / 代理池采购 | 不碰灰产；代理池用本地可配置列表，可为空直连 |
| 支付/订单/私信数据 | 涉及隐私与商业机密，只采公开商品字段 |
| 复杂前端设计系统 | 看板复用 #20 的 ECharts 骨架，4 个视图够用 |

## 9. 风险点

| 风险 | 影响 | 应对 |
|---|---|---|
| 平台页面结构变更导致解析失败 | 采集中断、字段错位 | 每日字段缺失率监控（>10% 告警）；保留 `raw_page` 快照可离线复跑；adapter 单测用固定 HTML 快照回归 |
| 无真实登录账号/账号被封 | 天猫详情页采不到 | Cookie 池可空；空时降级为列表页 + RPA 手动登录演示；演示环境用本地 mock 服务兜底，指标如实标注「mock 环境」 |
| 合规风险（爬取被判违规） | 项目不可展示 | 明确合规边界写进 README；限速 + robots 遵守 + 只采公开字段；演示用自有 mock 站点 |
| 反爬对抗升级（指纹/行为检测） | 采集成功率低 | 不追求"绕过"，追求"可持续的低频采集 + 观测 + 降级"；成功率指标如实记录 |
| Excel 公式在非 Windows/LibreOffice 打开异常 | 验收失败 | 用 openpyxl 写入标准公式并用 LibreOffice headless 重算校验一次 |
| 与 #20 看板撞车 | 立项重复 | 已划清：#20 数据源为本地项目产物，无外网采集/反爬/RPA/Excel 导出 |

## 10. 量化基线指标

| 编号 | 指标 | 验证方式 |
|---|---|---|
| C01 | 3 平台 × 每平台 ≥100 商品采集完成 | `price_snapshot` 计数按平台分组核对 |
| C02 | 采集成功率 ≥95%（单日 ≥300 请求） | `antibot_metrics` 统计 2xx/有效页占比 |
| C03 | 限速生效：单域名实际 QPS ≤ 配置上限（误差 0） | 令牌桶日志与请求时间戳核算 |
| C04 | 断点续采：中断后重启，重复采集 = 0，漏采 = 0 | 两次运行 SKU 集合比对 |
| C05 | 去重：同 `(platform, sku_id, date)` 落库 1 条 | DB unique index + 计数 |
| C06 | 清洗：脏数据拦截率 ≥90%（构造 50 条脏样本） | `clean_report` 拦截计数 |
| C07 | 异常检测：价格突变 >30% 全部标出（构造 10 条） | `price_anomaly` 命中 10/10 |

| C09 | Excel 日报 5 sheet 生成 <10s，公式可重算且与 DB 对账差异 0 | LibreOffice headless 重算 + 三方对账 |
| C10 | 看板 4 视图首屏加载 P95 <1.5s | 浏览器实测 10 次 |
| C11 | pytest 用例 ≥25 条全绿（解析/清洗/去重/报表） | `pytest -q` 输出 |

## 11. 数据模型

| 表 | 关键字段 | 说明 |
|---|---|---|
| `task` | id, name, platform, cron, enabled | 采集任务定义 |
| `task_run` | id, task_id, status, cursor, started_at, finished_at, error | 运行记录，`cursor` 支持断点续采 |
| `raw_page` | id, platform, url_hash, url, body_path, http_status, crawled_at | 原始快照落文件，表存指针 |
| `product` | id, platform, sku_id, title, shop, url, category | 商品主数据 |
| `price_snapshot` | id, product_id, price, sales_tag, captured_date | 按 `captured_date` 分区；唯一键 `(product_id, captured_date)` |
| `clean_report` | id, run_date, total, passed, blocked, reasons_json | 清洗校验结果 |
| `antibot_metrics` | id, platform, url, http_status, latency_ms, via_proxy, blocked_flag, at | 反爬与健康度观测 |
| `rpa_flow` | id, name, version, yaml, enabled | 流程定义与版本 |
| `rpa_run` | id, flow_id, status, started_at, finished_at, screenshot_dir, log_path | 流程执行记录 |
| `report_file` | id, run_date, path, sheets_json, rows_json | 报表产物登记 |

索引：`price_snapshot(product_id, captured_date)` 唯一；`product(platform, sku_id)` 唯一；`antibot_metrics(platform, at)` 普通索引（看板按时间聚合）。
