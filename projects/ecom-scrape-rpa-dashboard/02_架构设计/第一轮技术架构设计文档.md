### 1.2 明确不引入（与设计书 §3/§8 一致）

| 不引入 | 原因 | 影响面 |
|---|---|---|
| Scrapy 全家桶 | 本项目价值锚点是"策略与流程"，不是框架用法；Scrapy 的调度器/中间件会遮住限速与退避的实现细节 | 采集并发用 `asyncio.Semaphore` + 自研令牌桶替代 |
| Celery / Kafka / Redis | 单机、单任务、日批，消息队列只增加运维面；基线明确排除分布式集群 | 任务态落 MySQL `task_run`，去重靠 DB 唯一键 |
| 商业 RPA 工具 | JD 要"RPA 流程开发能力"，代码化 DSL 可版本化/可测/可 CI，更贴岗位 | 以文档对照证明概念等价（M2 交付文档） |
| ORM（SQLAlchemy/Django ORM） | 报表核心是窗口函数与分区表，ORM 反而挡路；表数少（12 张），手写 SQL 更可控 | `db.py` 提供 `query()` / `execute_many()` 两个薄封装 |
| 前端组件库（Element Plus 等） | internal-tool 4 个视图，组件库引入 300KB+ 体积，压 C10 预算 | 手写 3 个基础组件（Card / StatTile / DataTable） |
| 验证码识别 / 打码平台 | 合规红线（§8） | 检测到验证码 → `blocked_flag=1, block_reason=captcha` → 转人工队列 |
| 前端设计系统 / 主题系统 | 基线排除范围明确 | 单 CSS 变量文件定色板 |

### 1.3 版本兼容性说明

- **Python 3.11 × pandas 2.2.3 / lxml 5.3.0 / playwright 1.48**：三者均有 cp311 官方 wheel，Linux 容器内无需源码编译。
- **openpyxl 3.1.5 × LibreOffice 24.8**：openpyxl 写公式时**不写 `<v>` 缓存值**，这是刻意的（见 ADR-07）——任何消费者（Excel / LibreOffice）打开都会重算，因此 C09 的"公式可重算"不依赖打开方设置。
- **MySQL 8.0.36 分区限制**：`PARTITION BY RANGE COLUMNS` 要求**每个唯一键都包含分区列**。故 `price_snapshot` 主键为 `(id, captured_date)`、唯一键为 `(platform, sku_id, captured_date)`——这条约束同时也是 C05「同 `(platform, sku_id, date)` 只落 1 条」的架构级保证（ADR-04）。
- **FastAPI 0.115 × Pydantic 2.9**：`response_model` 用 v2 语法（`model_config`），不用 v1 的 `class Config`。
- **Vue 3.4 × ECharts 5.5**：ECharts 用 `echarts/core` 按需注册，避免全量包 1MB。
- **Playwright 1.48 与浏览器版本绑定**：镜像与 pip 包必须同版本（`v1.48.0-jammy` ↔ `playwright==1.48.0`），版本不一致会在容器内报 "Executable doesn't exist"。

## 3. 核心业务链路（端到端输入 / 处理 / 输出）

> 每条链路写清「输入 → 处理节点 → 输出 → 失败与降级」，末尾挂基线编号。链路编号 L1–L10 与 §13 D 清单、§10 指标对照表三处一致。

### L1 配置装载与任务编排

- **输入**：`config/targets.yaml`（品类、关键词、SKU 列表、平台、频率）、`config/sites.yaml`（并发/速率/选择器）、`.env`（DB 连接）。
- **处理**：
  1. `config.py` 装载并**强校验**：platform ∈ {jd,tmall,pdd,douyin,mock}；每平台 SKU 数 ≥100（不足 `WARN_SKU_SHORTAGE`，不静默）；rate.qps ∈ (0,1]。
  2. 计算 `config_hash = sha1(canonical_json(targets))`；与 `task` 最近一行比对，变了→`version+1`。
  3. `task` upsert（name=`daily_<platform>`），生成 `task_run`（status=running，`cursor={page:0,done:0}`）。
- **输出**：`task`（4 行）/`task_run`（4 行）/ 控制台 JSON 摘要。
- **失败与降级**：配置非法 → 进程退出码 2，不发起任何请求（避免"配置错还去打站点"）；SKU 不足只 WARN，由 C01 断言兜底。
- **对应**：C01、C04。

### L2 HTTP 采集主链路（单页请求的完整路径）

- **输入**：`task_run` + `targets.yaml` 中的 (platform, keyword/sku, page)。
- **处理**（严格按此顺序，任何一步短路都要写原因）：
  1. `rate_limiter.acquire(domain)`：单域名令牌桶，容量 1、补充 1/1.5s；拿不到令牌就 await（**不是 sleep 后硬闯**），记 `wait_ms`。
  2. `ua_pool.pick(platform)`：10 条真实 UA 轮换；`headers_template(platform)` 固定 header 顺序（Accept / Accept-Language / Accept-Encoding / Connection / UA / Referer），避免"顺序异常"被判机器人。
  3. `cookie_pool.acquire(platform)`：天猫必须；京东/拼多多可选；空池 → 走无 Cookie 路径并在 `antibot_metrics.cookie_state=none`。
  4. `proxy_pool.pick()`：空列表 → 直连（`via_proxy=0`）；连续失败 2 次 → 标记 unhealthy 并切下一个。
  5. httpx 请求（timeout: connect 5s / read 10s；`follow_redirects=False` 以便识别 302 到登录页）。
  6. 判定：`http_status` + 启发式风控页检测（页面含「验证码 / 访问受限 / 请稍后再试」关键词 / 302→login）→ `blocked_flag=1` + `block_reason`。
  7. 写 `antibot_metrics`（platform/url/http_status/latency_ms/via_proxy/blocked_flag/cookie_state/retry_no/at）。
  8. `raw_page` 落盘：`data/raw/<platform>/<YYYYMMDD>/<url_hash>.html` + 表存指针（byte_size、content_type）。
  9. `adapter.parse_list/parse_detail`（parsel）→ 8 字段统一结构（platform/sku_id/title/price/sales_tag/shop/url/crawled_at）→ 送入 L5。
- **输出**：`raw_page` 1 行 + 1 个 HTML 文件 + `antibot_metrics` 1 行 + 统一 item 列表。
- **失败与降级**（顺序固定，写进 `ops.md`）：429/503 → 长冷却 30s 起（不走普通退避）→ 重试；网络错误 → 指数退避 `1s×2^n`，`max=3` 次；持续 blocked → 换 UA → 换 Cookie → 换代理 → 降并发 → 转 RPA 低频补采（L4）→ 人工兜底。
- **对应**：C01、C02、C03，风险 §8 R-01/R-04/R-06。

### L3 断点续采与去重

- **输入**：`task_run.cursor={page, offset, done_sku_count}` + 本页 item 列表。
- **处理**：
  1. **页级提交**：一页解析成功 → 事务内写 `product`（upsert `uk_platform_sku`）+ `price_snapshot`（`INSERT ... ON DUPLICATE KEY UPDATE`，命中 `uk_platform_sku_date` 则更新价格）+ `task_run_item`（run_id, platform, sku_id, status='ok'）→ 同一事务内 `UPDATE task_run SET cursor=?`。**先落数据再推游标**，断电不会"跳过一页"。
  2. **URL 指纹去重**：`url_hash = sha1(normalize(url))`（去 query 中 utm/track 参数、排序剩余参数）；同 hash 已存在且 `force=False` → 跳过请求（省一次出网）。
  3. **DB 兜底**：`uk_platform_sku_date` 命中即更新，不产生第二行。
  4. **重启续采**：`task_run.status='interrupted'` 时，读 `cursor.page` 从下一页开始；`done_sku_count` 与实际 `task_run_item` 计数不一致 → 以 item 表为准并记 WARN（自愈而非报错）。
- **输出**：`task_run_item` 每 SKU 一行（ok/skip/fail），`task_run.cursor` 单调前进。
- **失败与降级**：单 SKU 解析失败 → `status=fail` + 原因，**不中断整页**（一页里坏 1 个不影响其余 99 个）；整页失败 3 次 → 标记该页 `status=fail` 并继续下一页，最终 `task_run.status=partial`。
- **对应**：C04、C05。

### L4 RPA 补采链路（登录态 / 复杂翻页）

- **输入**：`flows/jd_price_scan.yaml` + 变量 `${keyword}`；`rpa_flow` 最新启用版本。
- **处理**：
  1. `loader.py` 校验 DSL：步骤类型 ∈ 8 种；`assert` 必须有 `expect`；每个 select 必须有 `by ∈ {role,text,css}`。
  2. `engine.py` 顺序执行：每步 `timeout`（默认 15s）+ `retries`（默认 2）；等待策略为**显式等待**（`wait_for_selector(state='visible')`），禁止 `sleep`（DSL 里 `wait` 只允许 `selector` 或 `networkidle`，不允许裸毫秒）。
  3. `extract` 支持 `loop`（对卡片列表遍历，`as: items[]`）→ 输出结构与 L2 的 8 字段对齐，直接复用 L5 清洗。
  4. 失败 → 截图 `data/rpa_run/<run_id>/step_<n>_fail.png` + 上下文快照（URL、可见文本前 500 字）。
  5. 写 `rpa_run`（status/screenshot_dir/log_path/步骤耗时明细）。
- **输出**：`rpa_run` 1 行 + `screenshots/` + 抽取 item 入库（走 L3 同一条落库函数）。
- **失败与降级**：登录页出现 → `assert` 失败 → 截图 → `status=failed`，不重试登录（不碰账号安全策略）；Chromium 启动失败 → 记录并跳过当日 RPA 补采，L2 主链路不受影响（**RPA 是补采，不是主链路**）。
- **对应**：C08。

### L5 清洗校验链路

- **输入**：L2/L4 产出的统一 item 列表（当日全量）。
- **处理**（固定顺序，顺序即优先级）：
  1. **归一化**：`¥1,299.00`/`1299元`/`1,299` → `1299.00`；`1.3万+人付款` → `sales_num=13000, sales_unit='万'`；标题去营销词（`【】`、`包邮`、`秒杀`、`官方旗舰店`）+ 全半角统一 + 连续空白折叠。
  2. **必填校验**：`platform/sku_id/title` 空 → 拦截（`rule=required`）。
  3. **价格缺失策略**（ADR-06）：`price` 空 → 查 `product` 最近一次快照价，有则沿用 + `imputed=1`；无则拦截（`rule=required_price`）。**不因缺价丢整行**，但绝不编造价格。
  4. **范围校验**：`0.01 ≤ price ≤ 99999`；`sales_num ≥ 0`；`title` 长度 ≤255 → 越界拦截（`rule=range`）。
  5. **枚举校验**：`platform ∈ 4 值`、`sales_unit ∈ {件,万,None}` → 非法拦截（`rule=enum`）。
  6. **唯一校验**：`(platform, sku_id, captured_date)` 在批次内重复 → 保留 `crawled_at` 最晚一条（`rule=duplicate`），DB 唯一键二次兜底。
  7. **突变检测**：同 `product_id` 与上一有效快照比较，`|Δ|/prev > 30%` → `anomaly_flag=1` + 写 `price_anomaly_reason`（**标记不拦截**，异常是业务信号不是脏数据）。
  8. **跨平台同款**：同品类内 `difflib.SequenceMatcher` 标题相似度 >0.8 → 聚为 `same_group_id`，供比价表使用。
  9. 汇总写 `clean_report`（total/passed/blocked/reasons_json）+ `clean_issue` 逐行原因。
- **输出**：`clean_report` 1 行/日、`clean_issue` N 行（拦截明细）、`price_snapshot` 更新（imputed/anomaly_flag 回填）。
- **失败与降级**：pandas 处理异常 → 整批不落库（避免半干净数据污染报表），`clean_report.status=failed` + 记 `_失败日志`；单行异常被 try/except 包住记 `rule=unexpected` 并拦截。
- **对应**：C06、C07、C09（报表口径来源）。

### L6 落库与查询口径

- **输入**：清洗后的 DataFrame。
- **处理**：
  1. `price_snapshot` 批量 upsert（`executemany` + 事务，500 行/批）。
  2. 生成当日 `agg_daily_platform`（平台维度：sku_count / avg_price / min_price / max_price / sum_sales / req_cnt / success_cnt / blocked_cnt / p95_latency_ms）。
  3. 报表与看板**共用** `sql/queries/*.sql` 中的同一组 SQL（ADR-08）：
     - 最新价：`ROW_NUMBER() OVER (PARTITION BY sku_id, platform ORDER BY captured_date DESC)`
     - 环比：`LAG(price) OVER (PARTITION BY sku_id, platform ORDER BY captured_date)`
     - P95：`ROW_NUMBER() OVER (ORDER BY latency_ms)` + `CEIL(0.95*cnt)`
- **输出**：`price_snapshot` / `agg_daily_platform` / 可复用查询结果集。
- **失败与降级**：分区不存在（跨月）→ `db.py` 启动时按 `schema` 配置自动 `ADD PARTITION`（幂等）；upsert 冲突 → 更新不报错。
- **对应**：C01、C05。

### L7 Excel 日报链路

- **输入**：当日清洗后数据 + `agg_daily_platform` + `price_snapshot` 近 7 日。
- **处理**：
  1. `pivot_table`（index=platform, columns=category, values=price → mean/min/count）。
  2. 5 个 sheet 按固定顺序写：`原始明细` / `清洗后明细` / `透视汇总` / `异常清单` / `趋势`。
  3. `透视汇总` 写公式（**不写死值**）：`SUMIFS`、`COUNTIFS`、`VLOOKUP`、`AVERAGEIF`，引用 `清洗后明细` 的整列区域。
  4. 格式：`涨幅 >20%` 红底（`CellIsRule`）、冻结 `A2`、列宽按内容、`¥#,##0.00`、商品 URL 超链接。
  5. 图表：`LineChart`（TOP5 商品 7 日价）+ `BarChart`（平台均价）。
  6. 文件名 `ecom_report_YYYYMMDD.xlsx` 落 `data/reports/`，写 `report_file`（path/sheets_json/rows_json）。
  7. 生成耗时埋点：`t0=now()` → 写完 → 记 `elapsed_ms` 到 `report_file`（C09 的 <10s 由此取证）。
- **输出**：xlsx + `report_file` 1 行。
- **失败与降级**：写盘失败（磁盘满/被占用）→ 重试 1 次 → 仍失败则 `report_file.status=failed` + 告警日志，不删旧报表。
- **对应**：C09。

### L8 看板出数链路

- **输入**：浏览器请求 5 个接口之一。
- **处理**：nginx `location /api` → `proxy_pass http://api:8094` → FastAPI 路由 → 参数校验（`days ∈ {7,30}`、`limit ≤ 50`）→ 读 `sql/queries/*.sql` → Pydantic 序列化 → 统一响应包。
- **输出**：JSON（`code=0`）。
- **失败与降级**：DB 不可用 → 503 + `code=50301`（前端显示"数据服务暂不可用，最后更新 <时间>"，不白屏）；无数据 → `data=[]` + `code=0`（不是错误）；缓存命中（60s TTL）→ 直接返回。
- **对应**：C10。

### L9 调度与运维链路

- **输入**：APScheduler cron（`collect` 02:00、`report` 08:00，`Asia/Shanghai`）。
- **处理**：`coalesce=True`（错过多次只跑一次）、`max_instances=1`（防重入）、`misfire_grace_time=3600`；任务失败 → **重试 1 次**（间隔 5 分钟）→ 仍失败写 `logs/alerts.jsonl`（level=error, job, run_id, reason）。
- **输出**：`task_run` / `report_file` / `alerts.jsonl`。
- **失败与降级**：进程被杀 → compose `restart: unless-stopped`；MySQL 不可用 → 任务直接失败并告警（不静默重试到天亮）；日期跨月分区缺失 → 自动补分区后重试一次。
- **对应**：C09、C02（健康度时点）。

### L10 mock 环境链路（无真实账号时的兜底）

- **输入**：`MOCK_MODE=1` 或 `targets.yaml` 中 platform=mock。
- **处理**：`mock_site/app.py`（FastAPI，端口 5190，**仅 127.0.0.1**）提供：3 平台列表/详情页（含内嵌 JSON 价格）、分页、可选注入 429、可选注入验证码页、可选注入脏数据（价格 `面议`、销量 `--`）。适配器 `mock.py` 走完全相同的 L2 路径（同样过令牌桶与观测），保证"换真站点只换 adapter"。
- **输出**：与真实站点结构一致的数据；所有对外指标标注「mock 环境」。
- **失败与降级**：不适用（本地自建，无外部依赖）。
- **对应**：C01–C11 全链路可复现性，基线 §3 配套范围第 1 项。

## 4. 数据模型设计

### 4.1 设计原则

1. **原始与结构化分离**：`raw_page` 只存指针（`body_path`），HTML 落文件——表不被大字段撑爆，且可离线复跑解析（风险 R-01 的应对）。
2. **唯一性下沉到 DB**：能在 DB 保证的，不在应用层"记得去重"。C05 的断言因此是一句 `SELECT`。
3. **分区列进唯一键**：MySQL 8 硬约束，也顺带把"按日唯一"变成架构保证。
4. **冗余少量字段换可查性**：`price_snapshot` 冗余 `platform`/`sku_id`，避免看板查询每次 join `product`（C10 P95 的关键）。
5. **不可变 + 可追溯**：`antibot_metrics`/`task_run_item` 只追加不更新；`price_snapshot` 只 upsert 当日行。
6. **字符集统一** `utf8mb4 / utf8mb4_0900_ai_ci`（中文标题、¥ 符号、emoji 商品名都不炸）。

### 4.2 DDL（`sql/init/01_schema.sql`）

  finished_at    DATETIME     NULL,

  KEY idx_flow_status (flow_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 12) 报表产物登记
CREATE TABLE IF NOT EXISTS report_file (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  run_date    DATE         NOT NULL,
  path        VARCHAR(255) NOT NULL,

  rows_json   JSON         NOT NULL,           -- {"原始明细":312,"清洗后明细":300,...}

-- 13) 平台日聚合（P95 的预聚合来源）
CREATE TABLE IF NOT EXISTS agg_daily_platform (
  stat_date       DATE        NOT NULL,
  platform        VARCHAR(16) NOT NULL,

  success_cnt     INT         NOT NULL DEFAULT 0,

### 4.3 主键 / 分区 / 索引决策

| 决策 | 内容 | 理由 | 验证方式 |
|---|---|---|---|
| 分区 | `price_snapshot` 按 `captured_date` RANGE COLUMNS，按月一个分区 + pmax | 单日全表仅 300 行、30 天 9000 行，分区收益不在查询而在**归档**（删月份即 `DROP PARTITION`）与"按日唯一"约束的合规实现 | `SHOW CREATE TABLE` + `information_schema.PARTITIONS` |
| 唯一键 | `uk_platform_sku_date (platform, sku_id, captured_date)` | C05 的"1 条"由 DB 保证，不靠应用逻辑 | `SELECT platform,sku_id,captured_date,COUNT(*) c ... HAVING c>1` 必须 0 行 |
| 商品唯一 | `uk_platform_sku` | 同平台同 SKU 只有一个 product 行 | 同上断言 |
| 观测索引 | `idx_platform_at`、`idx_blocked` | 健康度按平台+时间聚合（C02） | `EXPLAIN` 走 range |
| 运行明细 | `uk_run_sku (run_id, platform, sku_id)` | C04 集合比对用 `NOT IN` / `EXCEPT` 语义，天然无重复 | 两次 run 的 `task_run_item` 集合差为 0 |
| 分区自动补 | `db.py` 启动执行 `ADD PARTITION IF NOT EXISTS` 等价的 `ALTER ... REORGANIZE pmax` | 跨月忘补分区会让写入直接报 1526 | 跨月模拟：改系统日期/写入下月日期 |

### 4.4 表关联关系

```
task 1 ── n task_run 1 ── n task_run_item n ── 1 product
task_run 1 ── n raw_page ──(body_path)──> data/raw/*.html
product 1 ── n price_snapshot (product_id)  [按日分区]
product 1 ── n price_snapshot (platform, sku_id 冗余，便于分区内唯一)
clean_report 1 ── n clean_issue (run_date)
rpa_flow 1 ── n rpa_run
report_file (run_date) ── 独立，无外键（产物路径即关联）
agg_daily_platform (stat_date, platform) ── 由 price_snapshot + antibot_metrics 聚合而来
```

**不建物理外键**（`FOREIGN KEY`）：批量 upsert 时外键检查会拖慢 3–5 倍，且清洗层允许 `product` 与 `price_snapshot` 先后到达。改为**逻辑外键 + 每日一致性检查**（`scripts/reconcile_check.py` 断言孤儿快照为 0）。

### 4.5 关键查询口径（报表与看板共用）

```sql
-- Q1 最新价（每 SKU 每平台取一行）
SELECT platform, sku_id, price, captured_date FROM (
  SELECT platform, sku_id, price, captured_date,
         ROW_NUMBER() OVER (PARTITION BY platform, sku_id ORDER BY captured_date DESC) rn
  FROM price_snapshot WHERE captured_date BETWEEN :start AND :end
) t WHERE rn = 1;

-- Q2 环比（LAG）
SELECT platform, sku_id, captured_date, price,
       LAG(price) OVER (PARTITION BY platform, sku_id ORDER BY captured_date) prev_price,
       ROUND((price - LAG(price) OVER (PARTITION BY platform, sku_id ORDER BY captured_date))
             / NULLIF(LAG(price) OVER (PARTITION BY platform, sku_id ORDER BY captured_date),0) * 100, 2) change_pct
FROM price_snapshot WHERE captured_date BETWEEN :start AND :end;

-- Q3 P95 耗时（MySQL 8 无 percentile_cont，用行号取）
SELECT platform, latency_ms FROM (
  SELECT platform, latency_ms,
         ROW_NUMBER() OVER (PARTITION BY platform ORDER BY latency_ms) rn,
         COUNT(*)    OVER (PARTITION BY platform) cnt
  FROM antibot_metrics WHERE at >= :day_start AND at < :day_end
) t WHERE rn = CEIL(0.95 * cnt);
```

## 5. 接口规范定义

### 5.1 统一请求/返回格式

**请求**：`GET`，query 参数，无 body；时间用 `YYYY-MM-DD`，枚举值小写。

**返回**（所有接口一致，前端 axios 拦截器统一解包 `data`）：

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "trace_id": "3f8c1a9e",
  "cached": false
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | int | 0=成功，非 0 见 §5.2 |
| `message` | string | 人类可读；成功固定 `ok` |
| `data` | object/array | 载荷；无数据时 `[]` 或 `null`，**不省略字段** |
| `trace_id` | string | 8 位十六进制，写日志，便于对齐（同一次请求在 `logs/api.jsonl` 可查） |
| `cached` | bool | 是否命中 60s TTL 缓存（C10 调优时用来区分冷热） |

### 5.2 错误码规范

| code | HTTP | 含义 | 触发场景 | 前端处理 |
|---|---|---|---|---|
| 0 | 200 | 成功 | — | 正常渲染 |
| 40001 | 400 | 参数非法 | `days` 不在 {7,30}、`limit>50`、日期格式错 | 提示错误参数，不重试 |
| 40401 | 404 | 资源不存在 | `sku_id` 无任何快照 | 显示"暂无该商品数据" |
| 42901 | 429 | 请求过频 | 单 IP >30 req/min（nginx `limit_req`） | 提示稍后重试 |
| 50001 | 500 | 内部错误 | 未捕获异常 | 显示"服务异常"，带 trace_id 便于排查 |
| 50301 | 503 | 数据服务不可用 | MySQL 连接失败/超时 | 显示"数据服务暂不可用，最后更新 <时间>" |

实现：`api/errors.py` 注册 `@app.exception_handler(ApiError)`，所有路由只抛 `ApiError(code, message)`；未捕获异常由兜底 handler 转 `50001` 并记 `trace_id`。

### 5.3 鉴权与访问控制

- **无用户登录**：internal-tool，单机自用，不引入账号体系（基线未要求，且会挤占 5 人天预算）。
- **网络边界**：`api` 容器只映射 `127.0.0.1:8094`；`web` 映射 `127.0.0.1:5187`；外网不可达。
- **数据库最小权限**：`ecom_ro`（SELECT only）给 API；`ecom_rw`（SELECT/INSERT/UPDATE）给采集与报表；`DROP/ALTER` 只给初始化脚本用的 root。
- **CORS**：仅允许 `http://127.0.0.1:5187`（dev）与同源（prod nginx 反代）。
- **敏感信息**：DB 口令、Cookie 文件只在 `.env` / `config/cookies/`，进 `.gitignore` + `.secretignore`；`prepush_check.py` 兜底扫历史。

## 7. 监控与运维

### 7.1 监控指标体系

| 指标 | 口径（SQL 来源） | 阈值（告警） | 服务对象 |
|---|---|---|---|
| 采集成功率 | `SUM(http_status BETWEEN 200 AND 299 OR blocked=0)/COUNT(*)` from `antibot_metrics` | <95% → WARN（C02 红线） | 看板健康度 |
| 封禁率 | `SUM(blocked_flag)/COUNT(*)` | >10% → WARN，>25% → ERROR（触发降级链） | 看板健康度 |
| P95 耗时 | Q3（行号法） | >8000ms → WARN | 看板健康度 |
| 令牌桶速率 | `1/AVG(diff(at))` per platform | 高于配置 qps → ERROR（C03 破防） | 运维 |
| 字段缺失率 | `SUM(title IS NULL OR price IS NULL)/COUNT(*)` per platform/day | >10% → WARN（风险 R-01 前置信号） | 运维 |
| 断点续采一致性 | 两次 run 的 `task_run_item` 集合差 | 差 >0 → ERROR（C04） | 验收 |
| 清洗拦截率 | `blocked/total` from `clean_report` | 连续 2 日 >20% → WARN（可能站点改版） | 运维 |
| 报表耗时 | `report_file.elapsed_ms` | >10000 → WARN（C09 红线） | 运维 |
| 看板 P95 | `scripts/perf_probe.py` 10 次 | >1500ms → WARN（C10 红线） | 验收 |
| 任务状态 | `task_run.status` | `failed` → ERROR；`partial` → WARN | 看板任务视图 |

### 7.2 告警规则与处置

| 告警 | 级别 | 触发 | 处置（写进 `ops.md`） |
|---|---|---|---|
| `collect_failed` | ERROR | `task_run.status=failed` | 看 `logs/collect.jsonl` 最后一条 error → 分辨是 DB / 网络 / 解析 → 对应修 → `python -m app.cli backfill --date` 补采 |
| `success_rate_low` | WARN | 当日成功率 <95% | 降并发至 1、延长间隔至 3s、切 UA 池 → 观察 1 小时 |
| `blocked_spike` | ERROR | 单平台封禁率 >25% | 停该平台（`DISABLE_PLATFORMS`）→ 换 Cookie/代理 → 转 RPA 低频 |
| `report_failed` | ERROR | `report_file.status=failed` | 检查磁盘/文件占用 → 重跑 `python -m app.cli report` |
| `partition_missing` | ERROR | MySQL 1526 | `python -m app.cli initdb --ensure-partitions` |
| `rpa_failed` | WARN | `rpa_run.status=failed` | 看 `screenshots/step_*_fail.png` → 修选择器 → 升流程版本 |

告警落地：`logs/alerts.jsonl` 一行一条（`ts/level/rule/run_id/detail`），**不外发**（无短信/邮件依赖，符合 G11 无外部 key）；第 9 步验收以该文件为证据。

### 7.3 运维流程（`ops.md` 目录）

1. 每日巡检清单（5 项：任务状态、成功率、报表产物、异常数、磁盘）。
2. 一键起/停/重建（`docker compose up -d` / `down` / `up -d --build`）。
3. 端口冲突处理（`env_preflight.py` 报红 → 杀进程或改表）。
4. Cookie 失效处理（导出 JSON → 覆盖 `config/cookies/*.json` → 重启 scheduler）。
5. 报表被占用/重生成。
6. 跨月分区补齐。
7. 数据重置（保留 N 天 → 删 raw/报表/分区）。
8. 备份与恢复（`mysqldump` + `data/reports` 打包）。

### 7.4 数据保留与清理

| 数据 | 保留 | 清理方式 |
|---|---|---|
| `raw_page` 文件 | 30 天 | `python -m app.cli prune --days 30`（先删文件再删表行，失败不动表） |
| `data/reports` | 90 天 | 同上 |
| `antibot_metrics` | 180 天 | 按月 `DELETE ... WHERE at <` |
| `price_snapshot` | 永久（分区归档） | 按年 `DROP PARTITION` |
| `logs/*.jsonl` | 90 天 | 按文件日期删 |

## 8. 技术风险与应对

| # | 风险 | 概率 | 影响 | 应对（有落点，不写空话） | 验证 |
|---|---|---|---|---|---|
| R-01 | 平台页面结构变更 → 解析全空 | 高 | C01 崩 | ①`adapter` 单测用固定 HTML 快照（`tests/fixtures/*.html`），改版时先改快照再改解析；②字段缺失率 >10% 告警；③`raw_page` 保留 30 天，可离线复跑 `python -m app.cli reparse --date` | 快照测试 + 缺失率曲线 |

## 9. 设计决策记录（ADR）

| ADR | 决策 | 备选 | 理由 | 代价 |
|---|---|---|---|---|
| ADR-01 | 自研适配器 + httpx，不用 Scrapy | Scrapy | 价值锚点是策略实现细节，框架会遮住令牌桶/退避/断点；单机 300 请求/日框架收益为负 | 需自己写并发编排（约 120 行） |
| ADR-02 | 反爬策略全部配置化（`sites.yaml`）+ 每次请求落 `antibot_metrics` | 代码里写死 | 被封时改配置即降级，不改代码；观测数据是 C02/C03 唯一证据来源 | 每请求多一次 INSERT（批量化缓解） |
| ADR-03 | RPA 用 YAML DSL + Playwright，不接商业 RPA | UiPath/影刀 | 可版本化、可测试、可 CI；JD 要的是流程编排能力 | 需自写 8 个动作（约 200 行） |
| ADR-04 | `price_snapshot` 冗余 `platform/sku_id`，唯一键 `(platform,sku_id,captured_date)` | 只留 `(product_id,captured_date)` | MySQL 分区要求唯一键含分区列；且 C05 的断言变成一句 SQL，看板也免 join | 少量冗余存储（可忽略） |
| ADR-05 | 断点续采用 `cursor + task_run_item` 双写 | 只用 cursor | cursor 会因"数据写了但游标没推"或反之产生偏差；item 表是自愈与 C04 比对的唯一事实源 | 每 SKU 多一行（300 行/日，可忽略） |
| ADR-06 | 缺价沿用上次价 + `imputed=1`，不丢行 | 直接拦截 | 拦截会让"商品突然消失"污染走势；标记后可查可排除 | 报表需说明 `imputed` 行占比 |
| ADR-07 | Excel 只写公式不写缓存值 | 写死计算结果 | C09 要求"打开可重算"；无缓存值意味着任何消费方都必须重算，天然可验证 | 不能用 `data_only=True` 读（校验脚本要知道这点） |
| ADR-08 | 报表与看板共用 `sql/queries/*.sql` | 各写各的 | 防"报表一个数、看板另一个数"（C09 三方对账的根因） | 查询需兼顾两种消费（列名对齐） |
| ADR-09 | 加 `agg_daily_platform` 预聚合表 | 每次实时聚合 | C10 P95 <1.5s 的确定性保障；日批顺带算好 | 多一张表与一次写入 |

## 10. 基线 C01–C11 的架构支撑对照

| 编号 | 指标 | 架构支撑（落点） | 测量口径（防验收扯皮） |
|---|---|---|---|
| C01 | 3 平台 × ≥100 条/日 | L1 编排 + L2 适配器 + L3 落库 | `SELECT platform, COUNT(DISTINCT sku_id) FROM price_snapshot WHERE captured_date=:d GROUP BY platform`，每平台 ≥100；平台数 ≥3 |
| C02 | 成功率 ≥95%（≥300 请求/日） | L2 观测 + `antibot_metrics` + `/api/health` | `SUM(blocked_flag=0 AND (http_status BETWEEN 200 AND 299))/COUNT(*)`；分母为当日请求数（含重试） |
| C03 | 单域名实际 QPS ≤ 配置 | `rate_limiter.py` + `wait_ms` 落表 | 同平台相邻 `at` 差值 `MIN(diff) ≥ 1500ms`；`AVG(diff)` 换算 QPS ≤0.667 |
| C04 | 断点续采重复 0 / 漏采 0 | L3 页级事务 + `task_run_item` | 两次 run（中断/续跑）的 `task_run_item(ok)` 集合：`A EXCEPT B` 与 `B EXCEPT A` 均为空 |
| C05 | 同 `(platform,sku_id,date)` 1 条 | ADR-04 唯一键 | `GROUP BY platform,sku_id,captured_date HAVING COUNT(*)>1` 返回 0 行 |
| C06 | 脏数据拦截率 ≥90%（50 条样本） | L5 规则引擎 + `clean_issue` | `blocked/50 ≥0.9`；`clean_issue` 按 `rule` 分组计数与 `reasons_json` 一致 |
| C07 | 突变 >30% 命中 10/10 | L5 突变检测 + `anomaly_flag` | `SELECT COUNT(*) FROM price_snapshot WHERE captured_date=:d AND anomaly_flag=1` ≥10 且构造样本 10 条全命中（按 sku 列表核对） |
| C08 | RPA 5 步全通 + 失败截图 | L4 引擎 + `rpa_run` + `screenshots/` | `rpa_run` 最新一行 `steps_ok=steps_total`；`data/rpa_run/<id>/` 至少 1 张 `step_*_fail.png`（故障演练留证） |
| C09 | 5 sheet <10s + 重算差异 0 | L7 + `recalc_check.py` | `report_file.elapsed_ms <10000`；`recalc_check.py` 输出「Excel vs DB」4 项差异均为 0（总行数/平台分布/异常数/均价） |
| C10 | 4 视图 P95 <1.5s | L8 + 预聚合 + 缓存 | `perf_probe.py` 10 次 `navigation timing` 取 P95 <1500ms |
| C11 | pytest ≥25 条全绿 | `tests/` 6 文件 | `pytest -q` 输出 passed ≥25，failed 0 |

### 10.1 指标测量口径备注（易扯皮处先说清）

- **C02 分母**：含重试请求。若排除重试，成功率会虚高，与"单日 ≥300 次请求"口径不符。
- **C03 "误差 0 QPS"**：按 `MIN(diff) ≥ 1500ms` 判定，而非平均值——平均值达标但存在连发仍算破防。
- **C06 样本**：50 条脏样本由 `scripts/gen_dirty.py` 固定种子生成（可复现），不是手工随手造。
- **C07 与 C06 不重叠**：突变是"合法但异常"的数据，不拦截只标记；因此 C06 的 50 条不含突变样本。
- **C09 三方对账**：三方 = Excel（重算后）/ MySQL（SQL 聚合）/ 看板 API（`/api/platform-compare`），同一日期同一口径。
- **C10 首屏定义**：`navigationStart → loadEventEnd`，本地 127.0.0.1，冷缓存（每次 `no-store`），10 次取 P95。
