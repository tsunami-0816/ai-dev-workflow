# 问题台账（第 6 / 6.5 / 7 / 8 / 8.5 / 9 步共用 · 唯一问题清单）

> **一条问题只在这里记一次。** 不再分别新建「联调问题清单 / BUGLIST.md / 验收问题清单 / 回归验证报告」——
> 那些文件里的内容本台账都有列，分成五份只会让同一个问题被记五遍、状态五处不同步。
> 各阶段目录只放**证据**（检查清单、截图、执行日志、脚本），问题本身一律回流到本台账。

## 使用规则

1. **发现问题就记**：ID 用 `Q-001` 递增，不回收、不复用。级别只填 P0/P1/P2/P3（口径见 WORKFLOW_执行约定.md「问题分级」）。
2. **来源阶段**填发现它的那一步：`6` / `6.5` / `7` / `7.5` / `8` / `8.5` / `9`。回流后重新发现的，写回原行并在「轮次」里加一笔，不新开一条。
3. **状态只有四个值**：
   - `open` = 已确认、未修
   - `fixed` = 已改完代码、**未回归验证**
   - `verified` = 回归通过
   - `deferred` = 明确降级为 P2/P3 留到下版本（必须在「归属」写清去哪）
4. **只有 `open` / `fixed` 的 P0/P1 会阻塞放行**：门禁脚本会读本表，存在这两类行时第 7/8/9 步不得放行、`workflow_completion_check.py` 报红。
5. **轮次**写 `第几轮发现/修复`（如 `R2`）。每轮结束在下面「轮次日志」记一行：本轮 open 数必须比上一轮严格下降；不降或回升 → 按 WORKFLOW_执行约定.md「问题路由表」判架构问题回流。
6. **响应类型与 findings 数（G3）**：轮次日志每行填 `response_type`（stop / retry / human / transient，口径见执行约定 §二「失败响应四分类」）与 `findings_count`（本轮问题数）；`retry` 轮次 findings 必须递减，不降转 `human`；振荡第 2 次直接 `human`。
7. 修复/回归的具体 Prompt 用 `prompts/appendixA_通用修复回归模板.md`，那份模板按本台账操作。
