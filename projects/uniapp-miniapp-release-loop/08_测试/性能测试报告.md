## 6. 瓶颈分析

1. **客户端瓶颈（首要）**：Python urllib 无连接复用，单机 GIL 下 50 并发 Avg 翻倍而 TPS 不涨；同机 JMeter 10 线程即 6.9k TPS、50 线程 10.1k TPS。容量测试不应以 Python 绝对值为准。
2. **服务端读路径**：缓存命中 90.5%，冷缓存 10 并发只回源 ≤2 次，MySQL 读不是瓶颈；50 线程 P99 14 ms，仍无排队迹象。
3. **写路径**：预约单次 19 ms 均值，DB 唯一索引 + Redis SETNX + MQ publish 三段串行；当前 30 样本无冲突，未触发唯一键竞争分支。高并发同号场景会走「唯一键兜底」慢路径，生产需关注。
4. **云函数一跳**：本机 Node 模拟，额外 3–20 ms；真实云开发冷启动与公网 RTT 会抬高 P95，上线前应在真实环境复测一次 C03。
5. **本机资源**：15.7 GB 内存下同时跑后端 + Node + Vite + JMeter + Puppeteer，压测时 CPU 竞争会放大 Python 客户端抖动（Max 139 ms 出现在 10 并发档）。

## 7. 建议

- 容量/ SLA 验收统一用 JMeter（keep-alive），至少覆盖 50 / 100 线程；Python 脚本保留为功能级 P95 采样。
- 生产复测 C03 时把云函数换成真实云开发环境，并记录冷启动首个请求的 P95。
- 写路径若要做压测，需准备「同号冲突」「跨号并发」两组数据，观察唯一键兜底与 MQ 堆积。
