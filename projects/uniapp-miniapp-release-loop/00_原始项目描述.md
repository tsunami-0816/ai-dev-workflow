# 项目设计书 · uniapp-miniapp-release-loop（uni-app 双端 + 微信小程序提审发布闭环）

> 目的：补 G9 缺口——证明「uni-app 一套代码出 H5 + 微信小程序、真机预览、提审/审核/发布/回滚闭环」。
> 覆盖 JD：杭州伯遇智能（前端·Vue 方向校招）、杭州星光兔摄影（全栈·写真小程序方向）、灰豚科技（初级前端）、高帆破浪（前端实习）、杭州云联慧算（前端校招）、雄伟科技（AI Agent 全栈·小程序加分）。
> 与 react-taro-microfrontend 的关系：那个项目证明的是 React + Taro + qiankun 微前端与「开发者工具里的三页」，**不含真机体验版、不含提审发布**；本项目增量就是 **uni-app 技术栈 + 真机体验版 + 审核发布闭环**，不复做 Taro、不复做微前端。

## 1. 一句话定位

用 uni-app（Vue3 + TypeScript + Vite）写一套「写真预约」业务代码，同时编译出 H5 端和微信小程序端，小程序走完「体验版真机预览 → 提交审核 → 审核通过 → 发布上线 → 版本回滚」全流程；后端复用已有 Spring Boot 骨架（MySQL + Redis + RabbitMQ + RESTful API），小程序侧通过云开发 Node.js 云函数做接口代理，绕开未备案 HTTPS 域名的限制。

## 2. 业务场景（MVP 最小可用场景，必须能做完）

用户在微信里打开「写真预约」小程序 → 微信授权登录 → 首页看到 4 个写真套餐（价格/封面/标签）→ 点进套餐详情看样片与说明 → 填预约表单（日期、时段、联系人、备注）提交 → 「我的」页看到自己的预约单与状态 → H5 端用同一套代码同样跑通这 5 个页面。

**做完这件事，项目就算成了。** 不做支付、不做真实短信、不做商家后台、不做图片上传审核、不做多门店排期算法。

发布侧必须交出的证据（不是"能跑"就算）：
1. 微信开发者工具里生成的**体验版二维码**，真机扫码进入并截图；
2. 小程序后台的**提交审核记录**截图 + 审核结果截图（通过或被驳回后的修改再提审记录）；
3. **线上正式版本**的版本号、发布时间截图；
4. 一次**回滚演练**记录（回滚到上一版本或说明为何只需回滚体验版）。

## 3. 技术架构

| 层 | 选型 | 说明 |
|---|---|---|
| 跨端框架 | **uni-app（Vue3 + TypeScript + Vite）** | `uni-app` CLI 工程，条件编译区分 H5 / 微信小程序 |
| UI | uni-ui + 自写 rpx 样式 | 一套页面两端口径，rpx 适配 |
| 小程序端 | 微信小程序（mp-weixin） | 云开发云函数代理请求，规避未备案域名 |
| 云函数 | **Node.js 20** 运行时 | 云函数收前端请求，转调后端 RESTful API |
| 后端 | 复用已有 Spring Boot 骨架（#7 SaaS 工作流） | 只加预约相关 3 个接口，不新起一套服务 |
| 数据库 | **MySQL 8**（预约单/套餐/用户） | 已有 MySQL 实例，新增 3 张表 |
| 缓存 | **Redis** | 套餐列表缓存 + 提交防重（手机号+日期幂等键） |
| 消息 | **RabbitMQ** | 预约成功投递一条「待确认」消息，消费者写日志表（模拟通知） |
| H5 端 | uni-app H5 构建 + Nginx | 与小程序同一套组件，验证移动端 H5 与响应式布局 |
| 接口风格 | **RESTful API**（JSON） | 统一 `code/message/data` 包装，前端统一拦截 |
| 发布 | 微信开发者工具 / 小程序管理后台 | 体验版 → 提审 → 发布 → 回滚 |

**明确不做**：Taro（已由 react-taro-microfrontend 覆盖）、qiankun 微前端、React 在本项目不写业务代码（React 生态由 react-taro-microfrontend 与 G8 的 React Native 项目覆盖，本设计书只在技术选型对照里提及）、支付与退款、企业主体电商类目、多门店排期算法、原生 App 壳。

## 4. 硬骨头模块（P0，只做这些）

### 模块 1：uni-app 工程与双端编译（0.8 人天）
- `npx degit dcloudio/uni-preset-vue#vite-ts` 初始化 Vue3 + **TypeScript** 工程
- 配置 `manifest.json`（appid、小程序 appid 占位可切）、`pages.json`（5 个页面 + tabBar）
- 条件编译：`#ifdef H5` / `#ifdef MP-WEIXIN` 处理登录方式、请求封装、样式差异
- `build:h5` 与 `build:mp-weixin` 两条命令都能出产物，H5 用 Nginx 起静态服务

### 模块 2：5 个业务页面与交互（1.2 人天）
- 页面骨架用 **HTML5** 语义结构落地（`view` 映射语义块、`scroll-view` 列表容器），H5 端核对语义标签与可访问性（label/aria）
- 样式层用 **CSS3** flex 布局 + `transform` 按压反馈 + `transition` 过渡，不用第三方 CSS 框架
- 业务逻辑用 **JavaScript（ES6）** 写：`import/export` 模块化、解构与可选链、`async/await` 处理请求
- 登录页：小程序端 `uni.login` 拿 code → 云函数换 openid；H5 端账号密码 mock 登录
- 套餐列表页：分页加载 + 下拉刷新，**响应式布局**（rpx + flex，两档屏宽不溢出）
- 套餐详情页：轮播图、标签、说明折叠
- 预约表单页：日期时段选择、表单校验、提交幂等（防重复点击）
- 我的页：预约单列表 + 状态标签
- **UI 设计稿还原**四步：Figma 标尺量间距字号 → 按 375 基准换算 rpx → 双端各跑一遍 → 与设计稿叠图比对并记录偏差清单；还原结论直接进验收材料，不靠"看着差不多"

### 模块 3：后端接口 + 云函数代理（1.2 人天）
- Spring Boot 侧新增 3 个 **RESTful API**：`GET /api/packages`、`GET /api/packages/{id}`、`POST /api/bookings`
- **MySQL** 建 3 张表（user/package/booking），booking 唯一索引 `(phone, book_date, slot)`
- **Redis**：套餐列表缓存 5 分钟；提交前 `SETNX booking:{phone}:{date}:{slot}` 防重
- **RabbitMQ**：预约成功 publish `booking.created`，消费者落 `notify_log` 表
- **Node.js** 云函数 `apiProxy`：接收小程序请求 → 校验参数 → 用内网/公网地址转调 RESTful API → 统一错误码；覆盖**客户端与服务器通信**链路（签名、超时、重试 1 次、失败降级提示）
- **网络编程**要点落到代码里：HTTP 方法/状态码映射（4xx 参数错、5xx 服务错）、请求头签名、连接超时与重试、弱网下的降级提示；文档里写清一次完整请求的报文样例

### 模块 4：微信小程序提审发布闭环（0.8 人天，本项目的真正增量）
- 小程序账号：主体类型与**服务类目**确认（个人主体走「工具/生活服务-预约」可行类目，避开需要企业资质的电商交易类目），类目证明材料准备清单
- **隐私协议**配置：用户信息、手机号、位置权限逐项声明，`__usePrivacyCheck__` 接入
- 服务器域名：未备案场景走**云开发**调用；同时在文档里写清「有备案域名时如何切回 request 合法域名」
- 体验版：上传代码 → 设为体验版 → 添加体验成员 → **真机扫码预览**并截图
- 提审：版本描述、功能页面截图、测试账号（H5 侧提供 demo 账号），提交审核
- 审核：记录审核时长、驳回原因（若有）、修改点、二次提审
- 发布：全量发布，记录版本号与时间，线上扫码验证
- 回滚：管理后台回滚到上一版本（或说明体验版回滚流程），留操作截图

### 模块 5：对比文档与验收材料（0.5 人天）
- 双端差异表：登录、请求、样式、能力（分享/支付）逐项对照
- **浏览器兼容性**对照：Chrome、微信内置浏览器、移动端 Safari 三档跑同一 H5，记录滚动、安全区、字体渲染差异与修法
- 运行手册：本地起 H5、起小程序、云函数部署、提审步骤
- 验收截图集：真机体验版、审核记录、线上版本、回滚记录

## 7. 面试三问（本项目要能答出来的三个问题）

1. **uni-app 一套代码两端，差异到底在哪？** 条件编译怎么切（登录、request、分享、样式单位），哪些能力小程序没有、H5 没有；rpx 与 px 换算、安全区怎么处理。
2. **小程序为什么卡域名，你怎么绕的？** 未备案域名不能用 request 合法域名 → 云函数代理的原理与代价（多一跳、云函数冷启动、配额）；有备案域名时如何切回直连。
3. **提审最容易卡在哪？** 类目与主体资质、隐私协议与实际采集不一致、页面功能不完整、测试账号不可用；你被驳回过什么、怎么改的、多久过审。

## 8. 主动砍掉项

| 砍掉 | 原因 |
|---|---|
| 支付/退款/订单核销 | 需要企业主体与支付资质，与「证明小程序发布能力」无关 |
| 真实短信与消息推送 | 需要签名模板与费用，RabbitMQ 消息落库已能证明消息链路 |
| 商家后台/排期算法 | 超出 MVP，属另一个业务方向 |
| Taro / qiankun 微前端 | 已由 react-taro-microfrontend 覆盖，重复做算撞车 |
| React 业务代码 | 由 G2 与本轮 G8 的 React Native 项目覆盖，本项目不硬编 React 经验 |
| 图片上传与内容安全审核 | 需要云存储与审核接口，收益低 |
| iOS/Android 原生壳 | 不是小程序能力，属 G8 范围 |

## 9. 风险点

| 风险 | 影响 | 应对 |
|---|---|---|
| 小程序主体资质/类目不符 | 无法提审或审核驳回 | 先选个人主体「工具类/预约服务」可行类目；材料清单提前准备；驳回则按原因整改二次提审并留记录 |
| 无备案 HTTPS 域名 | request 合法域名无法配置 | 主线走云开发云函数代理；文档写清直连方案作为对照 |
| 审核周期 1–3 天，可能跨多日 | 阻塞项目收尾 | 提审后先做文档与 H5 验收，审核结果回来再补发布截图 |
| 微信开发者工具需扫码登录 | 自动化受限 | 人工步骤明确列出，截图留证 |
| 云函数冷启动慢 | 首屏接口偶发 >1s | 加 Redis 缓存与前端骨架屏，指标按 P95 记录 |
| 与 G2 技术栈重叠被判撞车 | 立项重复 | 已划清：本项目不写 Taro、不写微前端、不含 React 生产代码，增量只在 uni-app + 真机 + 发布闭环 |

## 11. 数据模型

| 表 | 关键字段 | 说明 |
|---|---|---|
| `user` | id, openid, phone, nickname, created_at | 小程序 openid 与 H5 账号共用一张表 |
| `package` | id, title, price, cover_url, tags, status | 4 条种子数据 |
| `booking` | id, user_id, package_id, book_date, slot, contact, remark, status, created_at | 唯一索引 `(phone, book_date, slot)` 保证幂等 |
| `notify_log` | id, booking_id, event, consumed_at | RabbitMQ 消费落库 |

Redis key：`pkg:list`（5 分钟 TTL）、`booking:{phone}:{date}:{slot}`（SETNX，10 分钟 TTL）。
