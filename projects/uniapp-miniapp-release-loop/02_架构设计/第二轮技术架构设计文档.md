## 5. 数据模型（修订部分）

表结构沿用第一轮 §5；修订：

1. **R-02 幂等键值改为哈希**：`ub:idem:booking:{sha256(phone|date|slot)[:32]}`，避免 key 里出现手机号（日志/审计泄露风险）。
2. **R-03 缓存 key 改单 key + 内存分页**：
   - `ub:pkg:list` → `string(JSON)`，存全部上架套餐数组（本 MVP 仅 4 条，整表缓存），TTL 300s；
   - 分页在服务层内存切片（`page/size` 参数不参与 key），避免页数膨胀稀释命中率；
   - 回源逻辑：miss → 查 DB → 写 `ub:pkg:list`；detail 读同一份缓存切片，不再单独缓存 `pkg:detail:*`；
   - 命中率口径（写入测试用例）：`INFO stats` 的 `keyspace_hits/keyspace_misses` 取**请求前后两次读数的差值**，样本 = 同参 20 次列表请求，目标 >80%。
3. 新增审计字段（P2 落地，便于 8 步排查）：`booking.created_at` 已有，补 `booking.updated_at DATETIME ON UPDATE CURRENT_TIMESTAMP`。
4. `package.tags` 保持逗号分隔字符串（P2-04 记录为可接受）。

Redis key 终表：

| key | 类型 | TTL | 用途 |
|---|---|---|---|
| `ub:pkg:list` | string(JSON) | 300s | 套餐全量缓存（C04） |
| `ub:idem:booking:{hash}` | string | 600s | 幂等键 |
| `ub:nonce:{nonce}` | string | 120s | HMAC 重放去重（R-08） |
| `ub:jwt:blacklist:{jti}` | string | 至 token 失效 | 登出踢人（R-08） |

## 6. 接口规范（修订部分，其余沿用第一轮 §6）

1. **R-02 POST /api/bookings 返回**：`{bookingId, status, duplicated}`；`duplicated=true` 时 HTTP 仍 200、`code=0`，前端展示"这是你的同一笔预约（单号 xxx）"。**取消 42901 作为"重复提交"的主路径**（42901 只保留给"频率过高"限流）。
2. **R-06 契约产物**：后端暴露 `/v3/api-docs`；`scripts/export_openapi.ps1` 拉取并落 `06.5_契约/openapi.json`；契约基线 = 5 接口 + 统一包装 + 3 头（`Authorization`/`X-Sign`+`X-Timestamp`+`X-Nonce`）。
3. **R-08 请求头新增 `X-Nonce`**（32 字符随机），后端校验：时间窗 ±60s 且 `SETNX ub:nonce:{nonce}` 成功，否则 40102。
4. 新增 `POST /api/auth/logout`（写 `ub:jwt:blacklist:{jti}`），用于演示"踢人"与 C14 越权用例。

## 8. 监控与运维（修订：P95 采样脚本）

**R-04 `scripts/latency_probe.py`**：
- 前置：`/actuator/health` = UP；预热一次 `GET /api/packages`（不算样本）。
- 循环 20 次 `POST /api/bookings`（每次用不同手机号避免幂等命中），记录 `t_client`（本机 `time.perf_counter`）与响应头 `Server-Timing: app;dur=`。
- 第 1 次标 `cold=true` **不计入 P95**（单独列为冷启动观测值）。
- P95 = 19 个有效样本按 nearest-rank 取第 ⌈0.95×19⌉ = 第 18 个值（升序）。
- 输出 `05_代码/backend/evidence/latency.csv` + `08_测试/性能测试报告.md` 的数据段；超 800ms 时退出码 1（`scripts/check_metrics.py` 判据）。
- 其余监控项沿用第一轮 §8。

## 10. 测试架构（R-07 新增）

```
08_测试/qa-automation/
├─ conftest.py            # base_url / auth_headers / clean_booking / sample_phone
├─ unit/                  # 纯函数与校验器（≥5 例）
├─ api/                   # 5 接口正反例（≥10 例）
├─ contract/              # 契约一致性（openapi 对照，≥2 例）
├─ e2e/                   # 登录→列表→详情→预约→我的（≥3 例）
└─ allure-results/        # Allure 结果
```

- `base_url` 由环境变量 `BASE_URL` 注入，默认 `http://127.0.0.1:8092`；`auth_headers` 自动登录取 JWT。
- 数据隔离：每用例独立手机号 `1380013{序号:04d}`，前置清该手机号的 `booking` 行（SQL）后断言。
- 幂等用例：同手机号同日同时段连发 3 次 → 断言 3 次 `bookingId` 相同且 `duplicated` 第 2/3 次为 true，DB 计数 = 1（C05 新版口径）。
- 消息用例：发 10 单 → 断言 `notify_log` = 10（C06）。
- 门槛：`pytest -q` 0 failed / 0 error；Allure 报告落 `08_测试/allure-report/`。

## 11. 安全机制（R-08 修订）

| 项 | 机制 |
|---|---|
| 密钥 | `APP_SECRET`（HMAC）与 `JWT_SECRET`（令牌）分开；90 天轮换；只在 `.env` / 云函数环境变量 |
| 重放 | `X-Timestamp` ±60s + `X-Nonce` 唯一（`ub:nonce:{nonce}` TTL 120s SETNX） |
| 鉴权 | JWT HS256 + `jti`；登出写黑名单（TTL = 剩余有效期） |
| 依赖漏洞 | `npm audit --audit-level=high`（0 high/critical）；Maven `dependency-check-maven`（CVSS ≥7 为 P0/P1） |
| 渗透用例（8.5 固定 6 条） | ① 无 token 写接口→401；② 用 A 的 token 读 B 的单→403；③ `contact` 注入 `' or 1=1`→参数校验拒绝；④ `bookDate=2099-01-01`→400；⑤ 2MB body→413/400；⑥ `Content-Type: text/plain`→400 |
| 其余 | secrets 扫描（`prepush_check.py`）、CORS 仅 dev、错误信息不回显堆栈 |
