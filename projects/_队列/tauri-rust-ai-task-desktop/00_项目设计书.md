# 项目设计书 · tauri-rust-ai-task-desktop（Tauri 2 + Rust 桌面 AI 任务工作台）

> 目的：补 JD 缺口——对口杭州镜跃网络「桌面软件开发工程师（Rust/Tauri/React/AIGC）」岗，证明能写 Rust（ownership/异步/错误处理）、能做 Tauri 2 桌面应用的 Rust 后端服务、API 与数据库建模存储层，并落地 AI 生成任务的执行、状态反馈与异常恢复。
> MVP 原则：不做复杂影视编辑，业务从简，硬骨头集中在 Rust 语言能力 + Tauri 后端分层 + 异步任务状态机这三个 JD 要的点上。

## 1. 项目一句话定位

基于 Tauri 2 + Rust（Tokio + rusqlite + thiserror）实现一个本地桌面 AI 任务工作台：前端提交 AI 生成任务，Rust 后端入库并在 Tokio 后台异步执行，经 IPC 推送状态反馈，失败自动指数退避重试，重启后从 SQLite 恢复未完成任务；前端用 TypeScript + React 最简界面对接 IPC。

## 2. 业务场景（MVP 最小可用场景，必须能做完）

- 目标岗位：桌面软件开发工程师（AIGC 影视创作桌面软件方向）
- 类比业务：影视创作工具里的「AI 生成任务中心」——用户提交一个文本/图像类生成任务，工具后台执行、回传进度与结果、失败可重试、关掉重开任务不丢。
- 最小可用闭环：用户在界面填写任务描述、选择模型 → 点提交 → Rust 后端把任务写入 SQLite → Tokio 后台异步执行（调用 OpenAI 兼容接口，可切 Mock）→ 状态由 pending → running → succeeded / failed 经 IPC 实时推到界面 → 失败自动重试 ≤3 次 → 重启应用后，上次中断的 running/interrupted 任务被扫描恢复。

**做完这件事，项目就算成了。** 不做素材管理/分镜时间轴/媒体剪辑，不做图像视频音频真实生成，不做多用户与云同步。

## 2.5 现有基础与缺口对照

- 已有可复用：#10 Schedule Pilot（Tauri v2 表层经验：27 个 IPC、Mutex 并发、Serde、JSON 文件持久化、托盘轮询）；#8 wf CLI（AI 编程工具与生成代码审查）；#7（前端工程化与接口对接）。
- 本项目要补的 Rust 硬缺口：ownership/借用/生命周期、Tokio 异步任务、Result/thiserror 错误处理体系、Rust 侧数据库建模与存储层、Rust 调 AI 模型服务的任务状态机。
- React 系统化实操由队列另一项目 `react-taro-microfrontend` 覆盖；本项目前端只做 React + TypeScript 最简界面，不展开跨端/微前端。

## 3. 技术架构（分层）

```
┌─────────────────────────────────────────────┐
│ 前端（React 18 + TypeScript + Vite）         │
│  任务列表 / 提交表单 / 状态徽标 / 重试按钮     │
└───────────────┬─────────────────────────────┘
                │ Tauri IPC（Command 调用 + 事件推送）
┌───────────────▼─────────────────────────────┐
│ Rust 后端（Tauri 2 Command 层）               │
│  ├─ command 层：参数校验、IPC 暴露、事件广播    │
│  ├─ service 层：任务状态机、重试、恢复编排      │
│  ├─ repository 层：rusqlite 任务表读写          │
│  └─ provider 层：reqwest 调 OpenAI 兼容接口    │
├─────────────────────────────────────────────┤
│ 存储：SQLite（rusqlite） tasks 表 + 元数据     │
│ 运行时：Tokio（async/await、spawn、mpsc 通道） │
└─────────────────────────────────────────────┘
```

- 分层：Command 层只做参数校验与编排，业务逻辑下沉 service，数据访问收敛到 repository，对齐 #10 的 Command-Service-持久三层但补全 Rust 工程规范。
- 并发模型：Tokio 后台任务执行器，mpsc 通道把状态变更发到 IPC 事件总线；前端通过事件订阅刷新。
- 存储：本地 SQLite 单文件，任务全量持久化，支撑重启恢复。

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 | **Rust 2021 edition** | ownership/借用/生命周期、Result 错误处理 |
| 桌面框架 | **Tauri 2** | IPC Command、事件、窗口打包 |
| 异步运行时 | **Tokio** | async/await、task::spawn、mpsc 通道、超时 |

| 工程化 | Git、Cargo、Tauri CLI | 版本管理、单元测试、Windows 打包 |

## 4. 硬骨头模块（P0 核心模块，真正花时间的地方）

### 模块 1：Rust 工程骨架与分层（1d）
- Tauri 2 初始化 Rust 工程，拆 command / service / repository / provider 模块目录
- 明确 ownership 边界：Command 层持有状态句柄，service 接收 owned 数据，repository 持有数据库连接；梳理借用与生命周期标注，消除拷贝
- 统一 AppState 结构，通过 Tauri manage 注入各 Command

### 模块 2：SQLite 数据建模与存储层（1d，**硬骨头**）
- rusqlite 建 tasks 表：id、task_type、payload(JSON)、status、result、error、attempts、created_at、updated_at
- 写 DAO 层：创建任务、按 id 更新状态/结果/错误、查询列表、扫描中断任务
- 简单迁移：首次启动建表，字段缺失时补列；连接串行化访问，避免并发写冲突
- 用 Rust 类型（struct + Serde）映射行记录，演示 ownership 与序列化

### 模块 3：Tokio 异步任务执行器与状态机（1.5d，**主项目亮点**）
- 任务状态机：pending → running → succeeded / failed；失败进入 retrying → 重试 N 次后 failed
- 提交任务后 `tokio::spawn` 后台执行，mpsc 通道把状态变更发回，Command 层 `emit` IPC 事件推给前端
- 调用 provider 层执行生成任务，带超时控制；结果/错误落库后广播最终状态
- 任务取消：提供取消信号（CancellationToken 或 AtomicBool），取消后状态落为 interrupted

### 模块 4：Rust 错误处理体系（0.5d，**硬骨头**）
- thiserror 定义 AppError 枚举：Db(rusqlite::Error)、Http(reqwest::Error)、Provider(业务错误)、Serialize、Canceled 等
- 全链路 Result 传播，Command 层把错误转成可跨 IPC 序列化的结构化错误码 + 消息
- 错误分类：可重试（网络/超时/限流）vs 不可重试（参数/鉴权/业务拒绝），驱动重试策略

### 模块 5：AI 模型调用适配层与异常恢复（1d）
- provider  trait 抽象：`trait Provider { async fn generate(&self, req) -> Result<Output> }`，OpenAI 兼容实现 + Mock 实现可切换
- reqwest 调 OpenAI 兼容 chat/completions，超时、错误映射到 AppError
- 异常恢复：启动时扫描 SQLite 中 running/retrying/interrupted 任务，重置为 pending 重新入队；失败任务指数退避重试 ≤3 次
- 前端可手动触发重试，重试次数与错误原因落库可见

### 模块 6：前端最简界面与联调（0.5d）
- React 18 + TypeScript：任务列表、提交表单、状态徽标（待执行/执行中/成功/失败/重试中）、重试按钮
- 订阅 Tauri 事件刷新列表，调用 Command 提交/重试任务
- 不做复杂样式与路由，界面够用即可

### 硬骨头难点说明
1. **ownership/借用/生命周期**：状态句柄、数据库连接、任务 payload 在模块间传递时，想清楚谁持有所有权、哪里只借引用；生命周期标注消除悬垂引用——这是 JD 第 4 条 Rust 基础的硬证据。
2. **Tokio 异步与线程模型**：后台任务、mpsc 通道、Tauri 主线程与 WebView 通信怎么衔接；spawn 的任务持有什么状态、怎么取消——对比 #10 里同步轮询的做法。
3. **错误处理设计**：自定义错误枚举怎么覆盖 DB/HTTP/Provider 各类失败，怎么跨 IPC 不丢失错误信息，怎么区分可重试与不可重试。
4. **数据库建模与一致性**：任务状态迁移与落库顺序，并发写同一任务时如何避免状态脏写，重启恢复如何判定中断任务。

## 7. 面试三问

1. **讲一个 Rust ownership/借用约束帮你避免问题的例子**：任务 payload 或数据库连接在 command/service/repository 间传递时，哪里需要 owned、哪里用借用引用，生命周期标注怎么定，避免了哪类拷贝或悬垂引用。
2. **Tokio 后台任务和 WebView 线程怎么通信？任务取消/重启怎么处理？**：mpsc 通道 + Tauri 事件广播；取消信号怎么传；重启后如何从 SQLite 扫描中断任务恢复。
3. **任务状态机怎么设计？失败重试与异常恢复怎么做？**：pending/running/retrying/succeeded/failed/interrupted 迁移规则；可重试 vs 不可重试错误分类；指数退避次数上限；状态与结果落库顺序。

## 8. 主动砍掉项（P0 不做，以后再说）

- ❌ 不做图像/视频/音频真实生成：只接 OpenAI 兼容文本 chat 接口，多媒体 provider 留 Mock 接口位
- ❌ 不做多用户、账号体系与云同步：本地单机 SQLite
- ❌ 不做素材管理、分镜时间轴、媒体剪辑等产品功能：本项目只做 AI 任务工作台骨架
- ❌ 不做 React 跨端/小程序/微前端：React 系统化由 `react-taro-microfrontend` 项目覆盖
- ❌ 不做 K8s/多机部署、不做模型训练或微调
- ❌ 不做复杂权限与团队协作功能

## 9. 风险点（结论与兜底）

- **Rust 编译学习曲线**：ownership/生命周期/异步编译报错较多。兜底：借助 Cursor/Claude Code 分步攻克，按模块小步提交，先过编译再补逻辑；每模块配 cargo test 锁定行为。
- **网络与模型接口**：国内网络访问外部模型接口可能不稳。兜底：provider 抽象出 Mock 实现，断网也能跑通全链路状态机。
- **Tauri 2 API 版本变动**：以官方 v2 文档为准，遇到 API 差异及时查源码与英文文档（对应 JD 第 7 条阅读英文文档要求）。
- **结论**：硬件无压力（Tauri/Rust/SQLite 本地均可运行，不占显卡），5.5 人天可出 MVP；完成后 Rust must_have 与 Tauri 后端/数据库建模缺口即可覆盖，配合 react-taro-microfrontend 补齐 React 后，镜跃岗 must_have 可达 100%。
