# 项目设计书 · cpp-game-server-kit（现代 C++ 游戏服务器基础设施套件）

> 目的：补 JD 缺口——对口杭州游梦光年「初级 C++ 游戏服务端开发」岗，证明能写现代 C++（C++17/20）、懂 epoll/无锁/内存模型、能做游戏服务器。
> MVP 原则：不做完整游戏，做一个可跑通的"网络库 + 日志 + 网关 + 战斗服 + 压测"五件套，简历上写一个主项目，五个模块都是自研技术亮点。

## 1. 项目一句话
基于 C++20 + epoll + KCP 的轻量级游戏服务器基础设施套件，包含自研 Reactor 网络库、无锁异步日志、Protobuf 登录网关、KCP 帧同步战斗服四件套，单机支撑 5000 长连接。

## 2. MVP 最小可用场景（必须能做完）
两个命令行客户端同时启动 → 连上网关 → 用 Protobuf 发登录包（MySQL 校验账号）→ 网关在 Redis 写登录态 → 客户端进同一个战斗房间 → 战斗服用 KCP 协议广播帧同步消息 → 任一客户端断线 3 秒内重连并恢复房间状态。

**做完这件事，项目就算成了。** 不做游戏逻辑（不做战斗数值/匹配/支付/商城/GM后台），不做跨服，不做前端，只做服务端基础设施。

## 2.5 业务场景
- 目标公司：20-99 人小游戏厂，自研 C++20 游戏服务器框架
- 目标岗位：初级 C++ 游戏服务端开发
- 业务类比：一个简易 MOBA/自走棋房间的服务端骨架——玩家登录、建房、帧同步、断线重连，不做战斗数值
- 为什么选这个场景：业务极简，硬骨头全在"网络/并发/性能"这三个 JD 要的点上，不浪费时间写业务

## 2.6 技术架构（分层）
```
┌─────────────────────────────────────┐
│  客户端（自研 tcp_client 压测脚本）    │
└──────────────┬──────────────────────┘
               │ TCP (Protobuf) / KCP
┌──────────────▼──────────────────────┐
│  模块 C: game-gateway 登录网关        │
│  ├─ Protobuf 编解码 + 粘包分包        │
│  ├─ MySQL users 校验                 │
│  └─ Redis session 写入                │
├──────────────────────────────────────┤
│  模块 D: kcp-battle-room 战斗服       │
│  ├─ 房间管理（Redis 成员列表）        │
│  ├─ KCP 帧同步广播（C++20 协程）      │
│  └─ 断线重连（Redis 房间快照）        │
├──────────────────────────────────────┤
│  模块 A: cpp-reactor-net 自研网络库   │
│  ├─ epoll 多路复用（LT 模式）         │
│  ├─ one-loop-per-thread 线程池       │
│  └─ 非阻塞读写缓冲区                  │
├──────────────────────────────────────┤
│  模块 B: lockfree-logger 无锁日志     │
│  ├─ SPSC 无锁环形队列（std::atomic） │
│  └─ 后台线程批量刷盘                 │
└──────────────────────────────────────┘
```
- 网络模型：epoll 多路复用，one-loop-per-thread（对比过 IOCP，Linux 下用 epoll）
- 并发模型：主线程 accept，worker 线程池各跑一个 epoll loop，日志用无锁队列跨线程传
- 存储：MySQL 持久化用户，Redis 做会话/房间热数据

## 3. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 | **C++17/20**（GCC 11+，WSL2 Ubuntu） | RAII / 移动语义 / std::variant / std::optional / 结构化绑定 / concepts |
| 网络 | **epoll（LT 模式起步）** + **libkcp 源码包入仓** | 自研 Reactor，不依赖 muduo/boost.asio |
| 序列化 | **Protobuf v3** | 登录包/房间包/帧同步包 |
| 并发 | std::thread + 自研线程池 + std::atomic 无锁队列 | 不引入 libco/boost.coroutine，用 C++20 协程做战斗服 |
| 数据库 | MySQL 8（mysql-connector-cpp） | users 表 |
| 缓存 | Redis（hiredis 同步封装） | 登录态/房间成员 |
| 构建 | CMake 3.20+ | find_package 找 protobuf/hiredis/mysql |
| 调试 | GDB / Valgrind / AddressSanitizer / perf | 每个模块都要过一遍 ASan |
| 部署 | WSL2 直接跑（不做 Docker，游戏服务器默认 Linux） | |

**明确不做**：游戏业务逻辑（伤害计算/技能/BUFF）、前端、Web 管理后台、跨服分布式、容器编排、微服务拆分（单进程多线程即可）。

### 主动砍掉项（P1 不做，以后再说）
- ❌ 不做 muduo/boost.asio 对比版——只手写一份 epoll，证明自己懂原理就行
- ❌ 不做 SSL/TLS 加密——内网测试不需要
- ❌ 不做 WebSocket——游戏用自定义 KCP/TCP 协议
- ❌ 不做 HTTP/REST——全是长连接游戏协议
- ❌ 不做跨服分布式——单进程多线程够支撑 5000 连接演示
- ❌ 不做游戏匹配/战斗数值/技能系统——那是策划的活，本项目只做基础设施
- ❌ 不做 Docker 部署——游戏服务器默认 Linux 裸跑，WSL2 直接跑
- ❌ 不做 gRPC——Protobuf 手写 RPC 足够

## 4. 核心模块（P0，只做这些）

### 模块 A：cpp-reactor-net（自研 epoll Reactor 网络库，1.5d）
- 非阻塞 socket + epoll LT 模式 + one-loop-per-thread 线程池
- 读写缓冲区（std::vector<char>，自动扩容）
- RAII 封装 fd（析构自动 close，演示 RAII）
- 事件回调用 std::function + std::any 存上下文（演示现代 C++）
- 自带 Echo Server 示例

### 模块 B：lockfree-logger（无锁异步日志，1d）
- SPSC 无锁环形队列（std::atomic + memory_order_relaxed/acquire/release，手写不依赖 moodycamel）
- 后台单线程批量刷盘
- 前端日志接口用 RAII 封装文件句柄、移动语义接管缓冲区
- C++17 fold expression 写格式化
- ASan/Valgrind 跑零泄漏

### 模块 C：game-gateway（Protobuf 登录网关，1.5d）
- 在模块 A 的 Reactor 上加 Protobuf 编解码层
- 粘包分包：4 字节包头 + Protobuf body
- 登录流程：收 LoginReq → 查 MySQL users 表 → 校验密码 → Redis 写 session → 回 LoginRsp
- 网关维护 fd ↔ uid 映射表

### 模块 D：kcp-battle-room（KCP 战斗服 + 帧同步，2d，**主项目**）
- 把 libkcp 源码放进 third_party/，在模块 A 的网络层加 KCP 传输层
- 房间管理：创建房间/加入房间/离开房间，房间成员列表存 Redis
- 帧同步：客户端每 100ms 上报操作输入 → 战斗服广播给房间内所有人
- 断线重连：Redis 存房间快照，重连时拉取
- 用 C++20 协程（stackless coroutine）写广播逻辑，避免回调嵌套

### 模块 E：perf-report（压测与调优，0.5d）
- 自研一个 tcp_client 压测脚本，打模块 A 的 Echo Server
- perf top 找热点，对比 std::string vs std::string_view、std::vector 预分配前后 QPS
- ASan/Valgrind 跑一遍全项目，贴零 warning 截图
- 写一份《性能调优报告.md》：QPS 从 X 提到 Y，瓶颈在哪，怎么改的

### 硬骨头模块（真正花时间的地方）
1. **模块 B 无锁队列**：手写 SPSC 环形队列，要彻底搞懂 C++ 内存模型（memory_order_relaxed / acquire / release / acq_rel / seq_cst）、内存屏障、伪共享（false sharing）对齐。这是 JD 第 4 条硬要求，写对了面试能聊 20 分钟。
2. **模块 A epoll 多路复用**：LT vs ET 模式、非阻塞 socket 边缘触发、惊群问题、one-loop-per-thend 的负载均衡——不直接抄 muduo，自己写一遍才懂。
3. **模块 D KCP 集成**：把 libkcp 源码接进 epoll 事件循环，处理 KCP 的 update 定时器、收发缓冲区对齐——KCP 是游戏服务器抗丢包的标配。
4. **模块 E 性能调优**：用 perf top 找热点，定位到具体哪一行 std::string 在拷贝，改用 string_view / 预分配 vector / move 语义，把 QPS 提上去。这是"内存/CPU/网络 IO 性能调优"的硬证据。

> 多线程编程、锁机制在模块 A/B 里自然出现：模块 A 线程池用互斥锁保护 fd 映射表，模块 B 用无锁队列避免锁竞争，正好对照"有锁 vs 无锁"两种方案。游戏服务器框架设计就是模块 A→B→C→D 这四层分层本身。7x24 线上运维与故障排查体现在模块 E 用 ASan/Valgrind 定位内存问题的流程。

## 6. 数据模型

- MySQL `users`：id BIGINT PK, username VARCHAR(64) UNIQUE, password_hash VARCHAR(128), created_at DATETIME
- Redis：
  - `session:{uid}` → token string，TTL 2 小时
  - `room:{room_id}` → hash: {uid_1: ready, uid_2: ready, ...}
  - `room:{room_id}:frame` → list，存最近 100 帧操作输入
