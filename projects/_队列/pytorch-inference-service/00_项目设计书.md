# 项目设计书 · pytorch-inference-service（PyTorch 模型微调 + ONNX 推理部署服务）

> 目的：补 JD 缺口——证明"会用 PyTorch 做模型微调 + 导出 ONNX + 包装成推理服务"，对口宇佐智能/绍兴猫草。
> 硬件约束：RTX 2050 4GB 显存 → 冻结 BERT backbone 只微调分类头，batch size=8 + gradient accumulation，不做全参微调。

## 1. 项目一句话
用 PyTorch + HuggingFace Transformers 微调 BERT-base-chinese 中文文本分类模型（冻结 backbone 只训练分类头），导出 ONNX 格式，用 FastAPI 包装成推理 HTTP 服务，Docker Compose 部署，压测推理延迟和 QPS。

## 2. MVP 最小可用场景（必须能做完）
下载 ChnSentiCorp 中文情感分类数据集 → 跑微调脚本（冻结 BERT backbone，只训练最后一层分类头，GPU 跑 2-3 epoch）→ 评估准确率/F1 → 导出 ONNX → 启动 FastAPI 服务 → POST /predict 传入一段文本 → 返回分类结果（正面/负面）+ 置信度 → 对比 PyTorch 原版和 ONNX Runtime 的推理速度。

**做完这件事，项目就算成了。** 不做大模型微调（LoRA/QLoRA）、不做多标签分类、不做前端页面、不做 MLOps 平台（MLflow/Kubeflow）。

## 3. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 深度学习框架 | **PyTorch 2.x** | 冻结 backbone，只训练分类头 |
| 预训练模型 | **BERT-base-chinese**（HuggingFace Transformers） | 110M 参数，4GB 显存可推理 |
| 微调方式 | **冻结 backbone + 只训分类头** | batch=8, grad_accum=4, lr=2e-5 |
| ONNX | **ONNX Runtime** | 导出模型对比推理速度 |
| Web 框架 | **FastAPI** | POST /predict 推理接口 |
| 数据集 | ChnSentiCorp（中文情感二分类） | HuggingFace datasets 直接加载 |
| 评估 | scikit-learn（accuracy/F1） | 微调后跑评估脚本 |
| 压测 | locust 或 JMeter | 测推理延迟 P50/P99 和 QPS |
| 部署 | Docker Compose | fastapi + onnxruntime 容器 |

**明确不做**：全参微调/LoRA/QLoRA（4GB 显存跑不动）、大语言模型微调、模型训练分布式、前端可视化面板、MLflow 实验追踪。

## 4. 核心模块（P0，只做这些）

### 模块1：数据准备与预处理（0.5d）
- 用 HuggingFace datasets 加载 ChnSentiCorp 数据集（约 1.2 万条中文评论）
- 文本预处理：用 BERT tokenizer 做 encode_plus，padding/truncation 到 max_len=128
- 划分 train/val/test（8:1:1）
- 封装成 PyTorch DataLoader

### 模块2：BERT 微调脚本（1.5d，**核心**）
- 加载 bert-base-chinese 预训练模型
- **冻结 BERT backbone 参数**（requires_grad=False），只加一个 Dropout + Linear 分类头（768→2）
- Trainer API 训练 2-3 epoch（batch=8, grad_accum=4, lr=2e-5, weight_decay=0.01）
- GPU 4GB 显存约束：max_len=128, batch=8, gradient_checkpointing=True
- 保存微调后的模型权重到 output/

### 模块3：ONNX 导出与对比（0.5d）
- 用 torch.onnx.export 把微调后的模型导出为 ONNX 格式
- 写对比脚本：同一批输入分别用 PyTorch 和 ONNX Runtime 推理
- 记录：单条推理延迟（ms）、吞吐 QPS、结果一致性验证

### 模块4：FastAPI 推理服务（1d）
- POST /predict：入参 {text: string}，出参 {label: "正面"/"负面", confidence: float}
- 启动时加载 ONNX 模型到内存（不每次请求重新加载）
- 健康检查 GET /health
- 请求日志：记录推理耗时

### 模块5：压测与 Docker 部署（0.5d）
- locust 压测：10/50/100 并发用户，测 P50/P99 延迟和 QPS
- Dockerfile：python:3.11-slim + 依赖 + ONNX 模型
- docker-compose.yml 一键起服务
- 写 README：如何微调、如何导出、如何启动服务、压测结果数据

## 5. 量化基线指标

| 编号 | 指标 | 验证方式 |
|---|---|---|
| M1 | 微调后验证集准确率 ≥ 85%（ChnSentiCorp baseline 约 90%） | 跑评估脚本输出 accuracy/F1 |
| M2 | ONNX 导出成功，PyTorch 和 ONNX Runtime 推理结果一致（差值 < 0.01） | 对比脚本验证 |
| M3 | ONNX Runtime 单条推理延迟比 PyTorch 原版降低 ≥ 20% | 对比脚本输出延迟数字 |
| M4 | FastAPI /predict 接口能返回正确分类结果 + 置信度 | curl 手动测 |
| M5 | locust 50 并发下 P99 延迟 < 200ms（GPU 推理） | 压测报告 |
| M6 | Docker Compose 一键起服务 | docker compose up 后 curl 通 |
| M7 | 代码里有冻结 backbone、requires_grad=False、gradient_accumulation_steps 用法 | grep 训练脚本 |

## 6. 数据模型
- 数据集：ChnSentiCorp（text: string, label: 0=负面/1=正面）
- 模型文件：pytorch_model.bin（PyTorch 原版）+ model.onnx（ONNX 导出）
- 服务端：无数据库，纯推理服务，不存历史请求（可选写 CSV 日志）
