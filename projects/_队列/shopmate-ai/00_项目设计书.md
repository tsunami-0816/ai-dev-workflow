# 项目设计书 · ShopMate 电商AI客服运营工作台

## 1. 一句话定位
给电商小卖家的AI工作台：自动回复买家商品咨询、查订单物流、处理退换货，同时一键生成商品文案、看运营数据看板。

## 2. 业务场景
一个淘宝/抖音小店铺（0-20人团队），每天客服被重复问题淹没："M码腰围多少？""几天能发货？""我要退货怎么退？" 同时运营每天还要写商品标题、改详情页、做日报。

ShopMate 做两件事：
- **客服侧**：买家消息进来，AI自动识别意图（问商品/查订单/要退货），从商品知识库检索答案，查模拟订单物流，答不了的转人工并标记badcase
- **运营侧**：输入商品信息（材质/尺寸/卖点），AI生成3版标题+详情文案；看板看今天多少会话、多少解决了、哪些问题答得不好

**MVP 最小可用场景（R18）**：
买家发"这件裙子M码胸围多少？我拍的什么时候发货？" → AI从商品知识库查到M码胸围86cm → 调订单API查到已发货顺丰 → 回复"亲，M码胸围86cm哦～您的包裹已发顺丰，预计明天到～" → 买家点"已解决"或"没解决"（没解决进badcase队列）。运营打开看板看到今天120条会话、解决率82%、Top3 badcase。

## 3. 技术架构

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | Python 3.11 + FastAPI | 主服务：客服对话/文案生成/看板API |
| Agent编排 | LangGraph | 多轮对话状态机：意图识别→知识检索→API调用→回复→反馈 |
| LLM | DeepSeek API | 对话决策+文案生成，成本低 |
| 向量库 | Qdrant（Docker） | 商品知识库检索（商品详情/规格/退换货政策） |
| 业务库 | MySQL 8（共用3310，database=shopmate） | 会话/订单/商品/badcase记录 |
| 缓存 | Redis 7（共用6379，db=5） | 会话状态缓存、限流 |
| 前端 | Vue3 + TypeScript + Vite + Tailwind CSS | 聊天界面+文案生成页+数据看板 |
| 部署 | Docker Compose（3服务：backend + qdrant + frontend） | 轻量，不超5服务 |

**技术栈关键词**：Python + FastAPI + LangGraph Agent 工作流编排 + RAG 向量检索 + Qdrant + MySQL + Redis + Vue3 + TypeScript + Tailwind CSS + Docker Compose 多轮对话反馈闭环。

**端口**：后端8088，前端5182

**核心模块（P0）**：
1. **M1 智能客服对话**：聊天界面、LangGraph状态机、商品知识卡片嵌入、快捷回复按钮
2. **M2 商品知识库（RAG）**：商品文档录入、切片向量化、带引用检索回答
3. **M3 订单物流模拟**：模拟订单数据、对话中自动调用API查物流
4. **M4 商品文案生成**：输入商品信息→3版标题+详情文案、风格切换
5. **M5 运营数据看板**：会话量/解决率/badcase列表/满意度趋势
6. **M6 反馈闭环**：👍👎反馈→badcase队列→Prompt优化→自动回归对比

**量化基线指标**：
- 商品知识检索准确率（人工评审）≥ 80%
- 多轮对话上下文保持 ≥ 3轮
- 文案生成响应时间 ≤ 5s
- 看板查询（1000条会话）≤ 1s
- 客服模拟解决率 ≥ 70%
- 前端LCP ≤ 2s

## 4. 硬骨头模块

### 硬骨头1：LangGraph多轮对话状态机
- 状态节点：意图识别→知识检索→订单查询→回复生成→反馈判断
- 条件分支：查商品走RAG、查订单走API、都答不了转人工
- 多轮上下文：连续对话能记住"刚才那件裙子""我那个订单"
- **为什么难**：不是简单的prompt调用，是有状态、有分支、有工具调用的Agent流程

### 硬骨头2：RAG商品知识精准检索
- 商品文档包含表格（尺码表）、图片描述、政策条款，切片策略要考虑表格完整性
- 检索结果必须带引用，不能瞎编（"M码胸围多少"必须从尺码表切片里出答案）
- 相似度阈值过滤，答不出来就说"这个问题我帮您转人工哦"，不硬编

### 硬骨头3：反馈闭环驱动持续优化
- 👎badcase自动入库，不是手动记录
- 运营改完prompt/知识库后，badcase自动跑一遍对比（旧回答 vs 新回答）
- 解决率趋势能看到优化效果

### 硬骨头4：精致UI（R24精修模式）
- 电商温暖风格：珊瑚橙主色(#FF6B6B) + 奶白底色(#FFF8F0) + 圆角16px卡片
- 聊天界面：气泡圆角、商品卡片嵌入、快捷按钮、👍👎反馈条
- 不用Element Plus默认灰蓝色，用Tailwind自定义
- **这个是JD"含界面设计"的直接体现**

## 7. 面试三问

**为什么用LangGraph不用Coze/Dify？**
Coze/Dify是低代码平台，适合快速验证但无法精细控制状态流转和自定义工具调用逻辑。LangGraph代码实现，每个节点的prompt、分支条件、错误处理都可控，面试时能讲清楚状态机怎么跑的。核心概念（节点/边/条件分支/工具调用）和Coze是相通的，上手低代码平台很快。

**最难的问题是什么？**
多轮对话中指代消解："刚才那件裙子""我那个订单"——需要维护会话状态上下文，不能每轮独立检索。RAG检索精度：商品尺码表是表格结构，普通文本切片会破坏表格完整性，需要按表格行切片。

**再做一次怎么改？**
加真实电商平台API对接（淘宝/抖音开放平台）、加多模态图片理解、加多平台消息接入（微信/抖音/淘宝）、加定时自动化日报推送。

## 8. 主动砍掉项

| JD词 | 砍掉原因 | 面试话术 |
|---|---|---|
| Coze/Dify/n8n低代码平台 | 作品集用代码实现工作流编排更有技术深度 | "用LangGraph代码实现了，核心概念和Coze/Dify相通" |
| 音图理解（多模态） | RTX 2050 4GB跑不了本地多模态 | "聚焦文本客服，多模态了解原理，架构预留扩展点" |
| 数据抓取/竞品监控 | 小店铺场景优先级低于客服+文案 | "运营自动化做了文案生成和日报看板，抓取属于增强项" |
| 高并发压测 | 小店铺场景不需要，50路会话足够 | "做了基础响应时间验证，高并发不是这个场景核心需求" |

## 9. 风险点

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 内存不足（当前可用0.3GB） | Docker Compose起3服务可能OOM | 关闭其他项目的容器，Qdrant用轻量配置，不跑ClickHouse |
| DeepSeek API调用成本 | 多轮对话+文案生成消耗Token | 设置会话上下文窗口上限，文案生成限次，用DeepSeek便宜模型 |
| RAG检索精度不够 | 商品知识回答不准确 | 人工评审20条测试集，调整切片策略和相似度阈值 |
| UI设计超出15人天 | 前端时间不够 | 先保证功能可用，UI精修最多2轮（R24硬约束），P0功能优先 |
