# 项目设计书 · enterprise-rag-agent（企业知识库问答 Agent）

## 1. 项目一句话

企业内部文档（PDF/Word/Confluence）自动切分向量化，员工用自然语言提问，AI 返回带原文引用的答案，替代传统全文搜索。

## 2. 业务场景

新员工入职问"年假怎么算"、客服查"退款政策"、开发者搜"API限流规则"——传统搜索返回一堆文档让人自己翻，RAG Agent 直接回答+标注出处。

## 3. MVP 最小可用场景（规则18硬性要求）

> 用户做完这个项目后，能实际完成什么：
> **上传一个 PDF 文档 → 等 10 秒索引完成 → 在输入框问一个和文档内容相关的问题 → 看到回答+引用了文档哪一段。**

这是 MVP 必须 100% 完成的核心链路。其他功能（多文档管理、多轮对话、权限隔离）列为增强。

## 4. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | Java Spring Boot 3 | API 网关、文档管理、对话历史 |
| AI 服务 | Python FastAPI | 文档切分、Embedding、向量检索、LLM 调用 |
| 向量库 | Qdrant | Docker 单容器，存文档 chunk embedding |
| 业务库 | MySQL 8 | 文档元数据、对话历史、用户 |
| 前端 | Vue3 + Element Plus | 文档上传、聊天界面、引用高亮 |
| LLM | DeepSeek API | 生成回答（不本地部署模型） |
| Embedding | bge-small-zh（本地 or API） | 中文向量模型 |

## 5. 核心模块（P0 = MVP 必须完成）

| 模块 | 等级 | 说明 |
|---|---|---|
| 文档上传+切分+向量化 | **P0** | 上传 PDF → 按段落切分 → Embedding → 写 Qdrant |
| 问答接口 | **P0** | 问题 → Embedding → 向量检索 Top5 chunk → 拼 Prompt → DeepSeek 生成回答 |
| 引用来源 | **P0** | 回答中标注引用了哪个文档的哪一段（可点击展开原文） |
| 聊天界面 | **P0** | 前端对话框，历史记录，流式输出（SSE） |
| 文档列表管理 | P1 | 已上传文档列表、删除、重新索引 |
| 多轮对话上下文 | P1 | 记住上文，支持追问"那退款呢？" |
| 多租户隔离 | P2 | 不同部门只能搜自己的文档 |
| 权限控制 | P2 | 管理员/普通员工角色 |

## 6. 量化基线指标

| 指标 | 目标 | 验证方式 |
|---|---|---|
| 文档索引速度 | 10 页 PDF ≤ 10 秒 | 上传后计时 |
| 问答响应延迟 | ≤ 3 秒（含 LLM 生成） | 接口计时 |
| 检索命中率 | 测试集 20 问，Top5 含正确段落 ≥ 80% | 人工标注 |
| 并发问答 | ≥ 20 路 | 简单压测 |
| 支持文档格式 | PDF + TXT + Markdown | 逐个上传测试 |

## 7. 与现有项目差异化

| 现有项目 | 本项目差异 |
|---|---|
| smart-outbound（外呼语音） | 无语音、无实时通话，是文档问答 |
| multi-tenant-crm（工单SaaS） | 无工作流、无状态机，核心是 RAG 检索 |
| llm-eval（LLM评测，搁置） | 本项目是**使用**LLM做问答，不是评测LLM |

## 8. 硬骨头模块（面试可讲）

1. **RAG 切分策略**：固定长度切分 vs 语义切分 vs 父子分块，为什么选这个
2. **检索+重排序**：向量召回后为什么要做 rerank，怎么优化命中率
3. **Prompt 工程**：怎么让 LLM 基于给定上下文回答而不是编造
4. **SSE 流式输出**：前端怎么接流式响应

## 9. 硬件约束

- Qdrant Docker 单容器（内存占用 ~500MB，可跑）
- 不本地跑 LLM（走 DeepSeek API）
- Embedding 用 bge-small（~100MB，CPU 可跑）
- 总容器数 ≤ 4（MySQL + Qdrant + Redis + 前端）

## 10. 工作量预估

- P0 MVP：3-4 天
- P1 增强：2 天
- P2 隔离：2 天
