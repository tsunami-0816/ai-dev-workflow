## 四、P1 问题（建议在第二轮定稿中吸收，P1-1 需人工先确认）

### P1-1　模型供给默认路径未锁定，M3「≤30 秒」在无独显本地存在条件性风险
- **问题描述**：架构给出本地 Ollama 与云端 API 双方案，但未指定默认路径。普通 PC 若无 NVIDIA 独显，Qwen2.5-7B-Q4 在 CPU 上生成可能仅数~十余 token/秒，叠加 embedding/检索，端到端 30 秒可能吃紧；bge 与 7B 首次加载也占内存。
- **影响范围**：指标 M3、M4 与部署成功率；决定第 6 步冒烟能否达标。
- **严重等级**：P1（有云端兜底，不构成「肯定不达标」，但开工前必须决策）。
- **修改建议**：
  1. 第 6 步冒烟**第一个动作**做「模型时延基准测试」：用固定 5 条问题对比 本地(3B/7B) 与 云端 API 的端到端时延、答案质量；
  2. 默认策略：**强涉密/有独显 → 本地**；**普通设备/追指标 → 默认云端 API**；
  3. 明确最低硬件门槛（建议：内存 ≥ 16GB；本地 7B 建议 ≥ 8GB 显存，否则用 3B/Q4）；
  4. 基准结果如实写入 MVP 测试报告。
- **需要人工确认**：本机是否有 NVIDIA 独显、内存大小，以及对「资料是否允许走云端 API」的态度。

### P1-2　本地 Ollama 的结构化输出（分级 JSON）稳定性不足，需明确不依赖 function calling 的兜底
- **问题描述**：分级链依赖模型输出稳定 JSON；本地 Qwen 经 Ollama 的 function calling/结构化输出稳定性弱于云端，可能频发 3002。
- **影响范围**：异常分级派单链路（链路二）、M5。
- **修改建议**：分级 prompt 强制 JSON schema + 5–8 个中文分级 few-shot 示例；用 Pydantic 校验；解析失败时「重试 1 次 → 正则提取 JSON → 仍失败则 `need_ticket=true`（宁派单不硬答）」；安全类规则前置，不依赖模型自觉。

### P1-3　「派单推送」在 MVP 对负责人侧的最小闭环未定义清楚
- **问题描述**：基线排除了真实 IM 推送，但「推送给负责人」若只生成工单、负责人无感知途径，M6 工单闭环在演示中可能停在「建单」。
- **影响范围**：工单链路闭环、M6。
- **修改建议**：明确 MVP「推送 = 负责人角色视图的待处理工单列表（按时间倒序、未处理高亮/角标、Streamlit 自动刷新）」；在测试报告中注明「系统内通知，不含钉钉/企微/飞书真实推送」；接口层预留 `notify` 扩展点。

### P1-4　纯向量检索对设备型号/故障代码等专有名词召回偏弱，关系 M4 达标
- **问题描述**：设备型号、故障代码、仪表编号是强专有名词，纯语义向量易漏召回；仅靠 rerank 属于事后补救。
- **影响范围**：M4 准确率、M7 再召回。
- **修改建议**：将「**元数据过滤 + 关键词(BM25)与向量双路混合检索（EnsembleRetriever / 双路召回取并集去重）**」从可选提为**核心实现**；专有名词走精确匹配；rerank 作为混合之后的精排。

### P1-5　缺少「评估 → 归因 → 调参」的达标闭环与初始参数
- **问题描述**：给了 top-k/阈值/rerank 但未给初始值与 badcase 归因方法，M4 不达标时没有明确调优路径。
- **影响范围**：M4/M5 的达成可复现性。
- **修改建议**：评估脚本分两层统计——「正确来源是否进 top-k（检索命中）」与「最终答案是否正确（生成命中）」；失败归因三类（没召回 / 召回了但答错 / 分级错）；初始参数 top-k=4、相似度阈值 0.35、rerank 后取 3，chunk=500/overlap=50，按 badcase 迭代并记录每次改动。
