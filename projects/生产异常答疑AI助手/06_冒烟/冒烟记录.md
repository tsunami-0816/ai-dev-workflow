### 阶段一真实报错与修复

**报错 1（代码 Bug，已修复）**
- 报错原文：`TypeError: list indices must be integers or slices, not ModelMetaclass`（`app/schemas/notification.py:21`）
- 根因：字段名 `list` 遮蔽内置 `list` 类型，Pydantic 重建注解 `list[NotificationOut]` 时 `list` 已绑定为字段值
- 改动：`app/schemas/notification.py` — 字段改名 `items`，`Field(default=[], alias="list")` + `populate_by_name`，对外契约字段名不变
- 验证：import 通过；/api/notifications 返回 `{"list": [], "unread_count": 0}`（alias 生效）

**报错 2（环境，已解决）**
- 现象：`GET /api/health` 超时（60 秒无响应）
- 根因：health 检查触发 Chroma 初始化 → 首次加载 bge-small-zh 需从 HuggingFace 下载 ~100MB，直连极慢
- 解决：预下载 `HF_ENDPOINT=https://hf-mirror.com python -c "SentenceTransformer('BAAI/bge-small-zh-v1.5')"`，启动后端时携带同环境变量
- 验证：health 正常返回

### 已知现象（非 Bug，用户须知）

① **首次启动慢**：torch/sentence-transformers/chromadb import 约 40 秒，期间端口未监听属正常，不要误判进程死亡。
② **首次问答慢**：Ollama 首次加载 3B 模型到显存约 10~30 秒，后续问答会快很多。
③ **知识库为空**：`kb_chunks=0`，问答暂无手册来源（sources 为空）；请在「知识库」页上传 1~2 份手册后再测带源问答。

### 阶段二真实问题与修复（3 条，均基于用户实测报错/现象）

**问题 1（代码 Bug，已修复）：admin 上传 docx 报 metadata 错误**
- 报错原文：`Expected metadata value to be a str, int, float or bool, got None which is a NoneType in upsert. Try filtering complex metadata from the document using langchain_community.vectorstores.utils.filter_complex_metadata.`
- 根因：`loaders._meta()` 允许 `page=None`（docx 无稳定页码），`_load_docx` 显式传 `page=None`，None 值写入 Chroma metadata 时 upsert 直接抛异常
- 改动：① `app/rag/loaders.py` `_meta()` 剔除值为 None/空串的键；② `app/rag/vectorstore.py` `add_documents()` 增加 `filter_complex_metadata` 兜底清理 + 跳过空切片
- 验证：重新上传同一 docx → `status=indexed`，文档入库成功（修复前后端日志确实记录「文档入库失败」）

**问题 2（代码 Bug，已修复）：点「有用/没用」反馈按钮后会话变空白**
- 现象：employee 提问后点反馈按钮，整个对话界面被清空
- 根因：反馈按钮写在单次 `if question:` 渲染块内部；点击按钮触发 Streamlit rerun 后 `question` 变为 None，该块整段被跳过，按钮 widget 未再注册 → 界面空白
- 改动：`frontend/pages/1_问答.py` — 反馈按钮移入「历史消息循环」内，`key=f"up_msg_{idx}"` 绑定消息位置；assistant 消息落库时带上 `trace_id` 供反馈调用
- 验证：用户刷新前端后反馈按钮不再清空会话

**问题 3（代码缺陷，已修复）：知识库无答案的兜底工单 process 角色看不到**
- 现象：employee 提了两个问题，切到 process 登录，工单页只有一条「设备温度报警」工单；通知里能看到提问但显示知识库无答案
- 根因：`ask_service.ask()` 的「知识库无相关内容」兜底派单分支只给 `admin` 发通知，未覆盖 process/repair/safety
- 改动：`app/services/ask_service.py` 兜底分支 — 保留 LLM 判定的 route_type（置信度 <0.4 或非法时回落 admin），并**给全部负责人角色（admin/repair/process/safety）发通知**
- 说明：LLM 分级对无意义提问会较激进地直接判 P0/admin 走正常派单路径，兜底分支只在「LLM 判简单 + 检索确实无内容」时触发；两处通知逻辑现已一致，任何角色登录都能看到
