## 二、上线方案

### 2.1 部署步骤（普通 PC，Windows）

1. 安装 Python 3.11+、Node 无需；安装并启动 Ollama，`ollama pull qwen2.5:3b-instruct-q4_K_M`
2. `python -m venv .venv && .venv\Scripts\activate`
3. `pip install -r backend/requirements.txt`、`pip install -r frontend/requirements.txt`
4. 复制 `.env.example`（或手动创建 `.env`）→ **必须设置强随机 `JWT_SECRET`**（P2-01：种子账号密码同时修改）
5. `python scripts/init_db.py`（建表 + 种子账号）
6. 启动后端：`set HF_ENDPOINT=https://hf-mirror.com` → `python -m uvicorn app.main:app --host 127.0.0.1 --port 8000`
7. 启动前端：`streamlit run app.py --server.port 8501`（frontend/ 目录下）
8. 可选（扫描件支持）：安装 Tesseract（含 chi_sim）+ poppler（L-02）

### 2.2 环境变量清单

| 变量 | 必填 | 说明 |
|---|---|---|
| `JWT_SECRET` | ✅ | 强随机 ≥32 字符；不设则用代码默认值（P3-03：下版本改为缺失即拒启） |
| `HF_ENDPOINT` | 建议 | `https://hf-mirror.com`（国内镜像，否则首次下载 embedding 极慢——失败日志第 2 条） |
| `DATABASE_URL` / Chroma 路径 / 模型端点 | 否 | 见 `config.py` 默认值（SQLite + 本地 data/chroma + Ollama 127.0.0.1:11434） |

### 2.3 数据库初始化与回滚

- 初始化：`python scripts/init_db.py`（幂等建表 + 种子账号）；向量库随文档上传自动构建
- 备份：SQLite 单文件 `data/app.db` + `data/chroma/` + `data/uploads/` 三处即为全量
- 回滚：代码回滚用 git 版本；数据回滚恢复上述三个目录到上一状态后重启服务；`.env` 变更前先备份

### 3.2 核心问题与根因（Top 3）

1. **检索无相关性守门（ACC-01，验收才发现）**——`hybrid_retrieve` 无任何相似度过滤，config 阈值成摆设，库外问题被无关文档自信作答。根因：需求理解偏差，「检索到文档」被等同于「知识库有答案」，且唯一防线押在 3B 小模型的 prompt 自觉上。
2. **AI 产出的校验脚本自身缺陷率 36%（4/11）**——契约校验 22/22 误报、联调脚本 7 项假失败、boundary 解壳错误、（第 9 步 e2e 2 项数据性假失败）。共同根因：脚本没有先对「已知正样本」自检，直接信其输出。
3. **第 6 步集中暴露 5 个运行期缺陷**——字段名遮蔽内置类型、Chroma metadata None、Streamlit rerun 语义、兜底通知漏角色、HF 下载慢。根因：阶段一探活只验证「服务能起」，未覆盖核心交互路径（上传/反馈/多角色）。

### 3.4 流程改进建议（每条对应真实失败记录）

1. **AI 产出的校验/测试脚本必须先自检**：用 2-3 个「已知正确响应样本」做脚本内置单测，输出可信才允许作为卡点判据。（对应第 6.5/7/8 步 3 条脚本缺陷——本步骤共浪费 3 次返工）
2. **评估集必须含负例**：黄金测试集补「知识库没有的问题应拒答/派单」用例，纳入 run_eval 机器校验。（对应 ACC-01——验收期才发现的 P1）
3. **阶段一探活清单升级为「核心交互路径」**：上传、反馈、多角色登录各来一发，不止 /health。（对应第 6 步用户实测暴露的 3 个缺陷）
4. **8.5 步机器校验加入 bandit 静态扫描**，与密钥扫描并列。（对应 SEC-01）
5. **响应解壳统一工具函数**：统一「data 外壳/直接顶层」两种结构的解析入口，禁止各脚本手写。（对应第 7/8 步两次解壳错误）
