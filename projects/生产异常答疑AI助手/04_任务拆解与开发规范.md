**最小可冒烟主流程（第 6 步必达，对应 P0 串线）**：
登录 → 上传/已内置 1 份手册 → 简单提问得到带来源答案 → 连续追问一次 → 问一个复杂问题触发派单 → 负责人收到通知 → 领取/处理/关闭（勾选沉淀）→ 管理员审核入库 → 相似问题再问命中。

## 4. 开发规范

### 4.1 代码规范
- 遵循 PEP 8，统一用 **black + ruff** 格式化/检查，行宽 100；全部函数与方法加类型注解。
- 严格分层：`api` 只做参数校验与编排；业务逻辑在 `services`；RAG 逻辑在 `rag`；ORM 在 `models`；禁止在路由里写业务与 SQL。
- 所有入参/出参用 Pydantic schema 校验；密钥、路径、模型名一律走 `core/config`，禁止硬编码。
- 外部依赖（LLM/Chroma/DB）调用统一捕获并转换为错误码；LLM 调用设超时与一次重试。

### 4.2 命名规范
- Python 变量/函数/文件 `snake_case`；类 `PascalCase`；常量 `UPPER_SNAKE`。
- 表名小写下划线（`ticket`、`ticket_handling`）；REST 路径用复数资源（`/tickets`、`/documents`）。
- 环境变量大写（`MODEL_PROVIDER`、`LOCAL_MODEL`）；任务编号即本文编号（如 `CHAT-04`）。

### 4.3 提交规范
- Conventional Commits：`feat / fix / docs / refactor / test / chore`，标题含任务编号。
  - 示例：`feat(chat): 多轮上下文拼装与追问承接 [CHAT-02]`
- 一个任务一次提交，保持可回滚；`.gitignore` 必须排除 `.env`、`data/`、`__pycache__/`、`*.db`。
- 分支建议：`main` 稳定 + `feat/<任务编号>` 开发分支（单人 MVP 可简化为按任务提交）。

### 4.4 注释规范
- 每个模块顶部 docstring 写职责；服务/函数 docstring 写输入、输出、可能抛出的错误。
- 分级兜底、检索融合、安全拦截等关键逻辑注释「为什么这么做」；FastAPI 路由 docstring 即接口说明（自动进 OpenAPI）。
- 不写无意义注释；复杂 prompt 放 `rag/prompts.py` 并注明用途。
