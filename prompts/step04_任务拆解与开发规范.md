# 第 4 步 · 任务拆解与开发规范

- **角色**：资深技术项目经理
- **输入**：评审通过的最终版《技术架构设计文档》+ 评审报告中的「已确认结论」
- **输出物**：《任务拆解与开发规范》→ 落盘 `04_任务拆解与开发规范.md`；同时在项目根目录建立 **`_设计实施映射表.md`**（本步建表，5A/5B/6/7/8/9 逐行更新，10.0 门禁卡 100%）
- **👤 人工检查点**：给用户一份**具体扫漏清单**对照勾，不要让用户凭感觉「扫一眼」。真实项目里漏过的都是具体环节，不是抽象感觉。

## 人工扫漏对照清单（交给用户逐项勾）

```
请你对照下面三类清单逐项确认，缺哪类就补：

【1. 角色权限矩阵】
□ 系统里有哪几个角色？（如 admin/普通用户/审核员…）
□ 每个角色：能登录吗？能看到哪些页面？能创建/修改/删除哪些数据？
□ 有没有「某角色应该能看到某数据，但任务清单里没写」的情况？
  （真实踩过的坑：兜底工单只通知 admin，process/repair/safety 角色登录看不到工单）

【2. 异常分支】
□ 网络请求失败/超时：前端有提示吗？后端有重试或兜底吗？
□ 数据为空（列表空、搜索无结果）：界面怎么展示？
□ 重复提交（同一个按钮点两次）：有防重吗？
□ 用户中途退出/断网：数据会丢吗？

【3. 边界输入】
□ 超长文本（输入框贴 1000 字）会怎样？
□ 特殊字符/emoji/sql 注入串会怎样？
□ 文件上传：超大文件、非法格式、空文件会怎样？
```

## 提示词

```
你是资深技术项目经理，基于架构设计文档，输出《任务拆解与开发规范》。
【输出要求】
1. 模块划分：按架构拆分为独立开发模块，明确每个模块的职责、交付物、依赖项
2. **任务拆解按端到端链路，不按文件**：把架构 §「设计要素与端到端链路清单」里的每条核心链路拆成「输入 → 处理 → 输出」的最小验证闭环，**一条链路一组任务**；每组任务必须写清：链路起点（用户什么操作/什么事件）、每个节点的处理与落点文件、链路终点（用户能看到什么结果）。禁止只列「写 user.py / 写 run.py / 写 Dashboard.vue」这种文件清单式拆解。
3. 优先级排序：所有任务按P0（核心必做）/P1（重要）/P2（优化）分级，梳理任务间的依赖关系与开发顺序；每条 P0 链路必须标「做完后用什么操作验证整条链通了」
4. 开发规范：统一的代码规范、命名规范、提交规范、注释规范
5. 验收标准：每个任务的完成验收标准
6. **设计→实施映射表（强制，本步产出）**：把第 1 步基线的核心/配套范围 + 第 2 步架构的「设计要素与端到端链路清单」逐条抄进项目根目录 `_设计实施映射表.md`，初始状态一律写 `❌未实现`。表头固定为：

   | 编号 | 设计来源 | 设计项（功能/链路） | 端到端链路（输入→处理→输出） | 用户操作路径 | 实现落点 | 状态 | 验证证据 |
   |---|---|---|---|---|---|---|---|
   | D-01 | 架构 §3 / 设计书 §3 | 示例：SDK 上报→看板展示 | 上报事件→入库→聚合→页面可见 | 打开 SDK 页→跑一次 run→刷新看板 | backend/app/api/xxx.py + frontend/src/views/xxx.vue | ❌未实现 | — |

   状态只能是四种：`❌未实现` / `⚠️已实现未验证` / `✅已实现已验证` / `✂️明确砍掉`。标 `✂️` 的行必须在「验证证据」列写 `砍掉依据：<设计书§8/基线排除范围原话>`，否则脚本判红。
   设计书或架构里写了的条目**一条都不许漏**：漏抄即视为「设计了但没打算实现」，第 6 步冒烟与 10.0 门禁会打回。
7. **风险级别标注（2026-11-01 新增，供第 5.5 步独立 review 定级）**：任务表每条必须带「风险级别」列（高/中/低），判定清单固定，不许自创：
   - **高**：鉴权与权限、数据迁移 / Schema 变更、并发·事务·幂等、对外部 API 或密钥的使用、部署与启动脚本、公共组件或公共接口的签名变更；
   - **中**：核心链路新增模块、跨端契约字段、批处理与定时任务；
   - **低**：样式、文案、独立工具函数。
   标「高」的任务在第 5.5 步被 review 命中时，必须额外产出「高风险变更确认清单」交给用户，不自动放行。
要求：任务颗粒度均匀，依赖关系清晰，优先级明确，可直接分配开发；每条 P0 链路在映射表里至少一行。
```

## 交付自检

- [ ] 每个模块有明确职责、交付物、依赖项
- [ ] 任务按端到端链路拆成「输入→处理→输出」最小闭环，不是按文件/模块列清单
- [ ] 每条 P0 链路都有「做完后怎么验证整条链通了」的验收动作与预期用户可见结果
- [ ] 全部任务标注 P0/P1/P2 及依赖顺序
- [ ] 代码/命名/提交/注释四类规范统一
- [ ] 每个任务都有可判定的验收标准
- [ ] **`_设计实施映射表.md` 已落盘**：架构 D-编号条目与基线核心/配套范围逐条抄全，无漏项，初始状态为 `❌未实现`
- [ ] 每条任务标了风险级别，且「高」是按固定清单判定的（鉴权/数据迁移/并发事务/外部 API 与密钥/部署脚本/公共组件签名），没有漏标
- [ ] `python scripts/design_impl_check.py <项目目录> --stage 4` 通过（只查表结构与非空，允许 `❌未实现`）
- [ ] 已向用户发出「人工扫漏对照清单」，并收到用户对角色权限/异常分支/边界输入三类的确认或补充
