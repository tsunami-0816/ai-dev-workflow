# 第 6 步 · 本地真实运行与冒烟（👤 人工卡点，分两阶段）

- **角色**：阶段一由 Agent 自启动验证；阶段二由用户走主流程；Agent 扮演资深全栈工程师负责全程修复
- **输入**：第 5 步产出的前后端代码
- **输出物**：能在本地跑起来的项目（核心主流程走通）+ `06_冒烟/冒烟记录.md`
- **循环**：阶段一「AI 自己装依赖 → 自己启动 → 自己修报错 → 服务起来」→ 阶段二「用户走主流程 → 贴报错 → AI 修 → 再走」，直到主流程通。
- **铁律**：Agent 不得虚构运行结果——阶段一必须有真实终端输出作证；没有用户真实报错，不得进入阶段二修复。

---

## 6.0 阶段一：AI 自启动验证（新增，必须先做）

> 目的：把「装依赖装不上、服务起不来」这类纯环境问题在 AI 手里解决掉，不浪费用户的时间。用户只负责验证「功能对不对」，不负责当 AI 的终端。

**前提**：当前 AI 工具具备终端/命令执行能力（Trae、Cursor、Claude Code、Codeium 等 Agent 类工具）。若当前是纯对话环境（如豆包网页版），跳过本阶段，直接走 6.1 把命令清单给用户。

**Agent 必须按序执行，每步留证：**

1. **装依赖**：按部署说明执行 `pip install -r requirements.txt` / `npm install` 等。报错 → 自己分析、自己修（改版本、换源、补系统依赖），修好为止。
2. **初始化**：数据库初始化脚本、`.env` 从 `.env.example` 复制并填默认值（**同时做配置完整性检查：grep 代码里所有 `os.getenv`/`process.env` 引用，和 `.env.example` 里的 key 做差集，缺的补进去**）、模型拉取（如 `ollama pull`）。
3. **启动服务**：以后台方式启动后端和前端（如 `uvicorn ... &`、`streamlit run ... &`），确认进程存活、端口监听。
4. **全路径探活（不是只打 /health）**：对照第 4 步《任务拆解与开发规范》里的 P0 任务清单，逐个执行：
   - 用**每个角色**的账号登录一次，确认都能登进去、能看到自己该看到的页面；
   - 执行一次**核心写操作**（创建一条数据、上传一个文件、提交一个工单），确认写成功且能在列表查到；
   - 访问**每个前端页面**，确认不白屏、不报前端错误；
   - 再调 1~2 个核心业务接口确认 API 层主链路通。
   > 为什么这么宽：真实项目里「GET /health 200 + 登录拿 token」28 秒就跑通了，但用户一上传 docx、一点反馈按钮、一换角色登录，立刻踩 3 个 bug。探活只打健康检查 = 把测试工作全推给用户。
4.1 **按用户操作路径走查（不是按接口列表逐个 curl）**：拿第 4 步 `_设计实施映射表.md` 的「用户操作路径」列，把每条核心链路从**用户第一个动作到看到最终结果**串起来走一遍（如「建 prompt → 建 dataset → 跑 run → 看结果页」）。只验证单个接口 200 不算通，必须验证「上一步的输出能成为下一步的输入」。每条链路的走查记录（操作步骤、预期、实际、截图/响应）写进冒烟记录。
4.2 **映射表逐行核对（冒烟前闸门）**：
   - 运行 `python scripts/design_impl_check.py <项目目录> --stage 6`：只要还有 `❌未实现` 行（P0 链路/功能）就**不得进入阶段二**，必须先回 5A/5B 补实现；
   - `⚠️已实现未验证` 行允许带进阶段二，但必须在阶段二由用户操作或后续 7/8/9 步验证掉；
   - 核对时发现「设计书/架构里写了、映射表却漏了」的条目，当场补行并标 `❌未实现`——这正是「到冒烟才发现功能压根没写」的拦截点。
4.3 **字段值断言（硬要求）**：探活与 P0 用例**禁止只断 code=200/0**。每条用例必须至少断言一个关键字段值：状态/枚举字段值在合法集合内、关键字段（如耗时、名称、关联 ID）非空、返回值不是 mock 假数据。来源：SparrowScheduler 第 9 步 3 条验收不通过（状态显示「未知」、耗时全空、页面假数据）全部是 code=200 但字段值错误，自动用例未拦住。
4.4 **前端 UI 质量检测（R23）**：探活通过后，跑一遍前端 UI 质量检查：
   - 运行 `python scripts/design_quality_check.py --url http://localhost:<前端端口> --json 06_冒烟/前端UI质量报告.json`
   - 结果写入 `06_冒烟/前端UI质量报告.md`（把 JSON 转成人类可读的摘要：error X 条 / warning X 条 / advisory X 条 + 问题列表）
   - **不阻塞冒烟**——功能能跑就行，问题记下来就行
   - error 级问题：记入 `_问题台账.md`，P1 级
   - warning 级问题：记入 `_问题台账.md`，P2 级（精修模式下优先修，普通模式下 deferred）
   - 组件库默认配色已自动降级为 advisory，不用管
4.5 **taste 审美检测（R25，软观察期）**：4.4 跑完后接着跑：
   - 运行 `python scripts/design_taste_gate.py --url http://localhost:<前端端口> --project <项目目录名> --project-type <看板里的项目类型> [--app]`
   - B端后台项目加 `--app`；C端/落地页不加
   - 结果写入 `06_冒烟/taste审美检测报告.md`（把 inspect 输出的 FAIL 列表整理成人读摘要）
   - **当前不阻塞**（脚本里写了永远 exit 0），但要人工/AI 看一遍报告里的 FAIL 项
   - 把每条 FAIL 在 `WORKFLOW_taste_gate_观察.md` 对应那行的「人工标注」列标成「真问题 N / 误报 M」——这是 step11 自动调软硬卡的数据源
   - 标「真问题」的项记入 `_问题台账.md`；标「误报」的项写进观察表「备注」列，step11 时加白名单
5. **生产构建验证（如适用）**：前端跑一次 `npm run build`、后端跑一次打包/语法全编译，确认 dev 能跑不等于 build 能跑（路径别名、环境变量注入、静态资源相对路径是常见炸点）。
6. **自启动记录**：把每一步的命令、结果、报错与修复过程写入 `06_冒烟/冒烟记录.md` 的「阶段一：AI 自启动记录」小节；**日志与报错严格按 `appendixA` A-0a 处理**（日志写盘、关键行提取、报错当场记入 `06_冒烟/_报错档案.md`）；每次修复运行 `scripts/log_failure.py` 记入 `_失败日志.md`。
7. **产出阶段二走查清单（硬要求）**：阶段一交付前，必须先产出 `06_冒烟/阶段二人工走查清单.md`（结构见该文件模板，固定 7 段：①环境与账号 ②覆盖度总表 ③按用户操作路径分步 ④角色与租户权限矩阵 ⑤负向与边界 ⑥问题回报模板 ⑦已知边界）。每步用「打开 X 页 → 点 Y 按钮 → 输入 Z → 预期看到 W」句式，写死可复制的测试数据，覆盖所有核心功能（不只主线）。**没有走查清单不得交付用户**。
8. **交付给用户**：服务保持运行，输出「阶段二操作指引」（访问地址、测试账号、走查清单路径 `06_冒烟/阶段二人工走查清单.md`），明确告诉用户：服务我已启动并全路径探活成功，请你按走查清单逐项验证，有问题按清单第⑥段模板回报。

**禁止行为**：
- 禁止说「代码可以直接运行」而不实际跑；
- 禁止跳过探活直接交给用户；
- 禁止在阶段一替用户做「主流程功能对不对」的结论（AI 只能验证服务活着、接口通，功能是否符合预期必须用户判）。

## 6.1 阶段二：用户本地操作步骤（AI 自启动通过后执行）

1. 确认 AI 交付的服务正在运行（AI 已给出访问地址）。
2. 打开 `06_冒烟/阶段二人工走查清单.md`，按清单第③段「按用户操作路径分步」逐项执行：每步操作 → 核对预期 → 勾选通过/不通过。
3. 发现报错时：按清单第⑥段「问题回报模板」填写（操作步骤/预期/实际/报错截图），贴回对话即可，不用复制整个日志文件；Agent 会自己去 `06_冒烟/` 目录读完整日志并提取关键行。
4. 走查清单第④段（角色/租户权限）、第⑤段（负向/边界）也要过一遍，不只走主线。

> 若当前环境 AI 无终端能力（纯对话），退化为旧模式：Agent 给出安装/启动命令清单，用户在本地执行 6.1，把完整报错贴回。

## 6.2 修复 Prompt（Agent 自己从日志提取报错，不依赖用户贴全文）

```
你是资深全栈工程师。以下是我走主流程时遇到的报错关键行（完整日志在 06_冒烟/ 目录，你自己用 Select-String 提取完整上下文）。
【报错关键行】
{{你从日志里提取的 ERROR/Exception/Caused by/Traceback 行，3-10 行}}
【当时在做什么】
{{用户描述：点了什么操作、预期什么、实际什么}}
【修复要求】
1. 先分析报错根因，不要猜，要基于报错信息和日志上下文推理
2. 给出修改后的完整文件内容，标注改了哪几行
3. 说明为什么这样改，改完后为什么不会再报错
4. 如果是缺依赖或版本问题，给出准确的安装命令
5. 修好后把这条报错按 appendixA A-0a 格式追加到 06_冒烟/_报错档案.md
禁止只给解释不给代码，禁止让我自己去查文档。
```

- [ ] **按用户操作路径走查了映射表里的每条核心链路**，不是只按接口列表 curl（走查记录含操作步骤/预期/实际）

- [ ] 过程中每个真实报错都有：报错原文 → 根因 → 改动文件/行 → 修复后验证
