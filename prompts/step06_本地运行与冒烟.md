# 第 6 步 · 本地真实运行与冒烟（👤 人工卡点，分两阶段）

- **角色**：阶段一由 Agent 自启动验证；阶段二由用户走主流程；Agent 扮演资深全栈工程师负责全程修复
- **输入**：第 5 步产出的前后端代码
- **输出物**：能在本地跑起来的项目（核心主流程走通）+ `06_冒烟/冒烟记录.md`
- **循环**：阶段一「AI 自己装依赖 → 自己启动 → 自己修报错 → 服务起来」→ 阶段二「用户走主流程 → 贴报错 → AI 修 → 再走」，直到主流程通。
- **铁律**：Agent 不得虚构运行结果——阶段一必须有真实终端输出作证；没有用户真实报错，不得进入阶段二修复。

---

## 6.0 阶段一：AI 自启动验证（新增，必须先做）

> 目的：把「装依赖装不上、服务起不来」这类纯环境问题在 AI 手里解决掉，不浪费用户的时间。用户只负责验证「功能对不对」，不负责当 AI 的终端。

**前提**：当前 AI 工具具备终端/命令执行能力（Trae、Cursor、Claude Code、Codeium 等 Agent 类工具）。若当前是纯对话环境（如豆包网页版），跳过本阶段，直接走 6.1 把命令清单给用户。

**Agent 必须按序执行，每步留证：**

1. **装依赖**：按部署说明执行 `pip install -r requirements.txt` / `npm install` 等。报错 → 自己分析、自己修（改版本、换源、补系统依赖），修好为止。
2. **初始化**：数据库初始化脚本、`.env` 从 `.env.example` 复制并填默认值（**同时做配置完整性检查：grep 代码里所有 `os.getenv`/`process.env` 引用，和 `.env.example` 里的 key 做差集，缺的补进去**）、模型拉取（如 `ollama pull`）。
3. **启动服务**：以后台方式启动后端和前端（如 `uvicorn ... &`、`streamlit run ... &`），确认进程存活、端口监听。
4. **全路径探活（不是只打 /health）**：对照第 4 步《任务拆解与开发规范》里的 P0 任务清单，逐个执行：
   - 用**每个角色**的账号登录一次，确认都能登进去、能看到自己该看到的页面；
   - 执行一次**核心写操作**（创建一条数据、上传一个文件、提交一个工单），确认写成功且能在列表查到；
   - 访问**每个前端页面**，确认不白屏、不报前端错误；
   - 再调 1~2 个核心业务接口确认 API 层主链路通。
   > 为什么这么宽：真实项目里「GET /health 200 + 登录拿 token」28 秒就跑通了，但用户一上传 docx、一点反馈按钮、一换角色登录，立刻踩 3 个 bug。探活只打健康检查 = 把测试工作全推给用户。
5. **生产构建验证（如适用）**：前端跑一次 `npm run build`、后端跑一次打包/语法全编译，确认 dev 能跑不等于 build 能跑（路径别名、环境变量注入、静态资源相对路径是常见炸点）。
6. **自启动记录**：把每一步的命令、结果、报错与修复过程写入 `06_冒烟/冒烟记录.md` 的「阶段一：AI 自启动记录」小节；每次修复运行 `scripts/log_failure.py` 记入 `_失败日志.md`。
7. **交付给用户**：服务保持运行，输出「阶段二操作指引」（访问地址、测试账号、要走的主流程步骤），明确告诉用户：服务我已启动并全路径探活成功，请你走一遍主流程验证功能是否符合预期。

**禁止行为**：
- 禁止说「代码可以直接运行」而不实际跑；
- 禁止跳过探活直接交给用户；
- 禁止在阶段一替用户做「主流程功能对不对」的结论（AI 只能验证服务活着、接口通，功能是否符合预期必须用户判）。

## 6.1 阶段二：用户本地操作步骤（AI 自启动通过后执行）

1. 确认 AI 交付的服务正在运行（AI 已给出访问地址）。
2. 打开浏览器 / Postman，走一遍最核心主流程（例如：注册 → 登录 → 创建一条数据 → 列表看得到）。
3. 把终端里的报错信息、截图，完整复制下来，贴回对话。

> 若当前环境 AI 无终端能力（纯对话），退化为旧模式：Agent 给出安装/启动命令清单，用户在本地执行 6.1，把报错贴回。

## 6.2 修复 Prompt（把用户贴回的真实报错填进去）

```
你是资深全栈工程师，以下是我在本地启动项目时遇到的真实报错。
【报错信息】
{{把终端完整报错、堆栈信息、截图描述粘贴到这里}}
【当前项目代码结构】
{{只贴报错相关的文件，不要贴全部代码}}
【修复要求】
1. 先分析报错根因，不要猜，要基于报错信息推理
2. 给出修改后的完整文件内容，标注改了哪几行
3. 说明为什么这样改，改完后为什么不会再报错
4. 如果是缺依赖或版本问题，给出准确的安装命令
禁止只给解释不给代码，禁止让我自己去查文档。
```

## 冒烟放行检查（写进 `06_冒烟/冒烟记录.md`）

- [ ] 依赖安装成功，后端、前端服务均能启动
- [ ] 核心主流程端到端走通（以架构中定义的最核心链路为准）
- [ ] 过程中每个真实报错都有：报错原文 → 根因 → 改动文件/行 → 修复后验证
- [ ] 用户确认「主流程已通」，方可进入第 7 步
