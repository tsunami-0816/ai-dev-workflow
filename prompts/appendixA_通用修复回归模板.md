# 附录 A · 通用修复-回归模板（第 7/8/9 步共用）

> 有了一份问题清单（联调问题 / Bug 清单 / 验收问题）时，直接套用本模板，不必每次重写 Prompt。

---

## A-1 定向修复 Prompt

```
你是资深全栈开发工程师，基于现有代码，修复以下问题清单。
【问题清单】
{{粘贴当前阶段的 P0+P1 问题清单}}
【严格执行规则】
1. 只修复清单内的问题，禁止任何额外的功能优化、代码重构、逻辑调整，禁止超范围修改
2. 修改前先输出「修改影响分析」：每个问题的修改点、涉及的文件/函数、可能影响的其他功能链路
3. 修改后的代码标注：// 修复-xxx 改动原因
4. 只输出有修改的文件完整内容（或关键 diff），不输出全部代码
5. 修复完成后输出「自测说明」：每个问题的验证方法、自测步骤
禁止修改不在清单内的任何逻辑，禁止重构原有正常运行的代码。
```

---

## A-2 定向回归 Prompt

```
你是资深测试工程师，基于修复后的代码和原问题清单，帮我生成定向回归验证清单。
【回归范围】
仅验证以下内容，不做范围外的全量测试：
1. 上一轮所有 P0、P1 级问题是否修复（逐条列出验证步骤）
2. 修改影响分析中提到的关联功能是否正常
【输出要求】
1. 每个原问题对应的验证操作步骤（我在本地照着做）
2. 每条验证的预期结果
3. 一个简单的记录表格模板：问题编号 | 验证步骤 | 预期 | 实测结果 | 是否通过
严格按既定回归范围执行，不扩大测试范围。
```

> 然后：用户在本地照着回归清单一条条测，把实测结果填进去。全过就进入下一步；有没过的就回到 A-1 再修。

---

## 各步轮次上限（防止无限返工）

| 步骤 | 修复-回归上限 | 超限处理 |
|---|---|---|
| 第 7 步 联调 | 最多 2 轮 | 判定架构性问题，回流第 3 步 |
| 第 8 步 全量测试 | 全量测 1 轮 + 修复回归最多 2 轮 | 架构问题走回流；其余作 P2/P3 留到下版本 |
| 第 9 步 验收 | 最多 2 轮 | 按根因回流第 1 步（需求）或第 3 步（架构） |
