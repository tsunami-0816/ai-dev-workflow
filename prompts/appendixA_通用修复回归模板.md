# 附录 A · 通用修复-回归操作手册（第 6/7/8/9 步共用）

> **唯一问题清单是项目根目录的 `_问题台账.md`。**
> 不再分别新建「联调问题清单 / BUGLIST.md / 验收问题清单」，也不再单独产《回归验证报告》——
> 问题的记录、修复、回归结果全部写回台账（状态 + 轮次列），台账就是回归证据。
> 各阶段目录只放**检查清单、截图、执行日志、脚本**这类证据。

---

## A-0a 日志与报错处理（硬规定，6/7/8/9 全程遵守）

> 适用场景：Agent 有终端能力时（Trae/Cursor/Claude Code 等）按本节执行；纯对话环境（豆包网页版等无终端）才退回旧模式（用户贴完整报错，见 step06 6.2）。

**日志三不准**：
1. 不准把整个 startup.log / backend.log 贴进对话——启动命令一律重定向写盘到本步骤目录（`... *> xxx.log`），对话里只留退出码和最后 20 行
2. 不准凭"我猜是 XX 错"修 bug——必须用 `Select-String "ERROR|Exception|Caused by|Traceback" xxx.log` 提取关键行，把那 3-10 行贴进对话作为修复依据
3. 报错不准只留在对话里——**当场**追加到本步骤目录下的 `_报错档案.md`，不攒到最后补写

**报错档案格式**（每条按这个模板写，不写长文）：
```markdown
## [MM-DD HH:MM] <一句话动作描述：在做什么时报的>
- 命令：<实际跑的命令>
- 报错：<3-10 行关键堆栈，从日志提取>
- 根因：<一句话>
- 修复：<改了哪个文件/哪一行>
- 关联：台账 #X（open/fixed/verified）
```

**原始日志保留**：`xxx.log` 不删不清理，留在原目录作为证据；报错档案是提炼，原始日志是全量，两个都要。

## A-0 每轮的标准动作（照这个顺序做，别跳）

1. **执行检查**：按本步的检查清单在本地走查 / 跑自动化，发现的问题**当场写进 `_问题台账.md`**（ID、级别、来源阶段、现象、根因标签、状态=`open`）。
2. **定向修复**：跑 A-1 的 Prompt，输入是台账里 `状态=open` 且 P0/P1 的行；修完逐行把状态改 `fixed`、轮次填 `R<n>`。
3. **定向回归**：跑 A-2 的 Prompt，只验 `fixed` 的行；通过改 `verified`，不通过改回 `open` 并写明原因。
4. **记轮次日志**：在台账「轮次日志」表加一行（本轮 open P0/P1 数 / 修复数 / 结论），再按下面的收敛判据决定「继续下一轮 / 放行 / 回流」。

> 台账里 `open` 或 `fixed` 的 P0/P1 一条都不许留到下一步——门禁脚本会直接读这张表报红。

## A-1 定向修复 Prompt

```
你是资深全栈开发工程师，基于现有代码，修复下面台账里状态为 open 的 P0/P1 问题。
【待修问题（从 _问题台账.md 复制，只贴 open 的 P0/P1 行）】
{{粘贴台账行：ID | 级别 | 来源阶段 | 现象 | 根因标签}}
【严格执行规则】
1. 只修这些行对应的问题，禁止额外功能优化、重构、逻辑调整，禁止超范围修改
2. 修改前先输出「修改影响分析」：每条的修改点、涉及文件/函数、可能影响的其他链路
2.1 每条问题先写「假设-验证」再动手：**假设根因 → 用哪条命令/日志/查询验证 → 验证不过时的备选假设**。禁止跳过验证直接改（AI 自己提问题又自己定根因，容易把第一个猜的当成真的，围着它白修三轮）
3. 修改后的代码标注：// 修复-<ID> 改动原因
4. 只输出有修改的文件（关键 diff 即可），不输出全部代码
5. 修完输出「自测说明」：每条的验证方法
6. 修完回报「本轮修了哪几条 ID、哪些没能修及原因」，我据此回写台账状态
禁止修改不在清单内的任何逻辑，禁止重构原有正常运行的代码。
```

## A-2 定向回归 Prompt

```
你是资深测试工程师，基于修复后的代码和台账里状态为 fixed 的问题，生成定向回归清单。
【回归范围】只验两类，不做范围外的全量测试：
1. 上一步所有 fixed 的 P0/P1 是否真的修好（逐条给验证步骤）
2. 修改影响分析里提到的关联功能是否正常
【输出要求】
1. 每个问题对应的验证操作步骤（我在本地照着做）+ 预期结果
2. 一张记录表：ID | 验证步骤 | 预期 | 实测 | 是否通过
3. 结论：本轮回归是否通过；未通过的 ID 与原因（我据此把状态改回 open）
严格按既定范围执行，不扩大测试范围。
```

> 用户在本地照着回归清单测，把实测结果填进表；Agent 按结果回写台账状态与轮次。

---

## A-3 收敛判据（不限轮次，防原地打转）

| 步骤 | 轮次 | 何时继续 / 放行 / 回流 |
|---|---|---|
| 第 6 步 冒烟 | 不设上限 | 核心主流程走通即放行；同一根因连续 3 次修复无效 → 回流第 2/3 步 |
| 第 7 步 联调 | 不设上限 | 台账 open P0/P1 单调下降 → 继续；不降或回升、或同一根因 3 次无效 → 回流第 3 步 |
| 第 8 步 全量测试 | 不设上限 | 同上；架构问题回流第 3 步，其余作 P2/P3 标 `deferred` 留到下版本 |
| 第 9 步 验收 | 不设上限 | 同上；按根因回流第 1 步（需求问题）或第 3 步（架构问题） |

> 只有第 3 步架构评审限 3 轮（防 AI 评审完美主义无限提新问题），且从第 2 轮起只验上一轮 P0、不新增 P0。
> 判据数据来自台账「轮次日志」表，不是凭印象说「这轮好多了」。
