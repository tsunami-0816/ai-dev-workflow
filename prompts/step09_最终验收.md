# 第 9 步 · 最终验收测试（👤 人工卡点）

- **角色**：资深验收测试工程师 + 用户（必须亲自在本地走查）
- **输入**：修复后的完整系统 + 项目基线
- **输出物**：`09_验收/最终验收清单与报告.md`
- **循环**：验收发现的问题**全部记入 `_问题台账.md`（来源阶段=9）**，修复与回归按附录 A 操作，**不设轮次上限**，按收敛判据（台账 open P0/P1 数须下降；同一根因 3 次无效或问题数回升 → 按根因**回流第 1 步（需求问题）或第 3 步（架构问题）**）。
- **铁律**：这一步必须用户自己在本地完整走一遍，不能只看 AI 生成的验收报告；重点测「正常人会怎么用」，不是「AI 觉得该怎么测」。
- **两段式验收**：AI 生成的清单只覆盖第二步，第一步自由探索才是抓野生 bug 的关键（真实项目里最重要的 P1 问题「检索无守门」就是用户正常使用时发现的，不在任何清单上）。
- **卡点交付物协议（来源 #78）**：交给用户的验收清单必须是可照做的操作手册——每条含「点哪里、输入什么、预期发生什么」。**交人工之前，AI 必须用浏览器自动化/接口调用把清单完整预走一遍**，把明显问题（页面打不开、字段显示「未知」、假数据、按钮无效）修掉再交付；人工只做 AI 验证不了的判断。SparrowScheduler 实证：AI 预走查先发现并修复 U-1~U-15 后才交人工。
- **前置条件（不满足则本步不得开始）**：① 第 8.5 步安全扫描已通过——security_scan_secrets.py 无发现、依赖 CVE 扫描无 P0/P1、AI 安全扫描 P0/P1 已清零、人工渗透 8 项全部通过；② 第 7.5 步测试数据已重置为干净状态，不是在联调垃圾数据上验收。

---

## 效果度量

- **目标**：用户在本地真实走一遍，确认项目能用来完成真实的事
- **成功标准**：
  1. 自由探索 10 分钟，记录的野生问题全部解决或 deferred
  2. 对照清单逐条走查，P0/P1 全部清零
  3. 基线指标全部验证通过或标"未验证风险"
  4. 项目能用来完成一件真实的事（不是骨架）
- **失败信号**：
  1. 想这么用但做不到 / 不对
  2. 页面假数据 / 按钮无效
  3. 核心功能走不通
  4. 验收发现的问题比测试还多
- **度量方式**：用户口头验收通过 + 台账 open P0/P1 = 0

## 第一步：自由探索（先做，不看清单）

请用户**不看 AI 清单**，像第一次拿到这个系统的真实用户一样自由操作 10 分钟：

```
现在请你把自己当成第一次用这个系统的人，不要看我接下来给你的清单。
按你自己的真实想法操作 10 分钟：你想先点哪里？想干什么事？遇到什么让你觉得「不对/奇怪/做不到」的地方，随手记下来。
目的：抓我清单没覆盖到的野生问题。10 分钟后告诉我你记了什么。
```

这一步发现的问题优先级**高于**第二步清单——因为它们是真实使用路径上的问题。

## 第二步：对照清单逐条走

AI 再生成清单 Prompt：

```
你是资深验收测试工程师，基于项目基线，帮我生成最终验收检查清单。
【验收范围】
1. 所有核心业务链路端到端再走一遍
2. 基线里定义的成功指标，逐条核对是否达标
3. 基础可用性：能不能正常注册登录、数据增删改查、退出再登录数据还在
4. 浏览器兼容性（如适用）：Chrome / Edge 各打开看一眼
【输出要求】
输出一份可勾选的验收清单，每条标注：是否通过 / 实测结果 / 备注
最后给出：是否达到上线交付标准的结论（通过 / 不通过，附原因）
```

> 精修模式 → 下面三项都过才放行；不通过项按附录 A 记入 `_问题台账.md`（来源阶段=9），修复后复验。

- [ ] **③ 空上下文视觉评审是否 ≥9 或已 deferred**：读 `05_代码/frontend/设计精修记录.md` 的「空上下文视觉评审」结论（R24：另起干净上下文、只喂页面截图不喂代码、1-10 分）。≥9 通过；<9 但已用完 2 轮评审上限 → 记 `deferred` 并写进 10.6 简历「诚实边界」，功能验收可继续，但验收报告必须写明未达 9 分及原因。**没有任何评审记录 → 视为未通过：按 R24 补做一次空上下文视觉评审（另起干净上下文、只喂截图、1-10 分，不许由写代码的同一上下文自评替代）**，仍 <9 且 2 轮用尽则记 deferred。
