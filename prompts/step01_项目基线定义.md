# 第 1 步 · 项目基线定义（第一步必做）

- **角色**：资深项目分析师
- **输入**：用户提供的原始项目描述（项目目录 `00_原始项目描述.md`）
- **输出物**：《项目基线说明书》→ 落盘 `01_项目基线说明书.md`
- **作用**：把模糊的需求描述，变成所有人共识的、可验证的项目基准，后续所有工作都不能偏离这个基线。

---

## 提示词（直接套用，把原始描述粘到对应位置）

```
你是资深项目分析师，基于下面这段项目原始描述，输出《项目基线说明书》。
【原始项目描述】
{{把你拿到的完整项目要求粘贴到这里}}
【输出要求】
1. 项目核心目标：明确项目要解决的核心问题、业务价值
2. 核心指标量化：把所有定性描述全部转化为可量化、可验证的指标，禁止模糊表述
3. 项目范围界定：
   - 核心范围（必须做）
   - 配套范围（辅助做）
   - 排除范围（明确不做什么）
4. 约束条件：技术栈约束、部署环境约束、资源约束、时间约束、合规约束
5. 成功标准：明确项目上线后，用哪些指标判定项目正式交付成功
要求：内容严谨、边界清晰，所有指标必须可衡量，不写空泛描述。
```

---

## 交付自检

- [ ] 核心目标说清了「解决什么问题、业务价值」
- [ ] 所有定性描述已转为可量化指标，无「高效/较好/尽快」等模糊词
- [ ] 核心 / 配套 / 排除三类范围都明确列出
- [ ] 五类约束（技术栈、部署、资源、时间、合规）无遗漏
- [ ] 成功标准可逐条核对

---

## 👤 轻确认（基线产出后，30 秒，不算卡点）

Agent 把基线写完落盘后，必须向用户输出一段**极简确认摘要**（不要贴整篇文档）：

```
我把项目基线整理完了，你花 30 秒核对三件事：
1. 一句话目标：<项目解决什么问题>
2. 量化指标列表：<逐条列出，如"30秒内响应""85%准确率""支持3个角色">
3. 明确排除范围：<列出不做的事>

回复「指标OK继续」就进入架构设计；要改哪条直接说。
```

**为什么放在这里**：需求理解错误拖到第 9 步才发现，前面 8 步全废。30 秒对一遍指标，成本极低，但能把方向性错误拦截在最早期。
