# 第 1 步 · 项目基线定义（第一步必做）

- **角色**：资深项目分析师
- **输入**：用户提供的原始项目描述（项目目录 `00_原始项目描述.md`）
- **输出物**：《项目基线说明书》→ 落盘 `01_项目基线说明书.md`
- **作用**：把模糊的需求描述，变成所有人共识的、可验证的项目基准，后续所有工作都不能偏离这个基线。

---

## 提示词（直接套用，把原始描述粘到对应位置）

```
你是资深项目分析师，基于下面这段项目原始描述，输出《项目基线说明书》。
【原始项目描述】
{{把你拿到的完整项目要求粘贴到这里}}
【输出要求】
1. 项目核心目标：明确项目要解决的核心问题、业务价值
2. 核心指标量化：把所有定性描述全部转化为可量化、可验证的指标，禁止模糊表述。**每条指标给 `criterion_id`（C01、C02…递增，G8 追溯挂接用）**，指标表固定列：`编号 | 量化指标 | 数字与单位 | 验证归属 | 对应主链路`；第 4 步映射表逐条挂接这些 C 编号，step9 验收按编号核对，不漏基线项
3. 项目范围界定（三节都必须带「决策理由」列，只列清单不写理由的基线打回重写）：
   - 核心范围（必须做）：每条写「缺了它哪条主链路会断」
   - 配套范围（辅助做）：每条写「原设计 → 降级成什么 → 为什么不硬做」
   - 排除范围（明确不做什么）：每条写「砍掉的依据（硬件/复杂度/JD 权重/非核心）」
   - 三节用表格：`范围项 | 具体内容 | 决策理由 | 对应主链路/来源`
4. 约束条件：技术栈约束、部署环境约束、资源约束、时间约束、合规约束
5. 成功标准：明确项目上线后，用哪些指标判定项目正式交付成功
要求：内容严谨、边界清晰，所有指标必须可衡量，不写空泛描述；每条范围界定后必须跟一句「因为…」。
```

---

## 交付自检

- [ ] 核心目标说清了「解决什么问题、业务价值」
- [ ] 所有定性描述已转为可量化指标，无「高效/较好/尽快」等模糊词
- [ ] 每条量化指标都有 `criterion_id`（C01 递增），指标表含数字与单位、验证归属、对应主链路
- [ ] 核心 / 配套 / 排除三类范围都明确列出，且每条都带决策理由（核心=断哪条链路，配套=原设计→降级→为什么，排除=砍掉的依据）
- [ ] 范围表含「对应主链路/来源」列，后续 `_设计实施映射表.md` 可直接按它拆行
- [ ] 五类约束（技术栈、部署、资源、时间、合规）无遗漏
- [ ] 成功标准可逐条核对

## 🤖 机器闸门 + 三项输入（基线产出后；不阻塞，不再等确认）

> R20：基线后的「指标核对」已从人工轻确认**降级为机器闸门**（WORKFLOW_卡点协议.md「机器闸门」表）。闸门全绿 → 直接进入第 2 步，**不等用户确认**；报红才停下把报红项 + 建议改法列给用户拍板。**这一步不是卡点，用户没回复不得成为停住流程的理由。**

### 1. 先过机器闸门（WORKFLOW_卡点协议.md「机器闸门」表「第 1 步基线闸门」）

基线落盘后，**先跑脚本，报红才人工改**，不靠 Agent 自评：

```bash
python scripts/step_gate_check.py --step 1 --file <项目>/01_项目基线说明书.md
```

脚本会逐行检查量化指标表的「数字+单位 + 验证归属」，并检查「排除范围」段非空；退出 1 即报红。人工再补查脚本覆盖不到的项：

- [ ] 核心 / 配套 / 排除三类范围都带决策理由列（核心=断哪条链路，配套=原设计→降级→为什么，排除=砍掉依据）

脚本全绿 + 上述人工项补齐 → 看板「当前卡点」写「无卡点（基线机器闸门全绿）」，继续第 2 步；脚本报红 → 把无法量化的指标列给用户，请其拍板改成可量化或删掉，等回复（**这是本步唯一需要停的情况**）。

### 2. 只向用户问三项（一次性问完；异步回答；不阻塞）

机器闸门全绿后，Agent 在对话里一次性问下面三项（10 秒能答完），**问完继续做第 2 步，不设「等你回复再继续」**：

```text
基线已过机器闸门。顺手确认三项（不着急，我先按默认值往下走，你随时改）：
1. 项目类型（决定加载哪套设计 skill）：b2b-admin / internal-tool / landing / portfolio
2. 设计模式：普通模式（功能跑通就行）/ 精修模式（多花 30-60 分钟把页面做好看，作品集门面项目选这个）
3. 是否录 demo 视频：是 / 否
不回复就按默认值：项目类型=AI 按设计书自动归类，设计模式=普通模式，不录视频。
```

### 3. 默认值（用户未回复时直接采用，不必等）

| 输入项 | 默认值 | 说明 |
|---|---|---|
| 设计模式（R24） | **普通模式** | 功能跑通就行，用组件库默认样式；精修模式必须用户明确选 |
| 项目类型（R25） | **AI 按 `00_项目设计书.md` 的业务场景自动归类**（无设计书时按原始项目描述） | 归类判据见下；判不准一律 b2b-admin |
| 是否录 demo 视频 | **否** | 录视频要用户明确要 |

**项目类型自动归类判据**（判定不了就用 b2b-admin 并标「待用户确认」）：

- `b2b-admin`：B 端后台 / 管理系统 / 权限 / 表格 / 审核流（默认）
- `internal-tool`：纯内部效率工具，不在意美观（内网工具、脚本化小工具）
- `landing`：C 端落地页 / 产品官网（单页营销、注册转化）
- `portfolio`：个人作品集 / 门面页（展示自己的项目 / 文章 / 简历）

### 4. 三项输入写入看板（R24 / R25 落点，硬要求）

- **「设计模式」字段**：`普通` / `精修`。精修时后续 step02 出设计方向、step05B 设计精修、step09 加视觉质量验收（R24）
- **「项目类型」字段**：`b2b-admin` / `internal-tool` / `landing` / `portfolio`。决定 step02/5B 加载 `skills/` 哪些子目录：b2b-admin/internal-tool 只读 `skills/active/`；landing/portfolio 额外加载 `skills/motion/`、`skills/components/`，详见 `skills/README.md`（R25）
- **「demo 视频」字段**：`是` / `否`。是 → step10.6 参考 `D:\lg\skill\video-shotcraft-main` 做产品宣传片放简历 / B 站
- 三项全部或部分采用默认值时，对应字段后统一追加 **「（用户未确认）」**；用户后续任何时间回复，Agent 覆盖字段、去掉该标注，并按新值重跑受影响分支（只重跑对应分支，不重跑已完成步骤）
- 用户明确说「按默认」→ 不再标「用户未确认」

**为什么只问这三项**：机器闸门能判的（指标量化、验证归属、排除范围）不再打扰用户；这三项机器判不了，且会分叉后面 4-6 个步骤，问一次最省返工——但**问不等于卡点**，未回复按默认值推进。
