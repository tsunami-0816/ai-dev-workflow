# 第 11 步 · 工作流自迭代（项目做完后，回头改工作流本身）

- **角色**：工作流架构师
- **输入**：
  - 根目录 `WORKFLOW_改进建议.md`（本次项目运行中新记录的 backlog + 历史遗留）
  - 根目录 `WORKFLOW_规则体检台账.md`（**规则触发计数，休眠判定的唯一数据源**）
  - 本项目 `_失败日志.md`（交叉验证：backlog 里的建议是不是真的被本次失败验证了）
  - 当前 `WORKFLOW_工作流主控.md`、`prompts/` 下所有模板、`scripts/` 下所有脚本
- **输出物**：`10_交付/工作流自迭代报告.md`
- **流转**：本步产出 triage 报告后暂停，等用户确认采纳项，再实际改工作流文件。不自动改。

---

## 为什么要有这一步

每个项目做完，不只是交付一个软件，还应该让这套工作流本身变得更准。
运行过程中 AI 会碰到：提示词歧义、脚本缺一个、规则没覆盖这个场景、卡点顺序不合理。
这些问题当场记进 `WORKFLOW_改进建议.md`，项目结束后集中 triage。

**但工作流也会越长越胖**，所以本步有硬闸门（WORKFLOW_规则库.md R16）。

## 11.1 triage Prompt

```
你是工作流架构师。刚完成项目「{{项目名}}」，现在对工作流本身做一次自迭代。

【输入】
- WORKFLOW_改进建议.md 的待处理 backlog
- 本项目 _失败日志.md（交叉验证建议是不是真问题）
- 当前主控/提示词/脚本清单

【任务】对 backlog 每一条给一个结论：

✅ 采纳 —— 写清楚具体改法（改哪个文件、加哪条规则/脚本/提示词段），不要只写"优化 step03"
⏸️ 暂缓 —— 写清楚理由：信息不足？需要再看 1-2 个项目？时机未到？
❌ 驳回 —— 写清楚理由：个人项目规模不需要？与现有规则冲突？过度设计？本次是边角情况不是通用模式？

【膨胀闸门（强制）】
在输出采纳项之前，先做三项检查：
1. **全量体检（不抽样）**：把 WORKFLOW_规则库.md「规则正文」所有活跃规则逐条过一遍（含 R22 / R23 / R24 / R25 与翻新线 R-1 / R-2；台账里缺行的先按 WORKFLOW_规则库.md §8.0 补行再体检），每条记录三栏——① 本项目在哪儿执行了它 ② 由哪个脚本/卡点兜底 ③ 未触发原因。
   - **触发证据先查日志，别靠回忆**：优先读本项目 `_失败日志.md` 的「触发规则」列（日常 `log_failure.py --rule R<id>` 打的标），有实证的规则直接把 ✅ 和证据摘出来；日志里没有的，再按「本项目在哪儿执行了它」判断
   - **待溯源规则补源**：某条规则在本项目被实证触发 → 回填 WORKFLOW_规则库.md §8.0 规则登记表的「来源/证据」列（保留「初版」，追加 `YYYY-MM-DD <项目> 实证：<它拦住了什么>`），累计 2 条实证即可去掉「待溯源」标记
   - **机器闸门报红统计（2026-11-01 新增）**：读 `_失败日志.md` 中 `--step` 落在闸门步骤（`1` / `4` / `5.5` / `6.5` / `10.0`）且 `--rule R20` 的记录，按「步骤 + 闸门名」聚合。同一闸门报红 ≥2 次（跨项目）→ 判断是校验项太严还是产物质量真差，写进报告结论；这是WORKFLOW_规则库.md R20「报红率复盘」的数据源。
   - **新闸观察期核对（2026-11-11 新增）**：跑 `python scripts/gate_gatekeeper.py status` 核对各新闸（G1 输入卡 / G8 指标挂接）状态；step10 已跑 `review` 计入本项目。仍处于 observe 的闸口，在报告写明还差几个项目转闸、有无误报；已翻 strict 的核对是否有误报被误拦。观察期判据见 `workflow/gate_states.yaml` 文件头。
   - **体检结果必须写回 `WORKFLOW_规则体检台账.md`**：触发 → 「连续未触发项目数」清零 + 更新「最近触发项目」；未触发 → 计数 +1
   - 计数到 3 → 状态改「休眠候选」（仍按活跃规则执行）；到 4 → 状态改「已休眠」，同时移入 WORKFLOW_规则库.md 末尾「休眠规则（可复活）」区，保留 id + 一行摘要 + **复活条件**，标休眠日期与原因；**原文不删除**
   - **休眠区也在体检范围内**（休眠的规则已不执行，不可能再"触发"，只能复核）：每次体检拿它的「复活条件」问一遍本项目——
     - 本项目满足该条件 → 复活：移回 WORKFLOW_规则库.md「规则正文」、状态改「活跃」、计数清零、备注写复活日期与项目名
     - 不满足 → 复核次数 +1
     - 复核累计 4 次仍未复活 → 状态改「已归档」，标注「不再自动复核」，原文继续留在休眠区，等用户手动翻
   - 活跃规则 >20 条时，必须先完成体检 + 休眠清理才能收工；清理后仍 >20，逐条写明不能休眠的理由，交用户确认（例外通道）
2. **新增规则必须带三件套**：落点（脚本检查 / 卡点动作 / 看板字段）+ 来源项目 + 证据（失败日志或复盘条目）。缺一不进 WORKFLOW_规则库.md「规则正文」，只能留 backlog 建议区。发现 3 个大问题就加 3 条，不为凑数字逼着合并。
   - **加规则前先做「复用检查」（新问题 → 先查旧规则）**：
     - 先扫两处：WORKFLOW_规则库.md 活跃规则 + WORKFLOW_规则库.md 末尾「休眠规则」区。按**问题的现象/根因关键词**匹配，不只看规则名。
     - 命中近似规则时，逐条回答三问：① 它当初治的是同一个根因吗？② 放到本项目约束（技术栈 / 硬件 / 流程变了没）下还成立吗？③ 它对本次问题是不是**最优解**，有没有更轻的落点（脚本一行 / 看板一个字段）？
     - 结论只能三选一：`直接复用`（复活，移回 WORKFLOW_规则库.md「规则正文」）/ `改进后复用`（复活 + 修订，备注写「由旧规则演进，来源本项目」）/ `不复用`（照常新建，并在休眠条目备注写「本次问题为什么不复用」）。
     - **判据是「能不能真解决 + 是不是最优解法」，不是「长得像」**。宁可新写一条，也不要为复用硬套不适用的旧规则；反过来，能复用就别新增，避免同一个问题出现两条规则互相打架。
     - 因为「已有类似规则」就不解决实际问题，同样算违规——复用是手段，解决问题才是目的。
3. 新建议要不要新建脚本？先看现有 scripts/ 下有没有功能相近的。
   - 有 → 扩展现有脚本（加参数/子命令），不新建文件
   - 真没有 → 才新建
4. 新规则与现有规则有没有冲突？
   - 有冲突 → 明确写"退役 R<旧>，由 R<新> 取代"，不许两条矛盾规则并存
   - 引用规则一律写 id（R9），不写"第几条"；id 不回收、不复用

【来源追溯】
每条新规则/新脚本在报告里标注「落点 + 来源 + 证据」：落点=脚本/卡点/看板字段，来源=项目名，证据=失败日志或复盘条目。
规则的休眠/复活判定一律以 `WORKFLOW_规则体检台账.md` 的计数为准，不靠回忆上几个项目。

【taste gate 调参决策（R23 配套 · taste 子项，自动段）】
读 `WORKFLOW_taste_gate_观察.md`，按表头上的判定规则自动下结论：
- 样本 <3 个：跳过，在报告里写「观察中，累计 N 个项目，暂不调整」
- 连续 ≥3 个项目「真问题」占比 ≥50%：建议把 `scripts/design_taste_gate.py` 最后一行改成硬卡（`sys.exit(1 if rc==1 else 0)`），并在报告里说明依据
- 连续 ≥3 个项目「误报」占比 ≥70%：建议把对应规则写进 `--allow` 白名单或降级，列出具体规则名
- 样本够但趋势不明显：维持现状，备注「再观察 N 个项目」
这个决策不用等人确认，直接写进报告；改脚本动作放到 11.2 用户确认后执行。
规则号口径：taste 是 R23「前端 UI 质量自动检测」的子项，本段统一挂 R23；R25 只表示项目类型（看板字段），不用于 taste 调参，报告与观察表里不得再写「R25 调参」。

【铁律】
- 不为了一条建议改 3 个文件。简单建议一句话加进规则就行。
- "这次项目碰到一个边角情况"但不属于通用模式的，一律 ⏸️ 暂缓，不要硬塞成全局规则。
- 个人项目规模小，规则膨胀比规则缺失更危险。克制。

【输出】
一份 triage 报告，表格形式：每条建议的结论 + 理由 + 具体改法（采纳项）。
最后附：体检结果（活跃规则数、休眠了哪几条、新增规则的落点/来源/证据），以及**本次对 `WORKFLOW_规则体检台账.md` 的更新摘要**（哪些规则计数清零、哪些 +1、哪些改状态）。
报告写完暂停，等用户确认后再实际改文件。
```

## 11.2 执行 triage 后

用户确认采纳项后：
1. 按报告改 `WORKFLOW_工作流主控.md`、`prompts/*.md`、`scripts/*.py`
2. 把已实施的条目从 `WORKFLOW_改进建议.md` 移到"已归档"区（按文件自己的清理规则）
3. 暂缓/驳回的条目留在 backlog，标注结论和理由
4. 如果新建了脚本，更新 `scripts/README_脚本说明.md` 和 `AGENTS.md` 的机器校验清单
5. 在本项目 `_项目状态.md` 记录 step11 完成
6. **工作流仓库同步推送（硬要求）**：工作流本身也是项目，本轮对主控/提示词/脚本/台账的改动必须提交并推送到工作流仓库远端。
   - 提交前确认 `.gitignore` 已排除已交付项目目录（`projects/<已交付项目>/`，各自有独立仓库，防止误入工作流仓库形成嵌套 gitlink）；
   - `git add` 只加工作流自身的文件（主控、prompts、scripts、workflow_cli、WORKFLOW_*.md、模板目录）， commit message 概述本轮采纳项编号；
   - `git push origin main` 后核对远端分支已更新（`git status -sb` 显示与 origin 同步）；
   - 推送结果记入本项目 `_项目状态.md` 轮次日志。

## 11.3 收尾强制清单（报告落盘前逐项打勾，缺一不得结束）

> step11 的收尾硬闸：以下四项任一未完成，报告不得宣布完成、不得推送工作流仓库。

### ① 体检台账补全所有规则（全量不抽样）

`WORKFLOW_规则体检台账.md` 的规则行集合必须等于 WORKFLOW_规则库.md §8.0 规则登记表的 id 集合，**含 R22 / R23 / R24 / R25 / R-1 / R-2**，逐条有「最近触发/复核项目 | 连续未触发项目数 | 状态 | 复活条件」与本次体检记录行。缺行的当场补行（规则名从 WORKFLOW_规则库.md §8.0 抄，计数从 0 起算），不许只写「—」了事。

- 生产线项目：R22（逆向认知三分类）/ R-1 / R-2（翻新线卡点）**未触发是正常的**——写「未触发：路线=生产，翻新线不适用」并按未触发 +1，不得因为"不适用"就漏行
- R23（前端 UI 质量）/ R24（设计精修模式）/ R25（项目类型）每个项目都会触发，必须写清本项目在哪儿落地的（如 step06 的 `design_quality_check.py`、step01 看板字段、step09 视觉验收）
- 体检必须全量，抽几条写不算过（主控 R16 体检闸）

### ② 改进建议状态同步（已采纳 = commit + 落点，缺一不算）

扫 `WORKFLOW_改进建议.md` 所有「已采纳」行，逐条核对三样：

1. **对应 commit**：能 `git log --oneline` 找到实现该条改动的提交（把 commit 短 hash 写进该行备注）
2. **落地位置**：具体到文件与节/行或脚本参数（例：`prompts/step09_最终验收.md` §视觉质量验收；`scripts/env_preflight.py --smoke`）
3. **台账/文档落点**：涉及规则的写进 WORKFLOW_规则库.md §8.0 登记表 + `WORKFLOW_规则体检台账.md`；涉及提示词的写进 prompt 文件本身

三缺一 → 该条状态从「已采纳」改回「待落地」或「部分落地」，不允许"文档里写了就算采纳"。

### ③ 跑 `wf steps --check` 与 `wf queue --check`，输出贴进报告

在仓库根目录实跑两条命令：

```text
wf steps --check
wf queue --check
```

（未安装 `wf` 时用等价命令 `python -m workflow_cli.cli steps --check` / `python -m workflow_cli.cli queue --check`。）

要求：

- 两条命令的**原始输出**（命令、退出码、末尾若干行）原样贴进 `10_交付/工作流自迭代报告.md` 的「机器校验」小节，不得只写「已通过」；
- 任一报红 → 先修到全绿再收工；`wf queue --check` 若因历史项目/已搁置行报红，如实贴报红项并在报告里写处理结论，不许删行了事。

### ④ taste 调参挂 R23 配套

taste 调参结论、`WORKFLOW_taste_gate_观察.md` 的引用、改 `scripts/design_taste_gate.py` 的建议，规则号一律写「R23 配套（taste 子项）」，不得再出现「R25 调参」。R23 是前端 UI 质量规则，R25 是项目类型（看板字段），两者不得混用。

## 放行检查

- [ ] backlog 每条都给了 ✅/⏸️/❌ 结论，没有"以后再说"的模糊项
- [ ] 全量体检做了：每条活跃规则都有「执行落点 / 未触发原因」，休眠项已移入休眠区且未删除原文；**体检台账已补全所有规则（含 R22/R23/R24/R25/R-1/R-2），全量不抽样**（见 11.3①）
- [ ] 新增规则都带齐「落点 + 来源 + 证据」；引用全部用 R\<id\>（无「第几条」写法）
- [ ] 活跃规则 >20 时，已附「不能休眠的理由」并经用户确认（例外通道）
- [ ] 采纳项已经实际改到文件里，不是只写在报告里
- [ ] **「已采纳」条目都有对应 commit + 落地位置 + 台账/文档落点**，三缺一的已改回「待落地」（见 11.3②）
- [ ] **`wf steps --check` 与 `wf queue --check` 已实跑，原始输出（退出码 + 末尾行）已贴进 `10_交付/工作流自迭代报告.md`**（见 11.3③）
- [ ] taste 调参规则号已统一为「R23 配套（taste 子项）」，报告与观察表无「R25 调参」残留（见 11.3④）
- [ ] **已在对话里给用户 10 行以内的「工作流优化点摘要」并等审核**（哪条改什么 + 对下一个项目的影响）；不得只落盘就结束（来源 #59）
- [ ] `WORKFLOW_改进建议.md` 状态已更新（已实施的归档，暂缓/驳回的留档）
- [ ] 工作流仓库已提交并推送远端（`git status -sb` 与 origin 同步；已交付项目目录在 .gitignore 中）
- [ ] 改了主控/提示词后，无需再同步 AGENTS.md 等 4 份副本（2026-10-28 起它们已降级为指针，只指向主控）
- [ ] 告诉用户："工作流已升级，下一个项目会用上新规则。"
