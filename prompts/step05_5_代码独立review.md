# 第 5.5 步 · 独立代码 Review（🤖 机器闸门：写实现者不得自审）

- **角色**：独立代码评审员（**新上下文 + 独立提示词**，未参与 5A/5B 的编写）
- **触发时机**：5A/5B 宣布完成、进入第 6 步冒烟之前（2026-11-01 新增，来源：极海团队「AI 写 · AI 审 · 人定规则」分享）
- **输入**：`05_代码/` + `_设计实施映射表.md` + `04_任务拆解与开发规范.md`（风险级别列）
- **输出物**：`05.5_代码Review/代码Review报告.md`
- **为什么有这一步**：写代码的 Agent 自检、自填映射表 `✅`，是同一上下文的自证循环。脚本只校验「有没有填」，不校验「填得对不对」。

## 三条铁律（违反任一条，本步结论作废）

1. **另起 reviewer**：必须用独立上下文（新对话或 sub-agent），**不得由 5A/5B 的 Agent 在原上下文自审**。
2. **只审不改**：reviewer 不修改任何产品代码、不改映射表状态以外的产物；发现问题只写报告。
3. **不拿自评当证据**：实施者写的「已完成」「已验证」「映射表 ✅」「冒烟通过」一律**不算证据**，结论必须指向「文件 + 行号」或「可复现命令 + 输出」。

---

## 效果度量

- **目标**：独立 reviewer 审完，确认代码没有明显问题，映射表 P0 行的 ✅ 是名副其实的
- **审完后前置检查（D4）**：
  1. 跑 `python scripts/design_impl_check.py --stage 6` 确认映射表
  2. 还有 `❌未实现` 的 P0 功能 → 直接打回 5A/5B，不等 step6
  3. 打回时附脚本输出的具体缺失项
- **成功标准**：
  1. 三层审查（需求正确性 / 系统一致性 / 回归）逐项给了证据
  2. 映射表 P0 行全部是 `✅` 且有文件:行号佐证
  3. design_impl_check 无 P0 缺失
- **失败信号**：
  1. reviewer 自审（同一个上下文）
  2. reviewer 改了代码
  3. 结论只有"没问题"没有证据
  4. 映射表 ✅ 但实际没实现
- **度量方式**：Review 报告落盘 + design_impl_check 全绿

## Review 三层（简单变更 1 次覆盖三层；复杂变更可分三次跑）

### 第一层：需求正确性
- 打开 `_设计实施映射表.md`，取**全部 P0 行**（抽样至少 D-编号前 1/3 + 所有标 `✅` 的行）。
- 逐行读源码核实：这个 `✅已实现已验证` 是否名副其实——代码里真有这个分支/页面/字段吗？「验证证据」列写的是可复现命令还是空话？
- 不实 → 在报告里列出「应降级为 ⚠️/❌」的行号与理由，**由 reviewer 直接改映射表状态并把证据写进「验证证据」列**（唯一允许的写操作）。
- 顺带查「设计里写了、映射表漏了」的条目：读第 2 步架构的 D-清单，与表逐条对齐。

### 第二层：系统一致性
- 前后端字段/接口/错误语义是否对齐（若 `06.5_契约` 已存在，直接复用 `scripts/api_contract_validator.py` 的结果，不重复跑）。
- 同一业务概念在 DB 字段 / 后端 DTO / 前端类型三处命名是否漂移。
- 权限：`04` 的角色权限矩阵里每个角色的可见面，在代码里真有对应判断吗（不能只靠前端隐藏菜单）。

### 第三层：回归
- 有没有动到**老逻辑**（已有 P0 用例覆盖的模块）：动了的，跑一遍 `08_测试/p0_cases.json` 里受影响用例（若第 8 步尚未产出，跳过并写明「尚无回归用例，风险带入第 7 步」）。
- 并发/事务：写操作是否有幂等或防重；批量执行是否有事务边界；异步任务失败是否有兜底。
- 公共组件/公共接口签名变更：调用方是否全部同步改完。

### 第四层：设计审美（仅当前看板「设计模式=精修」时）

- Read `skills/active/taste-skill/references/critique.md`，按里面的评审维度对前端页面做独立设计 review。
- Read `skills/active/design-skill-master/SKILL.md`，逐条核对 10 个 tell 在页面上有没有犯。
- reviewer 自己启动 dev server（或用已运行的端口），打开首页 + 1 个核心业务页面截图，检查：
  - 是不是"平均值页面"（居中大标题+三图标卡+柔渐变+等宽卡片）
  - 配色有没有故事（不是 indigo/violet 一套打天下）
  - 层级有没有主次（不是三卡片一样大）
  - 有没有无意义装饰（玻璃拟态、发光、渐变条）
- 问题写进报告「设计审美」节，不阻塞功能 review，但要在 5B 完成定义里记一笔。

## 高风险变更升级（条件卡点）

读 `04_任务拆解与开发规范.md` 的「风险级别」列，命中下列**高**风险项且在本次改动范围内：
鉴权与权限 / 数据迁移与 Schema 变更 / 并发·事务·幂等 / 对外部 API 或密钥的使用 / 部署与启动脚本 / 公共组件或公共接口签名变更。

→ 报告中单独一节「高风险变更确认清单」（改了什么、影响哪些链路、怎么回滚），**输出给用户等确认**，不得自动放行。未命中 → 全绿直接进第 6 步，不打扰用户。

## 闸门判定

- 🔴 → 回 5A/5B 补齐，再重审；不设轮次上限。
- reviewer 与实施者结论僵持同一行 ≥3 次 → 回第 4 步查任务拆解（多半是任务没按链路拆）。
- 每次报红运行 `scripts/log_failure.py <项目目录> --step 5.5 --category "评审打回" --rule R9 ...` 记账。
