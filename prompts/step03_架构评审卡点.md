# 第 3 步 · 架构评审卡点（强制卡点，不通过不往下走）

- **角色**：资深技术评审专家 / 资深软件架构师
- **输入**：《项目基线说明书》+《技术架构设计文档》（均**全量**）
- **输出物**：
  - `03_评审报告/第一轮架构评审报告.md`
  - 评审通过后：`02_架构设计/第二轮技术架构设计文档.md`（定稿）
  - `03_评审报告/第二轮架构复审报告.md`
- **流转**：结论「修正后通过 / 不通过」→ 回第 2 步修订并重跑评审；「通过」→ 产出第二轮定稿并进入第 4 步。
- **👤 人工检查点（不可跳过）**：AI 评审完后，用户必须自己再看一遍架构文档，重点：① 技术选型本地环境能不能装、版本有没有冲突；② 有没有明显遗漏模块。AI 倾向于给自己打「通过」，不要全信。

## 3.1 第一轮评审 Prompt

```
你是资深技术评审专家，基于项目基线和架构设计文档，输出《第一轮架构评审报告》。
【P0 严格定义】
只有满足以下任一条件才算 P0 致命问题：
1. 会导致核心业务链路完全不通
2. 会导致核心性能指标肯定不达标
3. 存在技术选型不兼容、无法落地的硬冲突
4. 存在严重的数据一致性、可用性风险
可运行但不够优、可扩展但不够好的，一律归为 P1/P2，不算 P0。
【强制检查项：指标→机制映射】
逐条核对基线《项目基线说明书》里的每个量化成功指标（如响应时长、准确率、并发用户数、数据保留时长等），
在架构文档中找出它对应的实现机制（如：准确率→是否有相似度阈值过滤/重排/兜底降级；响应时长→是否有缓存/异步队列/索引设计）。
凡是「基线写了指标，但架构上没有任何机制支撑它达标」的，一律记为 P1 及以上问题——这是真实项目里最常见的「验收才发现的需求理解偏差」。
【输出要求】
1. 一次性列全所有问题，按 P0 / P1 / P2 分级，禁止分批输出
2. 每个问题必须包含：问题描述、影响范围、严重等级、明确的修改建议
3. 明确给出：如果所有 P0 问题按建议修改，是否可以通过评审
4. 最终结论：通过 / 修正后通过 / 不通过
要求：问题准确，建议可落地，不吹毛求疵，不把优化建议包装成 P0。
```

## 3.2 第二轮架构修订 Prompt（仅当存在需修正的 P0 时，回第 2 步使用）

```
你是资深软件架构师，基于《项目基线说明书》《第一轮架构评审报告》，输出完整的《第二轮技术架构设计文档》。
【输出要求】
1. 技术选型说明：对应基线需求的组件选型、版本选择理由、兼容性说明
2. 整体分层架构：按接入层、存储层、计算层、服务层、应用层、运维层划分，明确每层职责与组件
3. 核心业务链路：梳理所有核心业务流程，画出端到端的数据流/调用链，明确每个节点的输入、处理逻辑、输出
4. 数据模型设计：核心表结构设计、字段规范、主键/分区/索引设计、表关联关系
5. 接口规范定义：统一的API请求/返回格式、错误码规范、鉴权规则，核心接口清单
6. 部署架构设计：部署方式、高可用方案、弹性扩缩容策略、环境划分
7. 监控与运维：监控指标体系、告警规则、运维流程
8. 技术风险与应对方案：核心风险点、兼容性风险、性能风险、应对方案
要求：设计完整、边界清晰、可直接指导开发，优先考虑可扩展性与可维护性。
```

## 3.3 第二轮复审 Prompt（只验上一轮 P0）

```
你是资深技术评审专家，针对上一轮评审提出的问题进行复审，输出《第二轮架构复审报告》。
【评审规则】
1. 只验证上一轮列出的 P0 问题是否按要求修复，逐一核对
2. 上一轮的 P1/P2 问题不做验证
3. 本次新发现的问题，统一列入「后续优化建议」，不纳入本次评审结论，不阻塞通过
4. 不允许提出新的 P0 级问题
【输出要求】
1. 对上一轮每个 P0 问题逐一给出验证结果：已修复 / 未修复 / 部分修复
2. 未修复的说明原因和再次修改建议
3. 后续优化建议：本次新发现的非阻塞性问题
4. 最终结论：通过 / 需再次修正上一轮遗留问题
严格遵守评审范围，不扩大、不新增。
```
