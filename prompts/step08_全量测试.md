# 第 8 步 · 第一轮全量测试

- **角色**：资深测试工程师 / 资深开发工程师
- **输入**：《项目基线说明书》+ 联调通过的完整系统
- **输出物**（落盘 `08_测试/`）：
  - 《全量测试用例清单》
  - 《第一轮全量测试 Bug 清单》（只列 P0/P1，P2/P3 入待优化）
  - 8-1 修复：代码片段 + 修改影响分析 + 自测说明
  - 8-2《第二轮回归测试报告》
- **规则**：本轮只修 P0/P1，P2/P3 记下来留到下版本；修复-回归最多 2 轮，通过后进入第 9 步。

---

## 8.1 测试用例生成 Prompt

```
你是资深测试工程师，基于项目基线和功能清单，帮我生成一份全量测试用例清单。
【项目基线】
{{粘贴《项目基线说明书》}}
【功能清单】
{{粘贴任务拆解中所有P0/P1模块的功能点}}
【输出要求】
1. 按功能模块分组，每个功能点写出：正常用例 + 异常用例（空值、超长、边界、权限不够等）
2. 每条用例包含：前置条件、操作步骤、预期结果
3. 标注哪些用例是 P0（必须通过才能上线）、哪些是 P1
4. 【额外要求】把所有 P0 用例同时输出为 p0_cases.json（HTTP 接口用例格式：id/name/method/url/headers/body/expect_status/expect_json_contains，见 scripts/p0_regression_test.py 的 docstring），供自动化回归脚本使用
```

> 用户在本地照用例一条条测，把发现的问题记成 Bug 清单。P0 接口用例可用 `python scripts/p0_regression_test.py p0_cases.json` 自动跑，不必手点。

**Bug 分级**：P0 致命 / P1 严重 / P2 一般 / P3 轻微。本轮只修 P0 和 P1，P2/P3 留到下版本。

## 8.1.5 基线量化指标验证表（必做，不能跳过）

《项目基线说明书》里写的每个量化成功指标（响应时长、准确率、并发数、数据保留时长等），**到这一步必须给它一个验证归属**，不许默认达标：

```
请基于《项目基线说明书》，输出《基线指标验证表》：
| 基线指标 | 目标值 | 验证方式（自动化断言/人工实测/未验证） | 验证结果 |
逐条处理：
- 能自动化的：写进 p0_cases.json 或单独写一个 benchmark 脚本
- 只能人工测的：写清楚实测步骤和判定标准
- 既不能自动化也不好人工测的：标注「未验证风险」，如实告诉用户这个指标目前无法保证
禁止写「预计达标」「应该可以」这种模糊结论。
```

> 真实项目踩过：基线写了「85% 准确率」，一路跑到验收才发现架构上根本没有相似度阈值机制——指标是写在纸上的，没有任何代码支撑。这张表就是在第 8 步把这件事摊牌。

## 8.2 全量测试 Bug 清单 Prompt

```
你是资深测试工程师，基于项目基线和联调通过的系统，执行第一轮全量测试，输出《第一轮全量测试Bug清单》。
【输出要求】
1. 测试范围：本次测试覆盖的功能、链路、场景
2. 严重等级划分：
   - P0 致命：功能完全不可用、数据错误、系统崩溃、核心链路中断
   - P1 严重：核心功能异常、性能不达标、无异常兜底
   - P2 一般：非核心功能异常、交互体验问题
   - P3 轻微：样式、文案、提示类小问题
3. Bug清单：只列出P0和P1级Bug，每个包含：Bug编号、严重等级、Bug描述、复现步骤、预期结果、影响范围
4. 待优化建议：P2、P3级问题统一放入这里，不列入本轮修复
5. 未覆盖场景：本次测试未覆盖的场景与边界
【强制要求】
一次性列全所有P0、P1级Bug，禁止分批输出。本轮只修复P0和P1，P2及以下不处理。
```

**输出物**：分级 Bug 清单（P0+P1 为必修，P2+P3 留到下版本）

## 8.3 8-1 Bug 定向修复 Prompt

**输入**：原有代码 + 第 7 步输出的 P0+P1 Bug 清单

```
你是资深开发工程师，基于现有代码，修复第一轮全量测试 bug 清单列出的所有P0、P1级Bug。
【严格执行规则】
1. 只修复清单内的Bug，禁止任何额外的优化、重构、代码调整，禁止超范围修改
2. 修改前先输出「修改影响分析」：每个Bug的修改点、涉及的文件/函数、可能影响的其他功能
3. 修改后的代码标注：// 修复Bug-xxx 改动原因
4. 只输出有修改的代码片段，不输出完整全部代码
5. 修复完成后输出「自测说明」：每个Bug的验证方法
禁止修改不在清单内的任何逻辑，禁止重构原有正常运行的代码。
```

**输出物**：修改后的代码片段 + 修改影响分析 + 自测说明

## 8.4 8-2 定向回归测试 Prompt

**输入**：修复后的代码 + 原 Bug 清单 + 修改影响分析

```
你是资深测试工程师，执行本轮Bug修复的定向回归测试，输出《第二轮回归测试报告》。
【回归范围】
仅验证以下内容，不做范围外的全量测试：
1. 上一轮所有P0、P1级Bug是否修复
2. 修改影响分析中提到的关联功能是否正常
【输出要求】
1. 已修复验证：每个原Bug的验证结果（通过/未通过），未通过的说明原因
2. 引入新Bug：在修改影响范围内新发现的Bug，同样分级
3. 范围外新问题：本次测试中范围外发现的新问题，统一列入「下一轮待处理」
4. 结论：本轮回归是否通过，是否需要再次修复
【强制规则】
严格按既定回归范围执行，不扩大测试范围，范围外问题不纳入本轮结果。
```

**输出物**：回归测试报告
